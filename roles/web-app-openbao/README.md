# OpenBao

## Description

[OpenBao](https://openbao.org/) is an identity-based secrets and encryption manager governed by the Linux Foundation. It stores application credentials, API keys, service and database credentials, automation and agent identities, short-lived tokens and encryption keys behind a policy engine, and can act as an internal certificate authority.

## Overview

This role deploys OpenBao as an Infinito.Nexus application at `openbao.<domain>`, behind the platform's HTTPS reverse proxy. Humans sign in through Keycloak with OIDC and receive exactly the privileges their RBAC group grants; machines authenticate separately through AppRole. State lives in OpenBao's own raft store on a persistent volume, and a static seal auto-unseals the node on every restart so no operator has to intervene after a redeploy.

## Features

- **Keycloak OIDC login:** The `jwt`/`oidc` auth method is configured against the platform Keycloak, so users sign in with their existing Infinito.Nexus identity. Logout integrates with `web-svc-logout`.
- **Login Methods:** `services.openbao.login.method.*` in [meta/services.yml](./meta/services.yml) decides which auth mounts exist ([tasks/04_auth_methods.yml](./tasks/04_auth_methods.yml), [tasks/utils/oidc.yml](./tasks/utils/oidc.yml), [tasks/utils/userpass.yml](./tasks/utils/userpass.yml)). `sso` sets `listing_visibility=unauth` on the `oidc/` mount, so the login page opens on the OIDC entry; otherwise the mount is `hidden`. `ldap` enables and configures the `ldap/` mount when `svc-db-openldap` is deployed and disables it when the method is off, so with SSO on LDAP accounts sign in through the Keycloak federation. `native` enables the `userpass` mount described below. OpenBao offers no self-registration and no passkey, and its login MFA is an enforcement policy rather than a factor users opt into, so the role declares none of them.
- **Local administrator:** While the `native` method is on (by default when neither Keycloak nor `svc-db-openldap` is deployed), the `userpass` auth method carries one account, the platform administrator bound to the `administrator` policy. The role marks the mount it enables with the description `infinito-nexus-managed`. A deploy with the method off disables a mount that carries this mark; a `userpass` mount without it is left untouched.
- **Break-Glass:** The recovery key mints a root token from the CLI (`tasks/utils/recover.yml`), and the Token method, which stays on the login page under "Other" in every mode, signs that token in; AppRole keeps machine access. [test-login-token-administrator.js](./files/playwright/test-login-token-administrator.js) proves the browser half: the Token method signs an administrator token in and the logout revokes it. It takes that token from the LDAP or userpass method where the deployment provisions one, and through Keycloak where SSO is the only method, because the runner holds no Keycloak-independent administrator credential then; no spec drives the CLI half.
- **Group-mapped RBAC:** The Keycloak `groups` claim binds to OpenBao external identity groups carrying the `administrator`, `operator` and `reader` policies. Authenticating on its own grants only `default`.
- **Profile metadata:** The OIDC role's `claim_mappings` copy the email and name claims into the token and entity alias metadata on every login.
- **Automatic unsealing:** A `static` seal reads a 32-byte key from the encrypted inventory, so the node unseals itself on every container restart.
- **Machine identity:** AppRole is configured independently of human login, so services and automation use their own identities and short-lived tokens instead of a shared administrator token.
- **Optional internal PKI:** A service flag mounts the `pki` engine with an internal root CA and an issuing role.
- **Audit trail:** A `file` audit device at `stdout/`, declared in the server config, writes every request, with the accessing identity and a timestamp, to the server's stdout and so to the container log. Secret values appear only as salted HMACs. Every deploy reads a probe secret and fails unless the log shows that read with its identity and time.
- **Monitoring:** Prometheus scrapes `/v1/sys/metrics` on the role-local network. A sealed node is detected from `/v1/sys/health`, which answers 503 while sealed and 200 once unsealed.
- **Automated provisioning:** Configured by Ansible without manual steps; no Keycloak client or OpenBao path has to be created by hand.

## Developer Notes

- **The seal key is the whole ballgame.** The `static` seal wraps the raft root key with `secrets.credentials.seal_key`, injected as `env://OPENBAO_SEAL_KEY`. A backup of the raft volume is **undecryptable without it**, and `svc-bkp-secrets-2-local` does not cover it — the encrypted inventory is its only home, so back the inventory up accordingly. It is pinned `rotatable: false`: the static seal carries one generation of slack, and spending that every deploy makes any skipped generation unrecoverable. Rotate it deliberately by changing the inventory value; `openbao.hcl.j2` then emits the `previous_key`/`previous_key_id` pair, the node unseals with the old key and rewraps to the new one.
- **The recovery key is the way back in.** `bao operator init` issues it once and nothing reissues it, which is what makes it useful — it is the only authority here that does not rotate. It is persisted through `sys-token-store` (`DIR_SECRETS`, backed up, and it survives both `RESET` and a replaced manager, each of which takes `.applied.json` with it). When neither the inventory AppRole nor the recorded one is accepted, `tasks/utils/recover.yml` mints a root token from it and re-pins the AppRole. It cannot decrypt the store — only the seal key can — so it is not a substitute for backing up the inventory.
- **Every deploy rotates the AppRole.** The `role_id`/`secret_id` a run is handed are not the ones the running instance holds. `tasks/01_init.yml` tries the inventory pair, falls back to the pair recorded in `.applied.json`, then `tasks/06_rotate.yml` re-pins to this run's values and destroys the old SecretID. The record is written last, so a run that dies partway leaves the previous generation intact. `custom-secret-id` is **not** idempotent — re-writing a held SecretID answers `500` — so the swap is gated on the value having changed.
- **Bootstrap leaves no stored root token.** The first deploy holds it in memory, pins both AppRole halves to inventory values, then revokes it. Tokens reach the CLI through stdin and the container token helper, never through process arguments, and the helper file is removed at the end of the run.
- **Paths that look wrong and are not.** Policies mount at `/openbao/policies/`, because OpenBao parses *every* file under `-config` as server configuration. Storage is `/openbao/file`, not `/openbao/data`: the image pre-chowns only `/openbao/{config,logs,file}` for the non-root `openbao` user, so a volume elsewhere lands root-owned and raft cannot write. `command:` is just `server` — the entrypoint appends `-config` itself, and passing it duplicates the flag.
- **The LDAP auth method is an external plugin.** `files/Dockerfile` copies the `openbao-plugin-auth-ldap` binary out of the `auth-ldap` image declared in `meta/services.yml` into `/opt/openbao/plugins`, and `templates/plugins.hcl.j2` registers it as `plugin "auth" "ldap"` under the tag of that image. The file sets `plugin_auto_register = true` explicitly, because the server loads a config directory and 2.7.1 does not apply the documented default on that path. The mount is enabled with `-plugin-version=latest`, so it loads whichever plugin version the running image ships. To upgrade the plugin, bump `auth-ldap.version` and redeploy. `tasks/addons/auth-ldap.yml` tunes and reloads a mount that the former builtin engine created.
- **Do not alert on `vault_core_unsealed`.** OpenBao keeps Vault's metric namespace, and a healthy unsealed node emits `vault_core_unsealed{cluster=""} 0`, so an alert on `== 0` fires permanently. Use `/v1/sys/health` (503 while sealed); `vault_core_active{cluster="…"} == 1` corroborates.
- **Alert rules ship with the role.** `templates/prometheus/alert_rules.yml.j2` is discovered by the `alert_rule_roles` lookup, which returns only roles that are actually scraped, so the fragment carries no activation guard of its own. It must start at the `groups:` item level.
- **Swarm:** single replica, `placement: manager`, `nfs: false` on the raft volume, `service_update_order = stop-first`. Raft's BoltDB store is mmap + `fsync` based, so it must stay node-local and must never have two tasks writing one directory.
- **CLI OIDC login is out of scope.** `redirect_uris` registers `https://<domain>/*`, covering UI and API callbacks but not the CLI's `http://localhost:8250/oidc/callback`. Use AppRole for non-interactive access.
- **Test notes.** The RBAC tiers are proven by moving `biber` through the groups with LAM's Multi edit tool and asserting both the grant and the revoke, rather than by dedicated accounts. The UI's own `vault.cluster.logout` route behind `/ui/vault/logout` and the user menu's *Log out* link at most clear the token from browser storage, and with `logout` enabled the universal-logout patch sends that link to the Keycloak end-session URL instead. So the role injects `files/javascript/javascript.js`: on a click of the logout control, before that redirect, and on a direct load of `/ui/vault/logout`, it posts `revoke-self` for every token in the `vault-*` browser storage and then clears that storage. A token that escapes the revoke ends with the SSO session, because the OIDC role takes `token_ttl` and `token_max_ttl` from the Keycloak realm's `sso_session_idle_timeout_seconds` and `sso_session_max_lifespan_seconds` (30 minutes and 10 hours), the values its `ssoSessionIdleTimeout` and `ssoSessionMaxLifespan` render from.

### Workspaces

While `web-app-semaphore` is deployed, the role runs after it and keeps every workspace secret in OpenBao ([tasks/07_workspaces.yml](./tasks/07_workspaces.yml), [tasks/workspace.yml](./tasks/workspace.yml)).

- **The `jwt` mount.** `auth/jwt` trusts Semaphore's task tokens: `jwks_url` is `<semaphore origin>/.well-known/jwks.json`, `bound_issuer` is the Semaphore origin, and under `TLS_MODE` `self_signed` `jwks_ca_pem` holds the deployment CA. `auth/jwt-export` carries the same configuration for the export project.
- **Roles per workspace.** `workspace apply` writes `ws-<id>`, bound to the workspace project, `ws-<id>-provision`, bound to the provision project and its `unlock` and `dns` templates, one `ws-<id>-provision-<provider>` per provider of `OPENBAO_PROVISION_SECRETS`, bound to the provision project and that provider's own `provision-<provider> ws-<id>` and `destroy-<provider> ws-<id>` alone, so the task token's `template_id` picks the provider and a token of one provider's template logs in to no other provider's role, and `ws-<id>-zone`, bound to the provision project and `zone ws-<id>` alone, into `auth/jwt`, and `ws-<id>`, bound to the export project and `export ws-<id>`, into `auth/jwt-export` ([templates/workspace/jwt_roles.json.j2](./templates/workspace/jwt_roles.json.j2)). Every `apply` also keeps `members` in `auth/jwt`, bound to the Workspaces project and its `members` template, with the policy `members`, which grants `read` on `platform/data/store/invites/*` and nothing else, so `members invite` reads the address the store staged; `destroy` leaves it, since it serves every workspace. Every deploy writes the identity of the Workspaces project, the fact `semaphore_workspaces_identity` that Semaphore sets, to `platform/data/store/semaphore/workspaces` whenever it differs from the stored entry; the store pins the project and its `workspace`, `members` and `user` templates from there. The store's deploy writes its ERPNext API identity keys below `platform/data/store/erpnext/` through `ansible-admin`, which may create, read and update that subtree and no other store entry. Every `project_id` and `template_id` is a JSON number, because a numeric claim never matches a string; each role binds the audience `openbao` and uses `sub`, `task:<task id>`, as its `user_claim`, so every task logs in as an alias of its own. Its `token_ttl` comes from `services.openbao.workspaces.token_ttl`.
- **The templated policy.** `tenant` grants `read` on `tenant/data/<role>/*` and `update` on `transit/datakey/plaintext/<role>` and `transit/decrypt/<role>`, where `<role>` is the `role` metadata of the login's `jwt` alias, which OpenBao sets from the role name and no claim can set. The deploy role alone carries `tenant`. Each provision role carries the per-workspace policy of its own name ([templates/workspace/provision_policy.hcl.j2](./templates/workspace/provision_policy.hcl.j2)), which `apply` writes and `destroy` deletes: `read` on `tenant/data/ws-<id>-provision/s3`, `tenant/data/ws-<id>-provision/dns` and `platform/data/provision/transit/ws-<id>`, and `update` on `auth/token/create/ws-<id>-transit-child` and `auth/token/create/ws-<id>-dns-child` alone, never on bare `auth/token/create`; it reads no Cloudflare zone token. `ws-<id>-provision` reads no provider secret. `ws-<id>-provision-<provider>` adds the `workspace` paths of its provider in `OPENBAO_PROVISION_SECRETS`, the customer's own token, and its `platform` paths only while the apply input `WORKSPACE_PLATFORM_TOKENS`, the store's switch, is `true`; so a run reads no secret of another provider, and without the switch only `PROVIDER_TOKEN=workspace` runs. No provision policy reads the zone token. `apply` also deletes every `ws-<id>-provision-<provider>` role and policy of a provider the table no longer names ([files/shell/prune-provider-access.sh](./files/shell/prune-provider-access.sh)). The shared policy `provision-shared` of earlier releases is gone: every deploy deletes it, each `ws-<id>-provision` role that holds another policy than its own or binds other than two templates, and each `ws-<id>-transit-child` token role that allows another policy than `ws-<id>-transit` ([files/shell/drop-shared-provision.sh](./files/shell/drop-shared-provision.sh)), and fails on any OpenBao answer but "No policy named" or "No value found", so the provision, destroy, unlock and dns tasks of a workspace fail closed until its next `workspace apply` writes its roles and templates again. The zone role carries the per-workspace policy `ws-<id>-zone` ([templates/workspace/zone_policy.hcl.j2](./templates/workspace/zone_policy.hcl.j2)), which `apply` writes and `destroy` deletes: `read` on the zone token, on `tenant/data/ws-<id>-provision/s3` and on `platform/data/provision/transit/ws-<id>`, and `update` on `auth/token/create/ws-<id>-transit-child`, nothing else. No task role carries `ws-<id>-transit` ([templates/workspace/transit_policy.hcl.j2](./templates/workspace/transit_policy.hcl.j2)): `update` on `transit/datakey/plaintext/ws-<id>-provision` and `transit/decrypt/ws-<id>-provision` alone. `apply` writes it together with the token role `ws-<id>-transit-child` (`allowed_policies` `ws-<id>-transit`, `disallowed_policies` `default`, `orphan` and `renewable` false, `token_explicit_max_ttl` the provision task token TTL, `token_no_default_policy` true), and `destroy` deletes both. No role policy grants the transit key; a run mints one child through that token role, which carries `ws-<id>-transit` alone, hands only that one to OpenTofu, and revokes its own token with `auth/token/revoke-self` at the end, which revokes the child too. `tenant-export` grants `read` on `tenant/data/<role>/*` and `list` on `tenant/metadata/<role>/*` through the `role` metadata of the `jwt-export` alias, and `export-shared` reads `platform/data/export/*` and lists `platform/metadata/export/owners/`.
- **The DNS broker.** The token of each Cloudflare zone, `platform/data/provision/cloudflare/<zone>`, is read by two platform identities alone: `ansible-admin`, which writes it, and the policy `dns-broker` ([templates/policies/dns-broker.hcl.j2](./templates/policies/dns-broker.hcl.j2)), `read` on `platform/data/provision/cloudflare/*` and on the DNS scopes `platform/data/provision/dns-scope/*` and nothing else, which every deploy writes beside the other workspace policies. No workspace policy reads a zone token, so a workspace sharing a zone with another one holds no credential that rewrites the other's records. `apply` pins the DNS scope of the workspace, the `zone` and `zone_id` of the `workspace_dns` fact, at `platform/data/provision/dns-scope/ws-<id>`, so a zone change needs a re-apply, and writes the broker caller policy `ws-<id>-dns` ([templates/workspace/dns_policy.hcl.j2](./templates/workspace/dns_policy.hcl.j2)), `read` on `auth/token/lookup-self` alone, with the token role `ws-<id>-dns-child`, which carries the fields of `ws-<id>-transit-child` and allows `ws-<id>-dns` alone. A run mints one such child through its provision role and hands only that child to OpenTofu as its Cloudflare credential. The broker looks the presented child up with the child itself and takes the workspace from its one policy `ws-<id>-dns`, and the zone and zone id from that workspace's DNS scope, which it reads with its own identity; no part of the scope comes from the request. It forwards a call with the zone token only for a record `<label>.ws-<id>.<zone>` of type A, AAAA or CNAME in that zone id, and refuses any other, a record of another workspace in the same zone included, before it forwards anything (`provision/dns/scope.py` in `web-app-semaphore`). The knot and route53 flavors never reach the broker: their credential stays `tenant/data/ws-<id>-provision/dns`. The broker logs in per call with the AppRole `dns-broker` ([tasks/utils/dns_broker.yml](./tasks/utils/dns_broker.yml)), bound to the policy `dns-broker` alone, with short-lived tokens it revokes after the call; its pair is `secrets.credentials.dns_broker_approle_role_id` and `secrets.credentials.dns_broker_approle_secret_id`, which `web-app-semaphore` writes into a file only the broker's own uid reads, so no workspace task and no sandbox holds it.
- **Two KV v2 mounts.** `tenant` holds the workspace secrets, `platform` the store's service credentials and the provision secrets every workspace shares. Neither lies under `infinito`, and `reader`, `operator` and `administrator` grant nothing on either.
- **The transit key and its snapshot.** `workspace apply` creates `transit/keys/ws-<id>-provision` once as `aes256-gcm96`, with `exportable`, `allow_plaintext_backup` and `deletion_allowed` false. Right after a new key it writes a raft snapshot into `<DIR_BACKUPS>/web-app-openbao/raft/`, fails when that write fails, and keeps only the newest `services.openbao.workspaces.raft_snapshots` (3) snapshots there, since each one holds the whole store and so every key that still exists; then it records `key_created_at` and `snapshot_at` in `platform/data/provision/transit/ws-<id>`, which the provision script compares before it writes state.
- **Erasure by `workspace destroy`.** `destroy` refuses while the workspace still holds OpenTofu state. Then it deletes the four roles, every `ws-<id>-provision-<provider>` role and policy it finds, whether or not the table still names the provider, the zone, transit and broker caller policies with the token roles `ws-<id>-transit-child` and `ws-<id>-dns-child`, the provision policy, every version of every secret below `tenant/data/ws-<id>/` and `tenant/data/ws-<id>-provision/` ([files/shell/erase-tree.sh](./files/shell/erase-tree.sh) lists `tenant/metadata/` below both prefixes and deletes the metadata of each key), the workspace's monitoring tree below `monitoring/data/ws-<id>/` (digests, agent key mirror, label bindings and the release tombstones of requirement 138) and its federation tokens below `platform/data/monitoring/federation/ws-<id>/` with the same script, the pinned Owner group, the DNS scope, and last the transit key, by turning its `deletion_allowed` on. It is the one erasure path of a workspace; the store holds no delete on roles or keys.
- **The store AppRole.** The role `store` carries the policy `store` and nothing else, not even `default` ([templates/policies/store.hcl.j2](./templates/policies/store.hcl.j2)): `create` and `update` on `tenant/data/ws-*` without `read`, `read` and `delete` on `tenant/metadata/ws-*` (versions, never values), `read` on `platform/data/store/*`, `create`, `read` and `update` on `platform/data/store/workspace-keys/*` with `delete` on its metadata, full access to the pinned host keys with `list` only within one workspace's entries, `create` and `update` on `platform/data/store/invites/*` without `read` or `delete` to stage an invite (`{email, role}`), `delete` on `platform/metadata/store/invites/*` so that staged invite is erased with every version after the invite and on uninvite, and `update` on its own `secret-id`, `secret-id-accessor/destroy` and `secret-id/lookup`. No `auth/jwt`, `sys` or transit path, no `list` on `tenant`, no `custom-secret-id`. Its SecretID lives 720 h, its tokens 1 h and at most 4 h. The deploy pins the RoleID to `store_approle_role_id` and seeds `store_approle_secret_id` only while the role holds no SecretID.
- **Reach of a leaked store credential.** It writes and deletes any workspace secret without reading it, reads the store's own Semaphore and Gitea tokens, stages and erases an invite without reading a staged one, and replaces a pinned host key, so a host template would trust a server that pretends to be the host; that reaches no more than the `HOST_KEY` the store already passes to the six host templates. It lists the pinned hosts and ports of a workspace whose id it knows, and no list of the workspaces themselves. It reads no Keycloak credential and no workspace secret.
- **The workspace-key records.** An entry `platform/data/store/workspace-keys/ws-<id>` holds the public half of the workspace key `tenant/data/ws-<id>/ssh` and the KV version the store's check-and-set write of it returned. After a crash between its writes the store treats the key as its own only when that version is still `current_version` of `tenant/metadata/ws-<id>/ssh` and the public half matches its intent. No task token reads it.
- **The pinned host keys.** An entry `platform/data/store/hostkeys/ws-<id>/<host>/<port>` holds exactly one field, `line`, the server's public host-key line `<type> <base64>`. The store writes, reads and deletes it, and erases a workspace's entries by listing `platform/metadata/store/hostkeys/ws-<id>/` and `platform/metadata/store/hostkeys/ws-<id>/<host>/` and deleting the metadata of each `<port>`; `list` on `platform/metadata/store/hostkeys/` itself stays refused, so no store token enumerates the workspaces. No task token reads it.
- **The monitoring secrets (requirement 138).** The Checkmk login of the template `monitoring` lies at `platform/data/monitoring/checkmk` (`username`, `secret`), the federation token of each customer instance at `platform/data/monitoring/federation/<ws-id>/<host>` (`token`) and the read key of each workspace inventory repository at `platform/data/monitoring/inventory/<ws-id>` (`private_key`). The jwt role `monitoring`, bound to the Workspaces project and that template by number from `semaphore_workspaces_identity`, carries the policy `monitoring`, which reads these three and the platform monitoring public key at `platform/data/monitoring/agent-key`, mints and erases the federation tokens, and writes each token's SHA-256 digest to `monitoring/<ws-id>/federation/<host>` (`federation_token_sha256`) and that public key to `monitoring/<ws-id>/agent` (`public_key`), both on the KV mount `monitoring`, where the policy `tenant` lets the workspace's deploy read its own entries. No policy but `monitoring` writes that mount, so the store AppRole can neither replace a digest nor read one; no other template and not the store AppRole reads a token or the Checkmk login; the Ansible deploy writes the Checkmk login and the read keys.
- **The rotation of the store's other credentials.** The scheduled template `rotate store credentials` writes the store's Semaphore token to `platform/data/store/semaphore` and its Gitea token to `platform/data/store/gitea`. Each entry holds exactly two fields: `token`, and `expires_at`, the moment the rotation revokes that token, as RFC 3339 with a numeric UTC offset, 14 days after the mint. The template logs in to `auth/jwt` with the role `store-credentials`, which every deploy binds to the Workspaces project and that template by number from `semaphore_store_rotation_identity`; its policy `store-credentials` grants `create` and `update` on these two paths and nothing else, and the store reads both through `read` on `platform/data/store/*`.
- **The Playwright AppRole.** Only while the deploy runs the test runner (`RUNTIME` `dev`, `act` or `github`) and the workspace mounts exist, the role `playwright` carries the policy `playwright` and nothing else, not even `default` ([templates/policies/playwright.hcl.j2](./templates/policies/playwright.hcl.j2)): `read` on `tenant/data/+/proxmox`, `tenant/data/+/incus`, `tenant/data/+/s3` and `tenant/data/+/dns`, on `platform/data/provision/proxmox-*` and `platform/data/provision/incus-*`, on the transit snapshot records `platform/data/provision/transit/ws-*` and the transit key settings `transit/keys/ws-*`, on `platform/data/fixture/+/workspace-ssh` (the workspace fixture key the workspace deploy specs stage, see `web-app-semaphore`), on the two logins `platform/data/playwright/semaphore` (the Semaphore break-glass `username` and `password`) and `platform/data/playwright/store` (the store AppRole `role_id` and `secret_id`), and `update` on `auth/token/revoke-self`. It also holds `list` and `sudo` on `auth/token/accessors` and `update` on `auth/token/lookup-accessor` and `sys/capabilities-accessor`, so a spec proves what the token of a locked template reaches without a change to that template's script: it looks for the token under the display name `<mount>-task:<task id>`, built from the login mount and the task token's `sub` (unverified until a CI run of the spec proves it), and reads its login path, its `role` metadata, its policies and OpenBao's ACL decision on a path. These answers carry metadata and capability lists, never a token or a secret value, and the policy grants no revoke by accessor and no token creation. No write, no other `list`, no other `sys` path, no `auth/approle` path, and no transit path but `read` on `transit/keys/ws-*`, so no data key and no decrypt. The Playwright env files carry `playwright_approle_role_id` and `playwright_approle_secret_id` instead of the Ansible AppRole, the store AppRole or the break-glass password; a spec that acts as the store or as the break-glass account reads that login at run time and revokes its token. A deploy whose pair OpenBao refuses drops the role and registers it again; a deploy outside the test runtimes deletes the role, its policy and both logins.
- **The fixture reader.** Only while `web-app-semaphore` builds its deploy fixture does it hand over `semaphore_fixture_reader_identity`, the ids of the `workspace` template of the Workspaces project; then [tasks/07_workspaces.yml](./tasks/07_workspaces.yml) writes the policy `fixture` ([templates/policies/fixture.hcl.j2](./templates/policies/fixture.hcl.j2)), which grants `read` on `platform/data/fixture/*` and nothing else, and binds the jwt role `workspace-fixture` to that project and template by number with that policy alone ([templates/fixture_reader_role.json.j2](./templates/fixture_reader_role.json.j2)). `workspace.sh` logs in with it before its play, so the play resolves the OpenBao references the fixture holds for the platform host.

### Backup and restore

Backups run through `svc-bkp-volume-2-local` with `backup.stop_required: true`, so the container is quiesced for a consistent copy of the raft volume. To restore:

1. Restore the `openbao_data` volume from the backup generation.
2. Confirm the inventory still holds the original `seal_key` — a different key makes the restored store unreadable.
3. Redeploy the role. The static seal unseals the restored store automatically; verify with `/v1/sys/seal-status` (`sealed: false`) and read back a known secret. The redeploy also deletes `provision-shared` and the `ws-<id>-provision` roles naming it again, which a backup taken before 133 brings back; run `workspace apply` for each workspace afterwards.
