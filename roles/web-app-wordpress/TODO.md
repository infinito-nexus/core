# To-dos

- Core version drift: the image `wordpress:7.1.2` ships core 7.1.2 (`/usr/src/wordpress/wp-includes/version.php`), the data volume of a fresh install ran 7.1.3 when it was first measured, 77 minutes after its creation (`wp core version`, body class `version-7-1-3` in wp-admin). WordPress applies minor core updates in the background inside the volume, so the running version leaves the pin in `meta/services.yml`. Options: set `WP_AUTO_UPDATE_CORE` to `false` in `wp-config.php` and update through the image, or keep the background updates and stop treating the pin as the running version.
- `tasks/02_install.yml` passes the administrator password to `wp core install` as `--admin_password=<value>` on the command line of `container exec`, where the process list of the host shows it for the run of the command. Options: `wp core install --prompt=admin_password` with the value on stdin, or `wp user update <login> --prompt=user_pass` after an install that sets a throwaway value.
- A `site-owner` member who is no inventory user gets a site at the first SSO login but, without a wildcard certificate, no vhost, so that site is reachable only where a wildcard certificate is available. Options: add Keycloak members to `domains.served` at deploy from the directory (`tasks/utils/rbac/members.yml`), or leave such members to the wildcard modes.
- No variant enables `litellm` together with Multisite, so `files/playwright/addons/infinito-ai-engine-network.spec.js` skips in every round and the AI Engine network guard is proven by `tests/unit/python/roles/web-app-wordpress/test_ai_engine_network_guard.py` only. Options: enable `litellm` in the Multisite variant, or add a Multisite variant with `litellm`.
- `files/playwright/test-multisite-rbac.js` checks the member's own site with the protocol of the pass's base URL (`:78`, `:92`, `:112`, `:146`): on the Tor pass that is `http://` on an onion base, while own sites exist only on the regular network with TLS (served names get no onion sibling), and the own-site login redirect host at `:159` and the `maxRedirects: 0` POST at `:134-139` expect the onion network. Measured in `/tmp/compose-deploy-iam-20.log`; the SOCKS failure of the same spec is fixed by the served domains in `plugins/lookup/browser_proxy_bypass.py`. Options: render `WORDPRESS_SITE_OWNER_BASE_URL` into `templates/playwright.env.j2` from the served name through `lookup('tls', …)` and check own sites on their own network in every pass, or skip the own-site checks on the Tor pass.
- On the clearnet pass the same spec stops at `:113-114` because the REST nonce request answers 400 (`/tmp/compose-deploy-iam-19.log`, around line 72429).
- The profile specs red on the onion pass of `/tmp/compose-deploy-iam-20.log` carry spec fixes that never ran: `test-profile-sync.js` builds a website under the 100 characters WordPress allows (`user_url_too_long` rejected the whole sync), `test-profile-lock.js` expects the 501 `application_passwords_disabled` refusal on a non-https base (core issues application passwords only with `is_ssl()`), and reads the form URL through `getAttribute("action")` because the hidden `action` input of `user-edit.php` shadows `form.action`. Open: rerun both specs on an onion and a clearnet pass; decide whether application passwords stay https-only on onion hosts; and let `files/mu-plugins/infinito-oidc-rbac-mapper.php` drop an over-long website claim instead of failing the whole profile sync of that user.
