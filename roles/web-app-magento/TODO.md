# To-dos

- Finish implementation
- Two-factor authentication of the admin follows the flag `two_factor.enabled` in `meta/services.yml`: it is on exactly when the mail provider is in `group_names` and `web-app-keycloak` is not. Magento enrolls every admin through a mailed link (`tfa/tfa/requestconfig`), so without mail the administrator stays locked out ("Failed to send the message. Please contact the administrator"). `tasks/02_two_factor.yml` enables or disables `Magento_TwoFactorAuth` and `Magento_AdminAdobeImsTwoFactorAuth` to match the flag and provisions nothing for any user; with the flag off the administrator signs in with the password alone. Open for the role's owner: enforcing a second factor in Keycloak where SSO fronts the shop, and whether a deployment without mail and without SSO may run its admin on the password alone.
- `meta/csp.yml` grants `unsafe-eval` for `script-src`: Knockout compiles every `data-bind` attribute with `new Function`, and without the grant the Knockout forms of the admin stay empty ("Unable to parse bindings", measured on the code form at `tfa/google/auth`). The grant covers the storefront too, which runs the same Knockout components. Open for the role's owner: keep it, or serve the admin under a policy of its own.
- The admin dashboard requests a launch script from the host `assets.adobedtm.com` (the admin usage tracking of `Magento_AdminAnalytics`, whose notification dialog opens on the first dashboard visit) and the content security policy blocks it in `script-src-elem`, one console error per dashboard visit. Options: switch the tracking off with `admin/usage/enabled`, or allow the host.
- The persona test "administrator: app → universal logout" in `files/playwright/playwright.spec.js` does not enter the admin while `two_factor.enabled` is true: the shared native sign-in stops at Magento's two-factor page and the flow logs out through the link of that page. With the flag off it enters the admin and signs out through the account menu. `files/playwright/test-admin-sign-in.js` asserts the sign-in in both states of the flag.
- Indexers: after the install every indexer runs by schedule (`bin/magento indexer:status` shows `Update On: Schedule` for all of them, with a backlog) and no container runs Magento's cron, so a product or category created after the install never reaches the storefront. The three products the design gallery seeds over REST stayed out of the category listing, and `POST /rest/default/V1/carts/mine/items` answered 400 "Product that you are trying to add is not available." until `bin/magento indexer:reindex` was run by hand. Options: a service that runs `bin/magento cron:run` every minute, or `bin/magento indexer:set-mode realtime` in `tasks/01_setup.yml`. The gallery test in `files/playwright/test-design.js` needs one of them; the other design tests seed nothing.
- Search engine: `bin/magento indexer:reindex catalogsearch_fulltext` failed with `index_create_block_exception`, "cluster create-index blocked (api)". OpenSearch had set `cluster.blocks.create_index` itself because the disk of the host was 92 % full (140 GB free of 1.7 TB), which is above its percentage watermark; category pages and the search then list nothing. On the test stack the block was lifted by hand with the transient cluster setting `cluster.routing.allocation.disk.threshold_enabled: false`. Options: that setting or absolute watermarks in the environment of the `search` service.
- Storefront links carry `/index.php/` (the logo links to `<base URL>/index.php/`): `web/seo/use_rewrites` is not set. Options: `--use-rewrites=1` at `setup:install`, or `bin/magento config:set web/seo/use_rewrites 1`.
