# Semaphore UI

## Description

[Semaphore UI](https://semaphoreui.com/) is a modern web UI and API for running Ansible playbooks, Terraform/OpenTofu plans, and shell scripts on a schedule or on demand. This role deploys the official [`semaphoreui/semaphore`](https://github.com/semaphoreui/semaphore) container behind the Infinito.Nexus reverse proxy with central PostgreSQL, native Keycloak OIDC Single Sign-On, and optional LDAP login.

## Overview

The role deploys the Semaphore server and a dedicated task runner and wires them into the platform via `SEMAPHORE_*` environment variables. The setup wizard is bypassed by seeding the initial admin from rendered secrets, so a fresh deploy lands directly on the Semaphore login page. When SSO is enabled, the Keycloak `administrator` is created at deploy time as an external Semaphore admin via `semaphore user add --admin --external`; the OIDC callback matches it by email and signs the operator in as a Semaphore admin. As the last step of every deploy the role converges the `Infinito.Nexus` project, whose stop and start templates let members of the `operator` role group pause and resume the applications of the host through [sys-svc-app-control](../sys-svc-app-control/).

## Features

- **Pinned image:**
  `services.semaphore.image` and `services.semaphore.version` in [meta/services.yml](./meta/services.yml) pin the server to a concrete `semaphoreui/semaphore` release, never `latest`. The `🐳 Update Docker image versions` job of [cron-update.yml](../../.github/workflows/cron-update.yml) raises the pin in an update pull request. The next deploy starts the new server, which migrates the schema on start, and because the runner copies the `semaphore` binary of that image, the new pin rebuilds the runner as well (see **Runner build**). The egress proxy of a workspace runner (see **Workspaces**) runs `ubuntu/squid:6.6-24.04_beta` (`services.egress` in [meta/services.yml](./meta/services.yml)): Canonical publishes Squid 6.6 on Ubuntu 24.04 only in the `_beta` and `_edge` channels, without a `_stable` or `_candidate` tag, and `_beta` is the most stable of the two. The update job watches this pin like the server pin and raises it within the `-24.04_beta` flavor.

- **Central PostgreSQL:**
  `SEMAPHORE_DB_DIALECT=postgres` against the shared `svc-db-postgres` (or a per-role engine when not shared), with centralised backup and monitoring.

- **Native OIDC SSO:**
  Semaphore renders its own "Sign in with Keycloak" button via `SEMAPHORE_OIDC_PROVIDERS`; the Keycloak client is auto-provisioned by `web-app-keycloak`.

- **Login methods:**
  `services.semaphore.login.method.*` of [meta/services.yml](./meta/services.yml) switches each sign-in method on its own. `sso` renders the Keycloak provider through `SEMAPHORE_OIDC_PROVIDERS`; `ldap` sets `SEMAPHORE_LDAP_ENABLE`; `native` and `ldap` share one form, which `SEMAPHORE_PASSWORD_LOGIN_DISABLED` hides while both are off; `2fa` offers TOTP enrollment through `SEMAPHORE_TOTP_ENABLED`, and Semaphore has no setting that requires it, so `login.method.2fa.enforced` only offers it here. With SSO on, the sign-in page shows only the Keycloak entry and LDAP accounts sign in through Keycloak's LDAP federation.

- **LDAP login:**
  With the `ldap` method on (SSO off and `svc-db-openldap` present), Semaphore's login form binds against the central OpenLDAP directory (`SEMAPHORE_LDAP_*`). The form is then LDAP-only: Semaphore cannot tell local from LDAP accounts at the form, so no local account signs in, the break-glass account included.

- **LDAP role gate:**
  The LDAP search filter only finds members of the `administrator`, `operator` and `user` role groups (`memberOf` under the roles OU), so a directory account without one of them cannot sign in through the form.

- **OIDC role gate:**
  The provider's `email_claim` is a Go template rendered from `templates/oidc/email_claim.j2`. It yields the email only when the groups claim holds the `administrator`, `operator` or `user` role group and the `email_verified` claim is true, so Semaphore refuses the Keycloak sign-in of every other realm account, and of an account with an unverified address, with a missing email claim and returns it to the login page. Semaphore links a Keycloak sign-in to its account by that email.

- **Role group sync:**
  With SSO or LDAP, [files/sql/rbac/reconcile.sql](./files/sql/rbac/reconcile.sql) runs through `psql` in the database container as an RBAC hook of [sys-ctl-mtn-rbac-sync](../sys-ctl-mtn-rbac-sync/) at every deploy and on its timer, so a group change reaches Semaphore within one timer interval. The same run creates every member of the `administrator` and `operator` role groups that has an e-mail and no account yet as an external Semaphore account, admin only for `administrator`, so a member added between deploys has its account within one timer interval.

- **Admin flag reconcile:**
  The hook converges the admin flag of every account to the `administrator` role group. The break-glass account and the platform administrator are never demoted.

- **Operator role:**
  The `operator` role of [meta/rbac.yml](./meta/rbac.yml) maps to the Semaphore project role `task_runner` in the `Infinito.Nexus` project. The hook grants it to every account of an `operator` member and revokes it from every other account, so an operator can run the stop and start templates while a non-admin account outside the group neither sees the project nor runs its templates. Only `administrator` members are Semaphore admins.

- **Directory profile reconcile:**
  The hook writes the directory email, and the full name when the member list carries one, into every external account of an `administrator`, `operator` or `user` member. An email another account already holds is left in place.

- **Outsider sign-out:**
  The hook expires the sessions and API tokens of every external account that belongs to none of the role groups. The break-glass account and the platform administrator are exempt.

- **Break-glass local admin:**
  `SEMAPHORE_ADMIN*` seeds a local admin from the `web-app-semaphore-breakglass` user in every variant. With the `native` method on it signs in through the login form. With SSO on the form is hidden, and the account signs in through the login API, which `SEMAPHORE_PASSWORD_LOGIN_DISABLED` leaves open: `POST /api/auth/login` with `{"auth": "<username>", "password": "<password>"}` sets the session cookie, after which the UI opens signed in. With the `ldap` method on the account cannot sign in.

- **Dedicated runner:**
  Templates never run inside the server container: the server sets `SEMAPHORE_USE_REMOTE_RUNNER=true` and hands every task to the runner of its project (see **Workspaces**); `task-runner` runs the app-control templates and signs in with the runner token the deploy seeds for it. Its image is an Infinito.Nexus image (`SOFTWARE_IMAGE`) plus the `semaphore` binary of the pinned server image, tagged with the tag of that Infinito.Nexus image. It mounts no Docker socket, runs as an unprivileged user, and reaches hosts only over SSH with the key held in the key store of the project.

- **Runner build:**
  A deploy that names `web-app-semaphore` among its apps (`PRIMARY_APPS` of the matrix deploy, the `--id` list otherwise, every inventory group without one, read as `lookup('deployment').primary`) builds the runner on the Infinito.Nexus image of that deploy (`SOFTWARE_IMAGE_TAG`: `ci-<sha>` in CI, `dev-<sha>` locally, the release version in production, never `latest`), so the foreign-server deploy and the app-control templates run that checkout. A deploy that pulls Semaphore in only as a provider of another application reads the runner it deployed from the compose file on the stack host and keeps it, building neither the runner nor its base image, as long as the stack host still holds both images and the runner image carries the `nexus.infinito.semaphore.runner.inputs` label of this checkout. That label is the sha256 of every build argument but the base image: the digest of the [runner Dockerfile](./files/runner/Dockerfile), the digest of every file the runner runs or bakes in, those of `files/shell/`, `files/python/` and `files/opentofu/` with the provider lock files (`SEMAPHORE_RUNNER_SOURCE_GLOBS`), each named by its path below `files/`, the pinned server image, the runner user, its UID and GID, the repository link and the temporary directory. A missing image, a missing label or another digest rebuilds the runner on the image of this deploy, like Semaphore's own round, and a kept runner whose tag differs from `SOFTWARE_IMAGE_TAG` is reported by a warning task. With `SOFTWARE_IMAGE_BUILD` the base image is built from the checkout only when the stack host lacks it. After the compose stack is up, the deploy untags every tag of the runner image on the stack host and, with `SOFTWARE_IMAGE_BUILD`, every tag of `SOFTWARE_IMAGE`, except the runner and base image it runs; an image a container still uses keeps its layers. The Playwright environment carries `SEMAPHORE_RUNNER_IMAGE_TAG`, and every template run of the specs logs it.

- **Control flag:**
  Every invokable role declares `services.semaphore` with `enabled`, `shared`, `control` and `status`. `enabled` and `shared` follow `'web-app-semaphore' in group_names`; `control: true` puts the application under Semaphore control; `status` is `started` or `stopped` and only decides the state the deploy creates the application in, while a redeploy keeps the state Semaphore last set.

- **Control-plane exemptions:**
  `web-app-semaphore`, `web-app-keycloak`, `svc-db-postgres`, `svc-db-openldap`, `svc-prx-openresty` and `web-app-gitea` declare `control: false` and `status: started` with a `# nocheck:` reason, so no Semaphore run can cut off its own way back. Shared providers that other roles consume, such as `web-app-matomo` or `web-app-prometheus`, stay out of control as well. In `web-app-semaphore` the entry is the Semaphore container itself, so its `enabled` stays the container flag.

- **Stop and start templates:**
  The `Infinito.Nexus` project holds `stop <application_id>` and `start <application_id>` for every application the host registered with `control: true`, plus `stop all` and `start all` over exactly that set. The deploy converges the project, its SSH key, inventory, repository, environment and templates idempotently through a short-lived API token, and removes the templates of applications the host no longer holds.

- **App-control SSH path:**
  Each template runs `app-control.sh stop|start <application_id>|all` in the runner, which signs in over SSH as the host account `app-control` with the `app_control_ssh_key` credential and a pinned host key. The `authorized_keys` entry of that account is `restrict`ed to a forced command that accepts only `app-control stop|start <application_id>|all`, and sudo lets the account run exactly those two subcommands as root.

- **Paused page:**
  While an application is paused, nginx answers every one of its vhosts with HTTP 503 and a self-contained page with a beaver sleeping behind a pause sign, the paused notice and the contact channels of `service_provider.contact`. The page is rendered from the `core` gettext catalogs in every language they translate, picked from `Accept-Language`, with English as the fallback.

- **Variants:**
  [meta/variants.yml](./meta/variants.yml) defines three variants, each with `tor` on. Variant 0 enables every service but `docs` and adds `web-app-gitea` and the `deploy` block of the foreign-server deploy (see **Test variant**). Variant 1 disables every service but `docs`, whose round replays the instructions of this README. Variant 2 enables `ldap` only, so the login form binds against the directory. Variants 0 and 2 also deploy `web-app-lam`, the application the app-control specs pause and resume.

## Foreign-Server Deploy

Semaphore deploys Infinito.Nexus to foreign servers from an inventory repository once the inventory of the Semaphore host declares the optional `deploy` block:

```yaml
applications:
  web-app-semaphore:
    services:
      semaphore:
        deploy:
          repository:
            url: ssh://git@git.example.org:2222/infra/inventory.git
            branch: main
            key: "<OpenSSH private key with read access to the repository>"
          vault_password: "<vault password of that inventory>"
```

- **Mandatory keys:**
  Without the block the role converges no deploy project and registers no deploy app. Once the block is present, `repository.url`, `repository.branch`, `repository.key` and `vault_password` are all mandatory and none has a default, so a deploy with one of them missing fails.

- **Deploy project:**
  The deploy converges a second project, `Infinito.Nexus Deploy`, next to `Infinito.Nexus`. It holds the template `deploy`, the inventory `deploy` carrying the deploy key, the repository `inventory` and an environment named `deploy <digest>`. The hook grants every Semaphore admin, whose flag it keeps in step with the `administrator` role group, the project role `owner` in it and revokes every other membership, so `operator` and `user` members neither see the project nor run its template.

- **Private repositories:**
  Semaphore clones the repository over its SSH URL with `repository.key`, which the deploy stores as an SSH key of the project, so a private repository is the default case: register the public half of `repository.key` as a read-only deploy key of the repository. The repository holds the inventory the way `infinito administration inventory provision` writes it, with `devices.yml` at its root, and `vault_password` is the password its vault values are encrypted with. Beside it lies `workspaces.yml`, the inventory of the Workspaces project, which lists the platform hosts; `devices.yml` lists the customer devices alone, so the `deploy` template never reaches a platform host while one repository serves both projects.

- **Keys:**
  The deploy signs in to every host the inventory lists as `root` with the `deploy_ssh_key` credential, so authorize its public half for `root` there; outside the test fixture the Workspaces project signs in to the hosts of `workspaces.yml` with the same key. It is a key of its own: the `app_control_ssh_key` credential reaches only the `app-control` account of the Semaphore host through its forced command and never leaves that host. Every key is stored under a name that ends in its fingerprint, so the deploy that brings a rotated key stores it next to its predecessor and removes the predecessor. The vault password is a Semaphore secret of the deploy environment, whose name ends in a digest keyed with the deploy key, so a changed password replaces the environment the same way.

- **Runner path:**
  The block also registers the Semaphore app `infinito` through `SEMAPHORE_APPS`. The `deploy` template runs it in the dedicated runner as `bash /opt/app-control/deploy.sh devices.yml`, with the checkout of the inventory repository as working directory. Semaphore refuses a template whose playbook is absolute or leaves its repository, so every other template that runs a script of the runner image names the bare script as its playbook and runs the app `infinito-script`, which `SEMAPHORE_APPS` also registers on the server, the platform runners and every workspace runner: `bash /opt/app-control/script.sh <script> <arguments>` in the template's repository, where [script.sh](./files/shell/repository/script.sh) runs only a script of its own directory. [deploy.sh](./files/shell/repository/deploy.sh) needs `DEPLOY_VAULT_PASSWORD` only while the inventory, its `group_vars` or its `host_vars` hold a `!vault` block; then it writes the password into a `0400` file of a temporary directory it removes on exit and passes `--password-file <file>`, and an inventory whose credentials are OpenBao references runs without it. It pins the host keys of `DEPLOY_KNOWN_HOSTS` for its SSH connections when the environment carries any, and runs `infinito administration deploy dedicated <checkout>/devices.yml --skip-build -u root` with the deploy key in the SSH agent Semaphore starts for the inventory. The runner runs the Infinito.Nexus image of the deploy that last built it (see **Runner build**), so a foreign server receives the release of that deploy. Outside the test fixture the environment pins no host keys, and a deploy accepts every host key it does not know yet under the `accept-new` policy of `ansible.cfg`.

- **Test variant:**
  Variant 0 of [meta/variants.yml](./meta/variants.yml) deploys `web-app-gitea` next to Semaphore and declares the block with the private repository `target-inventory` of the platform administrator on the SSH port of that Gitea, the branch `main`, the `deploy_ssh_key` credential as repository key and a fixed vault password. On the `dev`, `act` and `github` runtimes, with Gitea and the block present, [tasks/utils/project/fixture.yml](./tasks/utils/project/fixture.yml) runs before the projects converge: it reads the address, pinned host keys and public root key of the [shared target](../../compose/target/README.md) from the holder, authorizes the deploy key for `root` on the target, recreates the repository whenever its `.infinito-fixture` marker no longer matches the repository key, vault password, host, application and variables, with an inventory for the host `target` that includes `web-svc-html` under `TLS_MODE` `self_signed` and the `DOMAIN_PRIMARY` of the stack, and binds the public half of the repository key to the repository as a read-only deploy key. No live credential of the platform enters the repository: the inventory holds only the credentials the provision generates for the target, encrypted with the fixed vault password, whose file lies outside the committed tree, and the marker holds a sha256 digest; [test_fixture_commit.py](../../tests/unit/python/roles/web-app-semaphore/test_fixture_commit.py) follows every committed value through the role vars and fails on any credential read. - **Fixture inventories:**
  The same commit carries the inventory of the Workspaces project. [tasks/utils/project/fixture/platform.yml](./tasks/utils/project/fixture/platform.yml) reads the inventory and the host_vars of the platform host, and [filter_plugins/semaphore_fixture_platform.py](./filter_plugins/semaphore_fixture_platform.py) builds `workspaces.yml`, which puts the host `platform` (`SEMAPHORE_DEPLOY_FIXTURE_PLATFORM_HOST`) into every group the platform host belongs to, and `host_vars/platform.yml`: the platform's own variables without any `ansible_*` variable, user password or `secrets.credentials` value, overlaid with `SEMAPHORE_DEPLOY_FIXTURE_REFERENCES` and with `ansible_host` `host.docker.internal`. The filter refuses a vaulted value or a credential that is no OpenBao reference, and the commit fails before it collects its files unless `devices.yml` lists `target` and no platform host and `workspaces.yml` lists the platform host alone. Both files enter the `.infinito-fixture` digest, so a changed platform inventory recreates the repository. `WORKSPACE_INVENTORY_FILE` of the Workspaces environment names `workspaces.yml`, and [test-foreign-deploy.js](./files/playwright/test-foreign-deploy.js) fails when the play recap of `deploy` names the platform host. The Playwright env carries `SEMAPHORE_WORKSPACES_PLATFORM_HOST` only while the fixture is on, and every workspace spec skips its workspace apply while it is empty.

- **Fixture root key:**
  While `SEMAPHORE_DEPLOY_FIXTURE_ENABLED` holds, the Workspaces project signs in to the platform host as `root` with the `fixture_ssh_key` credential and pins the host key of `host.docker.internal`; otherwise it signs in with the deploy key and pins nothing. [tasks/utils/project/fixture/root.yml](./tasks/utils/project/fixture/root.yml) runs on every deploy of the projects. With the fixture on it fails unless the fixture key differs from the app-control key, the deploy key and the root key of the shared target, writes the public half as the only line of `semaphore-fixture-root.keys` in `DIR_SSHD_DROPINS` and adds the sshd drop-in `semaphore-fixture-root.conf`, whose `Match User root` block lets `root` sign in with that file alone. With the fixture off it removes both, so a production deploy never authorizes the key. The private half lives only in the SSH key of the Workspaces project, which Semaphore hands the `workspace` task through its agent. [test_fixture_root.py](../../tests/unit/python/roles/web-app-semaphore/test_fixture_root.py) renders the gate for every runtime and fails on a key planted under a production render, on an ungated write and on a private half read anywhere else.

- **Fixture credentials:**
  While `SEMAPHORE_DEPLOY_FIXTURE_ENABLED` holds and the `workspaces` block is declared, [tasks/utils/project/fixture/credentials.yml](./tasks/utils/project/fixture/credentials.yml) writes the live credentials of the platform host that the workspace roles read to OpenBao below `platform/data/fixture/<host>/`, `<host>` being `SEMAPHORE_DEPLOY_FIXTURE_PLATFORM_HOST`: each user password of `SEMAPHORE_DEPLOY_FIXTURE_PLATFORM_CREDENTIALS` at `fixture/<host>/users/<name>`, field `password`, and the named credentials of each application the host runs, plus `objstore_secret_key` of every consumer of its shared object store, at `fixture/<host>/apps/<application_id>`, one field per credential, through `utils/kv.yml` of `web-app-openbao`, which writes only what differs, so a second deploy reports no change. `SEMAPHORE_DEPLOY_FIXTURE_REFERENCES` is the one source of the references the fixture commits for that host: `users.<name>.password` and `applications.<id>.secrets.credentials.<key>`, each `{openbao: "platform/fixture/<host>/<users|apps>/<name>#<field>"}`, built from names alone by [filter_plugins/semaphore_fixture.py](./filter_plugins/semaphore_fixture.py), so the commit carries no value.
- **Workspace fixture key:**
  The credential `fixture_workspace_ssh_key` is the key the workspace deploy specs sign in to the shared target with. While `SEMAPHORE_DEPLOY_FIXTURE_ENABLED` holds, [tasks/utils/project/fixture.yml](./tasks/utils/project/fixture.yml) fails unless its public half differs from the root fixture key, the app-control key, the deploy key and the target key, then authorizes that public half for `root` on the shared target, directly and through `SEMAPHORE_DEPLOY_FIXTURE_VARS`. With the `workspaces` block declared, [tasks/utils/project/fixture/credentials.yml](./tasks/utils/project/fixture/credentials.yml) writes the private half to `platform/data/fixture/<host>/workspace-ssh`, field `private_key`, where the Playwright AppRole reads it; a spec stages it into `tenant/ws-<id>/ssh` through the store AppRole and removes it after. With the fixture off, no task reads the key and the Playwright env names neither its path nor the root keys of the target ([test_fixture_workspace_key.py](../../tests/unit/python/roles/web-app-semaphore/test_fixture_workspace_key.py)).
- **Lock-out guard:**
  `load_workspace_key` of [lib.sh](./files/shell/repository/lib.sh), which a workspace deploy and every action of `host.sh` run before they touch the host, starts with `guard_workspace_inventory`, which `usage.sh` runs too. It pins every later ansible call of the task to the `ansible.cfg` of the core tree (`ANSIBLE_CONFIG`), so an `ansible.cfg` in the workspace checkout, the working directory of the task, loads no plugin from it; it enables the `yaml` inventory plugin alone and makes an unparsed inventory fatal, so an executable inventory never runs and a `plugin:` file never renders; and through [inventory_guard.py](./files/python/inventory_guard.py) over `ansible-inventory --list` it refuses every key or string with a Jinja marker, which a task would render on the runner, where a lookup runs a command or reads the task's files and environment, and every host or group variable named like a top-level key of the core tree's `group_vars/all`, which it would outrank: a `STACK_HOST: localhost` sends every `delegate_to` task over the local connection of the runner, a `MASK_CREDENTIALS_IN_LOGS: false` prints credentials into the task log. The one exception is `INVENTORY_SETTINGS` of the guard, `DEPLOYMENT_MODE`, `DOMAIN_PRIMARY` and `TLS_ENABLED`, the settings a workspace inventory sets for its own hosts; the store's member-settable variables stay a subset of it. The refusal names the place, never the value. The store's own writer refuses the same, and the guard keeps a store that writes otherwise from reaching the workspace key, which the store cannot read (Store, 2026-11-14). The function ends with [lockout_guard.py](./files/python/lockout_guard.py). It refuses an inventory under which the run would lose its own key login: the host names no `ansible_user`, a key of the task agent (`ssh-add -L`) is missing from `users.<ansible_user>.authorized_keys`, or the login user is `root` and `SYS_SVC_SSHD_PERMIT_ROOT_LOGIN`, the host variable or else the `sys-svc-sshd` default `no`, is neither `prohibit-password` nor `yes`. The refusal names the key's `SHA256:` fingerprint or the setting, never a key. Right after it, [transport_guard.py](./files/python/transport_guard.py) refuses an inventory that would take the connection away from the `ANSIBLE_SSH_ARGS` the task pins with its known-hosts line and `StrictHostKeyChecking=yes`, or run something on the runner: an `ansible_ssh_args`, which outranks the environment and replaces them; the common and extra arguments of ssh, scp and sftp, whose `ProxyCommand`, `LocalCommand`, `KnownHostsCommand`, `-F` or forwardings run a command on the runner or open its network whatever the pinned options hold; the ssh, scp and sftp executables; `ansible_ssh_pkcs11_provider`, a library the runner would load; or an `ansible_connection` other than `ssh`.
- **Workspace credentials of the specs:**
  While the fixture is on, `SEMAPHORE_WORKSPACE_CREDENTIALS_JSON` carries, per role of `SEMAPHORE_DEPLOY_FIXTURE_WORKSPACE_ROLES`, the credential schema `infinito inventory credentials --openbao` writes, from [schema.py](../../cli/administration/inventory/credentials/schema.py) through `semaphore_fixture_credential_schemas`: path, field and generator kind of every credential and user password, never a value, a role default as `default_b64`. A deploy spec generates the values, writes them create-only below `tenant/ws-<id>/` with the store AppRole, commits the references and keeps the platform administrator's password in memory; `SEMAPHORE_WORKSPACE_KEYCLOAK_JSON` names realm, admin username and host label of the deployed Keycloak. Every run deploys onto the same shared target with fresh credentials, which to the target is a rotation: of the deployed roles only Keycloak keeps credential-guarded state, its dedicated postgres, which `post_deploy.yml` realigns to the rotated password, and its admin, which the deploy moves over from the password the previous deploy rendered. [test_fixture_workspace_rotation.py](../../tests/unit/python/roles/web-app-semaphore/test_fixture_workspace_rotation.py) fails when a role joins `SEMAPHORE_DEPLOY_FIXTURE_WORKSPACE_ROLES` with state no deploy converges.

- **Fixture reader:**
  While the fixture is on, every deploy hands `web-app-openbao` the ids of the `workspace` template of the Workspaces project as `semaphore_fixture_reader_identity`, from which it binds the jwt role `workspace-fixture` to that project and template with the read-only policy `fixture`, and the Workspaces environment carries the role as `BAO_FIXTURE_ROLE`, empty otherwise. [workspace.sh](./files/shell/repository/workspace.sh) starts `ansible-playbook` only through [bao/preflight.py](./files/python/bao/preflight.py), the pre-flight of `infinito deploy`: when the inventory, its `group_vars` or its `host_vars` hold an OpenBao reference, it logs in with the task token and `BAO_FIXTURE_ROLE`, reads every reference once and hands the play the token as `BAO_TOKEN` alone; without a login, or with a reference it cannot read, the play never starts.

## Workspaces

The store runs every customer workspace through Semaphore. The optional `workspaces` block under `services.semaphore` turns this on next to the `deploy` block. It holds `private_targets`, the list of networks a workspace target may lie in beside public addresses (empty in production, the dev subnet on the dev stack), and `invite_client_id`, the Keycloak client id of the store that an invited member returns to (`KC_INVITE_CLIENT_ID` of the `members` action `invite`, empty until the deployment sets it; variant 0 sets `workspace-store-fixture`, the test-only store client [web-app-keycloak](../web-app-keycloak/README.md) then holds), beside `export`, `dns` and `catalog`, which the sections below describe.

- **Runner per project:**
  Every template core builds carries a `runner_tag`: `app-control`, `deploy`, `workspaces`, `provision` and `export` for the platform projects, `ws-<id>` for the templates of a workspace. Each platform project runs on a runner service of its own (`SEMAPHORE_PLATFORM_RUNNERS`): `task-runner` for app control, `deploy-runner` for the deploy project, `workspaces-runner` for the Workspaces project with `max_parallel_tasks` 2, `provision-runner` and `export-runner`, each with its own token credential, token file and tag (`SEMAPHORE_PLATFORM_RUNNER_TAGS`). The deploy and workspace runners run only when their block is declared, and every runner shares the image `task-runner` builds. After the projects converge, [runners.sql.j2](./templates/sql/project/runners.sql.j2) aligns one runner row per platform project, with that project as `project_id`, `is_default` FALSE and its one tag in `runner__tag`, and the deploy fails when a runner row has no project or a platform project runs on anything but exactly its own runner, so no global runner exists and a workspace task never runs on a platform runner. Each workspace has a runner of its own, whose row names the project `ws-<id>`, the tag `ws-<id>`, `max_parallel_tasks` 1 and `is_default` FALSE. The server keeps `SEMAPHORE_USE_REMOTE_RUNNER=true`, holds no `SEMAPHORE_RUNNER_REGISTRATION_TOKEN` and signs a task token for every task (`SEMAPHORE_JWT_ENABLED=true`, `SEMAPHORE_JWT_ISSUER` the canonical Semaphore origin).

- **Workspace runner:**
  `workspace apply` runs the compose project `semaphore-ws-<id>` from [templates/workspace/compose.yml.j2](./templates/workspace/compose.yml.j2): the runner, built from the runner Dockerfile on the Infinito.Nexus image `v<WORKSPACE_CORE_VERSION>`, or on a dev or CI deploy on the own build `WORKSPACE_CORE_BASE` names (its tag then names the runner image), under a UID no other runner holds, with a read-only root, `tmpfs` HOME, `/tmp` and task directory, all capabilities dropped, `no-new-privileges`, no extra hosts, no Docker socket, its token file as its only mount, `SEMAPHORE_RUNNER_ONE_OFF=true` and `SEMAPHORE_RUNNER_MAX_PARALLEL_TASKS=1`. Its only network is the internal `workspace` network of [utils/networks/render.py](../../utils/networks/render.py) (an internal bridge in both modes, since the project runs on one host); its one other member is the egress proxy, which alone also joins the outside `default` network.

- **Egress:**
  The egress proxy (Squid, [templates/workspace/squid.conf.j2](./templates/workspace/squid.conf.j2)) allows `CONNECT` to the Semaphore, Gitea and OpenBao names on their front-proxy ports, then denies loopback, link-local and the host's own addresses, then allows each pair of `WORKSPACE_TARGETS` at the address `apply` pinned, and denies everything else with a log line naming the target. SSH reaches it through `egress_connect.py`, which the runner image sets as `ProxyCommand` whenever `EGRESS_PROXY` is set.

- **Workspace operation:**
  The `Infinito.Nexus Workspaces` project holds the locked templates `workspace`, `members` and `user`, each with one template grant for `guest`, the store's role there. `workspace` runs [workspace.sh](./files/shell/repository/workspace.sh) with the survey variables `WORKSPACE` (a lowercase UUID), `WORKSPACE_ACTION` (`apply` or `destroy`), `WORKSPACE_CORE_VERSION` (a released version such as `17.0.0`, or `latest`), `WORKSPACE_TARGETS` (comma-separated `<host>:<port>` pairs, empty for a workspace without servers) and `WORKSPACE_PLATFORM_TOKENS` (`true` or `false`, required on `apply` and refused on `destroy`; see Inputs below). Only a release at or above `SEMAPHORE_WORKSPACE_CORE_FLOOR` (`vars/main.yml`, the first release that ships the workspace runner, empty while none does) is accepted, and `latest` is the newest such release, refused while none exists. The releases come from the `CHANGELOG.md` of the platform runner image alone: its build copies it to `/usr/local/share/semaphore-runner/CHANGELOG.md` (`SEMAPHORE_RUNNER_CHANGELOG_FILE`), every deploy reads it out of the image once in [tasks/00_core.yml](./tasks/00_core.yml) and fails when it is missing or empty, and the `semaphore_workspace_releases` filter runs the parse and floor of `workspace.py` on it for the release picks of the workspace specs. On a deploy with `SEMAPHORE_DEPLOY_FIXTURE_ENABLED`, which no production runtime turns on, the Workspaces environment also carries the deploying core's own build (`SOFTWARE_IMAGE` with the deploy's `SOFTWARE_IMAGE_TAG`) as `WORKSPACE_OWN_BUILD` with its `lookup('version')` as `WORKSPACE_OWN_BUILD_VERSION`; there its tag and `latest` both select that build, since dev and CI test the deploying core. On production both are empty and the tag is refused. [workspace.py](./files/python/workspace.py) refuses every malformed input before any playbook runs, pins every target address and hands the operation to [playbook-workspace.yml](../../playbook-workspace.yml) as extra variables. Every deploy reads the identity of this project (`project_id` and the `templates` entries of `workspace`, `members` and `user`, built like the entries `apply` prints) with `project.py workspaces-identity` in [tasks/utils/workspaces/identity.yml](./tasks/utils/workspaces/identity.yml) and holds it as `semaphore_workspaces_identity` for `web-app-openbao`, which writes it to `platform/data/store/semaphore/workspaces`, where the store reads it.
  `members` runs [members.sh](./files/shell/repository/members.sh) with `WORKSPACE`, `MEMBERS_ACTION` (`sync`, `list`, `add`, `invite`, `uninvite`, `role` or `remove`), `WORKSPACE_MEMBER` (`add`, `role`, `remove`), `INVITE_KEY` (`invite`, `uninvite`), `WORKSPACE_ROLE` (`role`) and `WORKSPACE_SUSPENDED` (`true` or `false`, required by every action). While the store suspends a workspace for non-payment it passes `true`, and the sync gives every member of `ws-<id>` with a mapped role group `guest`, so no member starts a task; `false` restores the mapping of the role groups. A missing or malformed value refuses the task before any change.

- **Store credentials:**
  The Workspaces project also holds the locked template `rotate store credentials`, which carries no template grant, so the store cannot start it, and one active schedule, `0 4 * * 1`, so it runs every 7 days. It runs [store-credentials.sh](./files/shell/repository/store-credentials.sh) without a survey: the task logs in to OpenBao with its task token and the role `store-credentials`, which binds the project and this template by number and grants `create` and `update` on `platform/data/store/semaphore` and `platform/data/store/gitea` and nothing else; [playbook-store-credentials.yml](../../playbook-store-credentials.yml) mints the store's Gitea token through `tasks/utils/store_token.yml` of `web-app-gitea`, which also revokes the expired Gitea store tokens; [rotate_store_credentials.py](./files/python/rotate_store_credentials.py) mints the store's Semaphore token in the Semaphore database with Semaphore's own `expires_at` 30 days after the run, writes each entry with exactly the two fields `token` and `expires_at` (RFC 3339 with the offset `+00:00`, 14 days after the run, refused without a numeric offset), and revokes every store Semaphore token whose name `store-<expires_at>` carries a moment before the run, and no other. No token reaches an argument, the task output or a Semaphore environment. Every deploy reads the template's ids with `project.py store-rotation-identity` and holds them as `semaphore_store_rotation_identity`, from which `web-app-openbao` writes the role.

- **Contract of `tasks/workspace.yml`:**
  `playbook-workspace.yml` runs `tasks/workspace.yml` of `web-app-keycloak`, `svc-dns-knot`, `web-app-semaphore`, `web-app-openbao`, `web-svc-seaweedfs`, `svc-virt-incus` and `web-app-proxmox` in this order on `apply` and in the reverse order on `destroy`, on every host that holds the role. This role acts on the stack host alone, so one host owns the projects, the runner row and the runner of a workspace, and it hands its result to every host. Each of these task files follows one contract:
  - **Inputs:** `WORKSPACE`, `WORKSPACE_ACTION`, and on `apply` `WORKSPACE_CORE_VERSION` (resolved, without `v`, the version the runner's core tree declares), `WORKSPACE_CORE_BASE` (the own build the runner builds on, empty for a release), `WORKSPACE_TARGETS` (`[{host, port, address}]`, pinned) and `WORKSPACE_PLATFORM_TOKENS`, the store's switch for the platform provider secrets: the survey value `true` or `false`, handed on as a boolean. An `apply` without it or with any other value, and a `destroy` that sets it, is refused before the playbook runs. A role reads the facts the roles before it set, `workspace_dns` (`zone`, `zone_id`) of the DNS flavor, which this role places itself under `cloudflare`, and `workspace_semaphore` (`project_id`, `workspaces_project_id`, `members_template_id`, `provision_project_id`, `provider_templates` (`<provider>`: `provision`, `destroy`), `unlock_template_id`, `dns_template_id`, `zone_template_id`, `export_project_id`, `export_template_id`) of this role.
  - **Idempotent apply:** a second `apply` with the same inputs changes nothing and keeps every credential it created.
  - **Destroy:** removes what `apply` created; every step counts a resource that is already gone as removed, so a stopped `destroy` finishes when it runs again.
  - **Result:** this role writes the result `workspace.sh` prints as the last line of `apply`, one JSON object with exactly `workspace`, `alias`, `read_key`, `project_id` and `templates`. `templates` is keyed by template name, each entry with exactly `project_id`, `template_id`, `repository_id`, `inventory_id`, `environment_id`, `git_url`, `git_branch`, `ssh_key_id`, `runner_tag`, `app`, `playbook`, `arguments` (decoded), `survey_variables` (the sorted survey variable names) and `environment_variables` (the names, never the values, of the template's environment) as Semaphore holds them, so the store compares a live template against core's own record (Store asks 21, 23, 24, 32 and 42); the Workspaces project identity the store pins in OpenBao carries the same entries; a name held twice fails `apply`. `destroy` prints `{"destroyed": true, "stopped_tasks": <n>, "workspace": "<id>"}`, where `stopped_tasks` counts the tasks it had to stop, 0 when none was unfinished (Store ask 41). On `destroy`, `playbook-workspace.yml` runs [tasks/workspace_stop.yml](./tasks/workspace_stop.yml) of this role before the role loop, so no role erases while a task of the workspace runs: it lists the tasks of every template of `ws-<id>` and of every `<template> ws-<id>` template of the provision and export projects, never of the Workspaces project, sends each task that is not `success`, `error` or `stopped` a stop without `force` and waits until each reports one of those three. This role's own `destroy` repeats the stop before its first erase, for a task started in between, and `stopped_tasks` is the sum of both. A task still unfinished 120 seconds after its stop fails `destroy` with its id before any role erases, so the next `destroy` stops and counts it again. The workspace runner goes after the projects, so a running task still reaches the runner that kills it.

- **Workspace values:**
  The project `ws-<id>` holds the repository, inventory and environment `workspace`, with `WORKSPACE`, `WORKSPACE_DNS_ZONE`, `WORKSPACE_TARGETS` and `WORKSPACE_INVENTORY_FILE`, and the templates `deploy`, `update`, `backup`, `restart`, `suspend`, `resume`, `release` and `usage`. The store account `store` is local, no admin and `manager` of every `ws-<id>`. The provision and export projects hold `provision-<provider>` and `destroy-<provider>` per provider, `unlock`, `dns` and `export` per workspace, named `<template> ws-<id>`, with a `guest` grant each. Their environment `ws-<id>` in the provision project holds `WORKSPACE` (`ws-<id>`), `WORKSPACE_DNS_ZONE`, `WORKSPACE_DNS_ZONE_ID` (empty under `knot`) and `WORKSPACE_TARGETS`, taken only from the `workspace_dns` fact of the DNS flavor. The same environment carries the platform values of `SEMAPHORE_PROVISION_VARIABLES`, which the provision script refuses to run without: `BAO_ADDR` (the OpenBao origin), `PROVISION_CA_FILE` (the self-signed CA under `TLS_MODE` `self_signed`, empty otherwise), `PROVISION_DNS_FLAVOR` (`services.semaphore.workspaces.dns.flavor`), `PROVISION_STATE_ENDPOINT` (the S3 origin of `web-svc-seaweedfs`) and `PROVISION_CATALOG_DIR` (the target of the read-only catalog mount `semaphore_provision_catalogs` of `provision-runner`).

- **Locked fields:**
  Every template core builds has `allow_override_args_in_task`, `allow_override_branch_in_task` and `allow_parallel_tasks` false, its `runner_tag`, `jwt_params` with `enabled` true and the audience `openbao`, and for an Ansible template `allow_override_inventory` false; every survey variable has target `env`. The next deploy or `workspace apply` realigns a template changed by hand. [meta/services.yml](./meta/services.yml) pins a released Semaphore tag of at least `v2.20.1`, the floor for task tokens and template runner tags.

- **Host templates:**
  The workspace `deploy` takes exactly `SALES_ORDER`, `LINE`, `HOST`, `HOST_KEY`, `ROLES`, `DNS_LABEL` and `INVENTORY_COMMIT` and deploys to the domain `<DNS_LABEL>.ws-<id>.<WORKSPACE_DNS_ZONE>`. `deploy`, `update`, `backup`, `restart`, `suspend`, `resume` and `release` take `HOST` and `HOST_KEY` and write `<HOST> <HOST_KEY>` as the only known-hosts line under `StrictHostKeyChecking=yes`; `HOST` has to be the host of a pair in `WORKSPACE_TARGETS`. `deploy`, `update` and `backup` take `INVENTORY_COMMIT`, a full commit of 40 lowercase hex digits, which the script refuses before any git call when it has another form, checks with `git merge-base --is-ancestor` against `origin/main` and checks out detached before it runs. The store protects `main` of the workspace repository so that only its write deploy key pushes there.
  `suspend` and `resume` take no `INVENTORY_COMMIT` and no argument beyond their fixed one, and run `app-control stop all` and `app-control start all` of [sys-svc-app-control](../sys-svc-app-control/) on `HOST` as root, so each is the exact inverse of the other and a repeated run changes nothing. A suspended application keeps its volumes, its configuration and its state marker `stopped`, and nginx answers it with the paused page. Neither `restart` nor `update` resumes it: a reboot brings back no container that `compose down` removed and no swarm service scaled to 0 replicas, and the last step of every deploy pauses it again, so only `resume` starts it. An application whose `services.semaphore.control` is false, such as a database or a shared provider, keeps running through a suspend, so a `backup` after it still dumps every database.
  `release` hands a bring-your-own server back to its customer and takes no `INVENTORY_COMMIT` and no argument beyond its fixed one. It runs [release_host.py](./files/python/release_host.py) on `HOST` as root through `ansible.builtin.script`, which reads every `authorized_keys` line with the option and quote parsing of sshd and refuses with exit code 2 before any write unless `ansible_user` keeps, beside the keys of the task agent, a line `ssh-keygen -l -f` accepts that carries neither `command=` nor `restrict` (Store, 2026-11-14: a forced-command key can leave the customer without a shell; `from=` and the other options count). It then deletes the `authorized_keys` of `app-control`, `/etc/sudoers.d/app-control` and `/etc/sudoers.d/backup`, so no platform account keeps sudo, empties the `authorized_keys` of `backup`, and drops every line whose key blob the task agent holds (`ssh-add -L`) from the `authorized_keys` of `root` and of `ansible_user`, that one last, so a release stopped on the way still logs in to finish; the blob alone decides, so an RSA key written as `rsa-sha2-256` or `rsa-sha2-512` goes too. Lines split at a line feed only, as sshd reads them, so a carriage return stays inside its line and a commented-out key stays off. Each file is replaced atomically with its owner and mode; the accounts, the data and every other line stay. Two fresh logins with the agent key alone, as `ansible_user` and as `root`, then have to be refused, else the task fails with exit code 1; [proof_of_release.py](./files/python/proof_of_release.py) judges the release and both logins in the task. They take their connection settings as extra variables from `proof_of_release.py proof-vars` (`BatchMode`, `IdentitiesOnly`, publickey only, no control master, the pinned known-hosts line, the agent key as the only identity), which outrank every `ansible_ssh_args`, private key, common or extra ssh argument, password and connection the inventory sets. The last stdout line is one JSON object, `{"host", "released": true, "removed": {"agent_keys", "app_control_keys", "app_control_sudoers", "backup_keys", "backup_sudoers"}, "kept"}`, `kept` counting the customer keys of `ansible_user` that open a shell; `/etc/sudoers.d/administrator` of `user-administrator` stays, since that account can be the customer's own login; a refusal ends with `{"host", "released": false, "refused"}` and exit code 2, a failure with `"failed"` in its place and exit code 1. A host that refuses the agent key already, such as one released before, is refused before any write, since the task can no longer log in to tell a released host from one that never let it in.

- **Usage template:**
  `usage` counts the active people of the workspace's instances for billing. `workspace apply` creates it locked, with no survey and no argument, and one active daily schedule, `0 3 * * *`; `destroy` removes both with the project. [usage.sh](./files/shell/repository/usage.sh) refuses any argument and runs `playbook-usage.yml` from the core tree over the `web-app-keycloak` hosts of the inventory, limited to the hosts of `WORKSPACE_TARGETS` with a local connection, so it opens no SSH connection. The usage tasks of `web-app-keycloak` read `credentials.usage_client_secret` with the task's own OpenBao token only for a host whose inventory turns `services.keycloak.usage_client.enabled` on, and the secret reaches no argument, environment value or output. A host with the client off is reported with `active_users` null and gets no call. Its last output line is one JSON object: `workspace`, `counted_at` (UTC, ISO 8601) and `hosts`, a list of `{host, realm, active_users}`. The store keeps each daily value and bills the monthly maximum; core keeps no billing state.

- **Export:**
  The export project `<SOFTWARE_NAME> Export` runs on `export-runner` and holds, per workspace, the locked template `export ws-<id>` with a `guest` grant, which runs [export.sh](./files/shell/repository/export.sh) and through it [export.py](./files/python/export.py). Like the scheduled templates below, it runs from the script directory of the runner image under the project's empty key, never from the workspace repository, because the export runner reaches no Gitea; so the export project holds no workspace read key. Its survey holds exactly `WORKSPACE` and `EXPORT_FOR`, the Keycloak user id of the Owner the export is for, and its environment `ws-<id>` holds `WORKSPACE` (`ws-<id>`) and the platform values of `SEMAPHORE_EXPORT_VARIABLES`, none of them a secret: `BAO_ADDR`, `BAO_CACERT`, `EXPORT_KEYCLOAK_URL` and `EXPORT_KEYCLOAK_REALM` with the values of the Workspaces project, `EXPORT_S3_ENDPOINT` (the S3 origin of `web-svc-seaweedfs`) and `EXPORT_S3_REGION`, `EXPORT_MAIL_HOST`, `EXPORT_MAIL_PORT`, `EXPORT_MAIL_FROM`, `EXPORT_MAIL_TLS` and `EXPORT_MAIL_AUTH` from the system mail settings, and `EXPORT_OWNER_MIN_AGE_DAYS`.
  `export-runner` has the workspace runner shape: a read-only root, all capabilities dropped, `no-new-privileges`, `tmpfs` HOME and task directory, `SEMAPHORE_RUNNER_ONE_OFF=true`, `SEMAPHORE_RUNNER_MAX_PARALLEL_TASKS=1` and `max_parallel_tasks` 1 on its row. Its only network is the internal `export` network; its one other member is the `egress` Squid of `meta/services.yml`, which alone also joins the outside network. The export reaches every service through it (`HTTPS_PROXY` and `EGRESS_PROXY`, an empty `NO_PROXY`), and its allow list `SEMAPHORE_EXPORT_PROXY` holds exactly the four pairs of `SEMAPHORE_EXPORT_EGRESS` (OpenBao, Keycloak, the S3 endpoint and the mail relay) and the Semaphore server at `SEMAPHORE_WEB_ROOT` the runner polls.
  The task logs in through `auth/jwt-export` with the role `ws-<id>` and reads the id of the pinned `Owner` group from `platform/data/export/owners/ws-<id>`. It exits non-zero before it reads a tenant secret when `EXPORT_FOR` is no direct member of that group id, holds no age recipient (`age1...`) in its Keycloak attribute `export_recipient`, or joined the group too recently, and it takes no recipient from the survey or the environment.
  The age gate reads the newest `ORGANIZATION_GROUP_MEMBERSHIP` admin event on `organizations/<org>/groups/<group>/members/<EXPORT_FOR>` and refuses while it is a `CREATE` younger than `services.semaphore.workspaces.export.owner_min_age_days` (default `7`); with no such event in the kept window the membership counts as older. The deploy fails when the parameter is no whole number, is below `2`, or is not below `services.keycloak.events.admin.expiration_days` of `web-app-keycloak`, because a missing event then no longer proves the age.
  The task writes a KeePass XML export of `tenant/data/ws-<id>/` with mode `0600`, builds `secrets.kdbx` from it with `keepassxc-cli import --set-password` and a random passphrase of 32 bytes on standard input, deletes the XML, seals the passphrase with `age -r <recipient>` into `passphrase.age` and uploads one tar of exactly these two files as `exports/ws-<id>/<task id>.tar`. Its last output line is a presigned `GET` link valid for 900 seconds; the passphrase and the secret values reach no argument, environment value, log or task output.
  The runner image pins both tools in `meta/services.yml` of `task-runner` as OpenTofu is pinned, with one download and one sum per architecture: `age_version` with `age_url_<arch>` and `age_sha256_<arch>` (the static `linux-amd64` and `linux-arm64` tarballs of [age](https://github.com/FiloSottile/age/releases)) and `keepassxc_version` with `keepassxc_url_<arch>` and `keepassxc_sha256_<arch>` (the `x86_64` and `aarch64` AppImages of [KeePassXC](https://github.com/keepassxreboot/keepassxc/releases)). The deploy picks the pair of the stack host's architecture (`SEMAPHORE_RUNNER_ARCHITECTURE`, from `HOST_ARCHITECTURE_BY_KERNEL`), since that host builds the image natively, and `build.sh mirror` fetches the providers of the same `linux_<arch>` platform. `build.sh install` refuses either download when its SHA-256 differs from the pin, so a build with a wrong sum fails. It extracts the AppImage with `--appimage-extract` into `/usr/local/lib/keepassxc-cli` and links `/usr/local/bin/keepassxc-cli` to its `usr/bin/keepassxc-cli`, so no FUSE is needed. `build.sh runtime` first installs the libraries the AppImage leaves to the distribution (glvnd, X11, fontconfig, FreeType, HarfBuzz, libgpg-error, libusb, OpenSSL 3, zlib) with `dnf`, `apt-get` or `pacman`, and the build runs `age --version` and `keepassxc-cli --version`, so a missing library fails the build rather than the first export.
  Before the upload, and on every refusal with its reason, the task mails every direct member of the pinned group, naming the workspace, the Owner the export is for and the time. It reaches the relay the way the system mail settings describe it: implicit TLS when `EXPORT_MAIL_TLS` is `true`, never STARTTLS, and an SMTP login when `EXPORT_MAIL_AUTH` is `true`, with the username and password the deploy writes into `platform/data/export/mail` and deletes again once the settings need no login.
  The export project also holds two scheduled templates on `export-runner`, each with an empty survey and no grant: `announce owners` runs [announce-owners.sh](./files/shell/repository/announce-owners.sh) daily at `0 6 * * *`, and `prune exports` runs [prune-exports.sh](./files/shell/repository/prune-exports.sh) hourly at `0 * * * *`. Their tasks log in through `auth/jwt-export` with the roles `announce-owners` and `prune-exports`, which `web-app-openbao` binds to the export project and that template, with the policy `export-shared` only. `announce owners` lists `platform/metadata/export/owners/` and, for each pinned group id, mails every direct member about every Owner whose newest `ORGANIZATION_GROUP_MEMBERSHIP` event on that group is a `CREATE` younger than the parameter, naming the new Owner, the join time and the first day an export for them is possible. It keeps no state, so a missed run is caught by the next one; a subgroup member or a group found by name never counts, and a failing workspace is named after the others ran. `prune exports` lists the bucket `exports` page by page and deletes every object older than one hour, naming each delete that fails.
  A leaked store credential can start an export for any Owner of any workspace, and the file opens only with that Owner's age identity; an account it makes Owner exports only after the age window, and every Owner is mailed daily about that account until the window ends.

## Provision

The provision project `<SOFTWARE_NAME> Provision` holds, per workspace, the locked templates `provision-<provider> ws-<id>` and `destroy-<provider> ws-<id>` for each provider of `PROVISION_PROVIDERS` in [project.py](./files/python/project.py) (`hetzner`, `incus`, `ionos`, `proxmox`, `scs`), each running its script with the provider as its one fixed argument, and `unlock ws-<id>`, `dns ws-<id>` and `zone ws-<id>`. `workspace apply` removes every other template of the workspace there, such as a `provision ws-<id>` an earlier release left. They run on the provision runner, never on a workspace runner, because that runner holds the provider tokens and the DNS credentials. The store's Semaphore account holds the role `guest` there, and each workspace template carries one grant for `guest` with `CanRunProjectTasks` and `CanReadProject`. So the store starts and reads exactly those templates and changes none. Every task output of the project is readable by the store, so no provision output carries a secret.

- **Interface:**
  [interface.json](./files/opentofu/interface.json) is the contract of every root under `files/opentofu/roots/` (`hetzner`, `ionos`, `scs`, `proxmox`, `incus`): the inputs `name`, `flavor`, `size`, `region`, `ssh_public_key` and `dns_label`, the outputs `host`, `host_key`, `server_id` and `fqdn`, and in `$defs` the shapes of the order line, the workspace values and the catalog. The runner image installs one pinned OpenTofu and a provider mirror, and the CLI configuration [tofurc](./files/opentofu/tofurc) names only that mirror.

- **Order line:**
  The templates take the survey variables `SALES_ORDER` (`^[A-Za-z][A-Za-z0-9-]{0,55}$`) and `LINE` (`^[1-9][0-9]{0,5}$`). A `LINE` has no leading zero, so `7` and `007` cannot name the same line twice. `provision` and `destroy` also take `PROVIDER_TOKEN`, `platform` or `workspace`: `platform` uses the provider token of the platform, `workspace` the customer's own token at `tenant/data/ws-<id>-provision/providers/<provider>` (field `token` for `hetzner` and `ionos`, the application credential for `scs`), and neither falls back to the other. A missing or empty customer token, and `workspace` on `proxmox` or `incus`, refuse the run before OpenTofu starts. `platform` reads the platform secrets only while the last `workspace apply` of the workspace set `WORKSPACE_PLATFORM_TOKENS` to `true`; otherwise OpenBao answers 403 and the run fails before OpenTofu starts. The task token names the template, and OpenBao binds each template of a provider to that provider's role alone, so the script logs in once, with `ws-<id>-provision-<provider>` of the provider its template pins, whose policy reads the workspace's state bucket keys, its DNS credential and that provider's secrets and no other provider's. A task token that leaks from the run opens exactly that role. The wrappers hand the task token to `provision.py` on descriptor 3 and drop `SEMAPHORE_JWT` from its environment, and `provision.py` refuses a start that still carries it. Before it reads the descriptor, `provision.py` sets `prctl(PR_SET_DUMPABLE, 0)`, so no other process of the runner's uid reads its environment or memory, where the task token and the role token sit while OpenTofu runs; OpenTofu's `execve` resets the flag. OpenTofu and its provider plugins never get the role token: `BAO_TOKEN` there is a non-renewable child token without the `default` policy, minted through the token role `ws-<id>-transit-child`, that carries `ws-<id>-transit` alone, `update` on the workspace's transit datakey and decrypt. On every exit Python handles, a SIGTERM and the run budget included, `provision.py` revokes its role token with `auth/token/revoke-self`, which revokes the child too. Any error of that revoke beside a refusal or failure of the run, the run budget passing during it included, is only reported on stderr, and the run ends with its own exit code and message. The exceptions are a SIGTERM or SIGINT during the revoke, which ends the run with that signal instead, and a SIGKILL at any point: the role token then stays valid until its TTL of 4h and the child until its TTL of 2h. A `provision` run checks the pinned provider against the live catalogs before it logs in. A `destroy` run has to log in first, because the provider is in the state record: it logs in, reads the state bucket keys and reads the record, and refuses a line recorded with another provider before it reads the DNS credential, mints the child token or reads a provider secret. A template without its provider argument is refused before any login. [provision.sh](./files/shell/repository/provision.sh) reads `provision/<SALES_ORDER>-<LINE>.tfvars.json` from the workspace checkout and checks it against `interface.json`: no unknown key, typed values, and a size and region from the catalog. It refuses a checkout that holds any `*.tf`, `*.tf.json`, `*.tofu`, `*.tofu.json`, `.terraformrc` or `.tofurc`. It copies the root from the image into a task directory, clears every `TF_*` and `AWS_*` variable it did not set itself, and runs OpenTofu there, never in the checkout.

- **Workspace values:**
  `WORKSPACE`, `WORKSPACE_DNS_ZONE` and `WORKSPACE_DNS_ZONE_ID` come from the template environment that `workspace apply` writes. The script writes them as `workspace.json` beside the root; the checkout cannot set them.

- **State:**
  The state lives in the workspace bucket `ws-<id>-state` under the key `<SALES_ORDER>/<LINE>.tfstate`, never under a run id, so a retry applies to the same server. The backend locks with `use_lockfile = true`. OpenTofu encrypts state and plan with the OpenBao transit key `ws-<id>-provision`, with `enforced = true`, so no plaintext state is ever written. Before any state write, `provision`, `destroy` and a `dns` record change read `key_created_at` and `snapshot_at` from `platform/data/provision/transit/ws-<id>` and refuse when the record is missing or the snapshot is older than the key, so no state is encrypted with a key that has no backup. After a successful `tofu destroy`, `destroy` deletes `<SALES_ORDER>/<LINE>.tfstate` and a `dns` removal deletes `<SALES_ORDER>/<LINE>.dns.tfstate`, each with its `.tflock`, so the bucket of a destroyed workspace can be emptied.

  Right before `tofu apply`, `provision` writes `<SALES_ORDER>/<LINE>.provision.json` into the same bucket: the provider and the catalog it ran with. `destroy` takes its root and `catalog.json` from that record, never from the live catalogs, so a retired region or a second provider listing the region does not block it. A state from before the record falls back to the live catalogs and says so on stdout. The destroy deletes the record with the state.

  The last stdout line of a successful `provision` is one JSON object of the outputs by name. The last stdout line of a successful `destroy` is `{"destroyed": [<resource address>], "state": "deleted"}`: the addresses `tofu state list` named before the destroy, printed only after the state lists nothing and is deleted. A destroy that leaves a resource fails and deletes nothing.

- **Backend keys:**
  The S3 keys of the state bucket come from `tenant/data/ws-<id>-provision/s3`. The script writes them into a backend file of mode `0600` in the task directory and passes its path as the only `-backend-config` argument. They never enter the environment or an argument, so under `route53` the environment holds only the workspace's own `AWS_*` keys. The task directory, with the backend file and `.terraform/`, is removed on every exit.

- **Target records:**
  [credentials.json](./files/opentofu/credentials.json) names, per OpenBao record, the field each provider variable or credential file takes; a value of `{field}` parts joins several fields of one record. `PROXMOX_VE_ENDPOINT` is the `endpoint` of `platform/data/provision/proxmox-<host>`, and `PROXMOX_VE_API_TOKEN` is `<token_id>=<secret>` of `tenant/data/ws-<id>-provision/proxmox`, whose `token_id` is the full token id `ws-<id>@pve!provision`. `INCUS_ADDR` is the `endpoint` of `platform/data/provision/incus-<host>`, its `certificate` is the pinned server certificate, and the `certificate` and `key` of `tenant/data/ws-<id>-provision/incus` are the client pair. The roles that write these records keep exactly these field names.

- **SCS customer credential:**
  Under `PROVIDER_TOKEN=workspace` an `scs` line runs with the customer's OpenStack application credential at `tenant/data/ws-<id>-provision/providers/scs`, which the store writes like the Hetzner and IONOS tokens, with exactly the two fields `application_credential_id` and `application_credential_secret`. Core picks the endpoint: `OS_AUTH_URL` is the `auth_url` and `OS_REGION_NAME` the `region` of the catalog region of the order, never a value of the customer's record, so an `scs` region names `auth_url`, `region` and `network`, and a region without `auth_url` or `region` refuses the run. A record that carries `auth_url` or `region_name` is refused. Before OpenTofu starts, the script holds the credential against Keystone: it must authenticate, be scoped to exactly one project, not be `unrestricted`, so it cannot create further credentials, and not expire within the run's time budget of two hours; every run fails once it outlives that budget: OpenTofu runs in the sandbox of its run (see "OpenTofu sandbox per run" below), so only the script interrupts it: the script has the spawner send every process of the sandbox SIGINT so OpenTofu writes its state and releases its lock, waits up to five minutes, has every process of the sandbox killed, OpenTofu and its provider plugins, only after that grace and says so, and the check covers the budget plus the grace, so the credential outlives OpenTofu. Should the script itself die, its connection to the spawner closes and the spawner kills the sandbox, so neither OpenTofu nor a provider plugin holding the credential runs on without the script. Once OpenTofu ends, the spawner kills every process left in its sandbox before the script goes on, so a provider plugin that outlived OpenTofu ends with the call; should a signal kill OpenTofu itself, the run fails saying the state may keep its lock. A budget that ends while the script revokes its Keystone token or removes its task directory fails the run as soon as that step is done, without moving the deadline; each connect, send and receive of the revoke times out after ten seconds, while name resolution keeps the system's own timeouts. Keystone answering the login with 401 or 403, or a credential that breaks a rule, refuses the run naming the rule; any other answer fails it. The script revokes the token it minted for the check, and no message carries any part of the secret. `PROVIDER_TOKEN=platform` keeps reading `tenant/data/ws-<id>-provision/scs` and never the customer's record.

- **Unlock:**
  `unlock ws-<id>` takes the same `SALES_ORDER` and `LINE`. It refuses while a `provision` or `destroy` task of the workspace runs, and otherwise runs `tofu force-unlock -force` with the lock id it reads from the `.tflock` object.

- **Catalog:**
  `services.semaphore.workspaces.catalog.<provider>` holds, per root, the sizes and regions of each flavor in the shape of `$defs.catalog`. An inventory replaces the catalog of a provider as a whole; core merges no entries into it. The defaults of `incus` and `proxmox` are the ones the live provision tests run with: one size `demo` (1 vCPU, 2048 MiB, 20 GiB); the Proxmox regions `pve` (`kvm` true) and `pve-emulated` (`kvm` false) on node `pve`, storage `local-lvm` and bridge `vmbr0`; the Incus region `default` on the pool `agents`, whose network comes from the project's default profile. A region's `host` is the first inventory host of `web-app-proxmox` or `svc-virt-incus`, empty without that group, and a provision refuses an empty host. The defaults of `hetzner`, `ionos` and `scs` are empty, so a deployment that sells hosted servers sets its own catalog; a provision against an empty catalog refuses and names it. Region keys must be unique across providers: an order names a region and no provider, so the deploy refuses a region that two providers offer. The deploy validates every catalog and writes it to the read-only catalog mount of the provision runner; the script reads it from there, never from the image or the checkout.

- **Bring-your-own record:**
  `dns ws-<id>` takes `DNS_ACTION` (`create`, `remove` or `unlock`), `SALES_ORDER`, `LINE`, `HOST` and `DNS_LABEL`. `create` points `<DNS_LABEL>.ws-<id>.<zone>` at `HOST`, which must be the host of a pair in `WORKSPACE_TARGETS`. An address writes an A or AAAA record. A fully qualified host name, checked with the pattern of `$defs.host_name` in `interface.json`, writes a CNAME to that name, and core never resolves it, so the record follows the customer's own DNS. It reads no file of the checkout. Its state key is `<SALES_ORDER>/<LINE>.dns.tfstate`, so a removal deletes only its own record and leaves the record of any other line in place. A `create` and a `provision` refuse a name that already holds an A, AAAA or CNAME record, unless their own state already holds it, because a CNAME cannot share its name with another record.

- **Customer zone:**
  `zone ws-<id>` creates, shows and deletes the Cloudflare zone of a customer domain sold as an order line, with core's own token, so the store holds no Cloudflare credential. It takes `ZONE_ACTION` (`create`, `show`, `delete` or `unlock`), `SALES_ORDER`, `LINE` and `DOMAIN`, each with target `env`. `create` and `show` need all four, `delete` and `unlock` refuse a `DOMAIN`, and `DOMAIN` must match `ZONE_PATTERN` of [lib.sh](./files/shell/repository/lib.sh). [zone.sh](./files/shell/repository/zone.sh) refuses any argument, an unknown action and a malformed or untaken variable, naming it, before any OpenTofu call, and reads no file of the checkout. The root `files/opentofu/zone/` ([main.tf.json](./files/opentofu/zone/main.tf.json)) holds only the zone, under the state key `<SALES_ORDER>/<LINE>.zone.tfstate` in `ws-<id>-state` with the lock and encryption of the server state, so no `provision`, `destroy` or `dns` of the line plans a change of it.
  `create` runs `tofu apply`, so a repeated `create` changes nothing, and refuses a `DOMAIN` the account already holds outside this state, and a `DOMAIN` other than the zone its state holds, before any write. `show` reads the state and the provider and writes nothing. The last output line of `create` and `show` is `{"zone", "zone_id", "status", "name_servers"}`: the provider's zone status and the assigned name servers the customer sets at the registrar. `delete` runs `tofu destroy`, deletes the state with its `.tflock` and prints `{"deleted": true, "zone": "<domain>"}`, or `{"deleted": true, "zone": null}` when the state holds no resource or is missing. A state that holds the zone without its outputs, as an interrupted apply leaves it, makes `create` and `show` fail without a change; `delete` reads the domain from the zone resource in the state, destroys it and fails without a change only when the state names no zone; `unlock` does not read the state. `unlock` force-unlocks the zone state with the lock id of its `.tflock`. A zone task refuses while another zone task of the same line runs. `workspace destroy` refuses while a `.zone.tfstate` remains, as for a server state.
  The zone token is the role secret `secrets.credentials.cloudflare_zones_token`, with the right to create and delete zones in the one account of `secrets.credentials.cloudflare_zones_account_id` and nothing else. The deploy writes both from stdin to `platform/data/provision/cloudflare-zones`, which only the zone role `ws-<id>-zone` of a workspace reads, and deletes that record when either is empty; the store, a provision, destroy, unlock or dns task, a workspace task and an export task get 403 there. `zone ws-<id>` logs in with that role, whose policy reaches no other provider secret. The token reaches the provider as `CLOUDFLARE_API_TOKEN` of the `tofu` process and the Cloudflare API only in an `Authorization` header, never an argument, a task output or a survey value. `services.semaphore.workspaces.dns.zone_probe` names the domain the live zone specs create and delete; empty, or either secret empty, skips them.

- **DNS flavors:**
  `services.semaphore.workspaces.dns.flavor` picks `knot` (the default), `route53` or `cloudflare`.
  - `knot`: Knot DNS serves the subzone, and each workspace's TSIG key changes only names at or below its own name `ws-<id>.<subzone>`, with the types A, AAAA, CNAME and TXT.
  - `route53`: each workspace has an IAM user whose policy holds exactly four actions: `route53:ChangeResourceRecordSets` on the hosted zone of the subzone, only for names below `ws-<id>.<subzone>` and the types A, AAAA, CNAME and TXT, `route53:GetHostedZone` and `route53:ListResourceRecordSets` on that hosted zone, and `route53:GetChange` on its changes. A workspace key therefore lists every record of the subzone, the names and addresses the subzone answers publicly anyway, but changes only its own names. `workspace apply` reads the AWS credential that manages the workspace IAM users from `platform/data/workspaces/route53` and fails, naming that path and the missing field, when the deployment holds none; it never skips. It finds the hosted zone of the subzone by `ListHostedZonesByName` and refuses unless exactly one hosted zone carries that exact name, sets `workspace_dns` to the subzone and that hosted zone, and renders the policy for `ws-<id>`. It then creates the IAM user `ws-<id>` when missing, holds the policy as its only inline policy `records` with exactly the rendered document, and keeps the access key `tenant/data/ws-<id>-provision/dns` holds with its secret while that key is active, mints one otherwise and deletes every other key of the user. The key goes to the fields `access_key` and `secret_key` that `credentials.json` reads and the policy to the field `policy`, keeping every other field of that record, so a second apply mints nothing and reports unchanged. `workspace destroy` deletes the user's access keys, its inline policies and the user, and refuses a user it cannot empty. Both call IAM and Route 53 through the role's modules `semaphore_route53_user` and `semaphore_route53_zone_info`, which sign each request with SigV4 from `utils/aws_api.py` and need no AWS SDK. The credential travels as a masked module argument and in the signature, never on a command line, and needs `iam:GetUser`, `iam:CreateUser`, `iam:DeleteUser`, `iam:ListUserPolicies`, `iam:GetUserPolicy`, `iam:PutUserPolicy`, `iam:DeleteUserPolicy`, `iam:ListAccessKeys`, `iam:CreateAccessKey`, `iam:DeleteAccessKey` and `route53:ListHostedZonesByName`.
  - `cloudflare`: a pool of zones, each with a token of its own. `workspace apply` places a workspace in the first zone below its record limit: it counts the records of every zone of the pool through the Cloudflare API with that zone's own token and refuses when every zone is full. The limit is `services.semaphore.workspaces.dns.record_limit`, the per-zone record limit of the deployment's Cloudflare plan, which core leaves at `0`, so `apply` refuses until the deployment sets it. A workspace stays in the zone its provision environment already names; `apply` refuses rather than moves it when that zone left the pool. A zone token changes every record of its zone and so reaches every workspace placed in that zone; no two zones share a token.

  The DNS credentials are role secrets, never `services.*`: `secrets.credentials.route53_access_key_id` and `secrets.credentials.route53_secret_access_key`, the AWS identity that creates the workspace IAM users, and `secrets.credentials.cloudflare_zone_tokens`, a JSON object from each zone to its token whose keys are the zone pool in placement order. Each is a `plain` credential, so the inventory holds it vault-sealed or as an OpenBao reference. The deploy writes the Route 53 pair to `platform/data/workspaces/route53` and each zone token to `platform/data/provision/cloudflare/<zone>`, both from stdin and under the masking of every credential task, so no value reaches an argument or a log. A credential placed under `services.*` is ignored. An empty credential means the flavor's live checks do not run, and the deploy names the missing key.

### OpenTofu sandbox per run

Every OpenTofu run on the provision runner runs in a sandbox of its own, so code in OpenTofu or a provider plugin of one run reaches neither the runner token nor the credentials, files or processes of another run.

- **Identity.** The provision runner alone starts as root, with [sandbox/spawner.py](./files/python/sandbox/spawner.py) as its entry point, which serves the sandboxes and takes the admission of a run from [admission.py](./files/python/provision/admission.py), the start-up layout and the closing of the container from [hardening.py](./files/python/provision/hardening.py) and every helper it runs as a sandbox uid from [privileged.py](./files/python/provision/privileged.py). The spawner starts the Semaphore runner as uid `64101`, reaps as PID 1, each by its own pid, every exited orphan but the children it waits for itself, whichever exited first, forwards `SIGTERM` and `SIGINT` to the runner, also while its main thread holds the reentrant lock of its children, and ends with its exit code. Its accept loop survives the `OSError` of any failed accept, `EMFILE` included, and the `RuntimeError` of a serve thread that cannot start, `can't start new thread` included, whose connection it closes, each with a stderr line naming the type and text of the error, and a closed stderr does not end it either; any other exception, one of the start of a serve thread included, ends the loop with its traceback on stderr, and the end of the accept thread sends `SIGTERM` to the spawner, whose handler stops the Semaphore runner, so the container restarts instead of keeping a runner that no sandbox serves; a serve thread closes its connection on every path, and a receive that raises still kills every process of the sandbox's uid and joins the waiter of its last run before the uid is freed. A run whose waiter thread cannot start is killed and waited for at once, so no zombie keeps its uid held, and its call ends with an error reply. Every descriptor a message carries is closed on every path, a line that is no JSON, a close and a failed start included. Once per run, when `provision.task_directory` enters `sandbox.opened`, which asks over a socket in the `0700` `/tmp` of that uid, it opens the sandbox every OpenTofu call of that run starts in, under a uid of its own from `SEMAPHORE_SANDBOX_UID_BASE` (`vars/main.yml`) for `SEMAPHORE_SANDBOX_UID_COUNT` uids, below the workspace runner uids from `SEMAPHORE_WORKSPACE_UID_BASE` on and apart from `64101`. OpenTofu starts there through `setpriv`; overlapping runs never share a uid, and a uid returns to the range only once no process holds it and no file or System V IPC object of its run is left. The spawner runs only the image's `tofu` (`SEMAPHORE_SANDBOX_TOFU`), or the live probe, with only the commands and flags `provision` uses (`opentofu.COMMANDS`): `-chdir=` and `-plugin-dir=` are refused, and `-backend-config=` and `-var-file=` take only the file form, never `<key>=<value>`, naming a file below the task directory without `..`, which the exec helper, as the sandbox uid, walks by directory descriptors and refuses when a link stands on the way, as root may not search the `2770` directory. Of the variables, only the names `provision` passes are admitted, no value with a line break or NUL, and per name: `PATH` is the spawner's own; `TF_CLI_CONFIG_FILE` only the image's `tofurc`; `BAO_ADDR` only the layout's `SEMAPHORE_SANDBOX_BAO_ADDR`; `BAO_CACERT` only the layout's `SEMAPHORE_SANDBOX_CA`, and none at all when that is empty, as it is unless `TLS_MODE` is `self_signed`; the proxy, locale and `SSL_*` names only the spawner's own values; `TF_ENCRYPTION` only the exact document `session.encryption` writes for one workspace, so no other key provider or address; `HOME` and `TMPDIR` only the run's home; a credential file name such as `INCUS_CONF` only a path below the task directory; an endpoint such as `OS_AUTH_URL`, `PROXMOX_VE_ENDPOINT`, `INCUS_ADDR` or the remote `INCUS_REMOTE`, in any case, no local path or socket and not the built-in `local` remote of Incus, the host's own daemon; every other value, a secret that starts with `/` included, passes as it is. That allowlist protects the spawner, other runs and the host; it does not guard a run against its own root module, which `64101` stages and whose `local-exec` runs inside the sandbox by design.
- **Reach.** A sandbox reaches its task directory `/run/provision/<uid>/task` (`2770`, owner `64101`) read-write, through the group of its uid, and its own `HOME` and `TMPDIR` `/run/provision/<uid>/home`; the image's `tofu`, provider mirror, CLI configuration, system libraries and CA store stay readable. Its environment is `Session.environment` with the spawner's own `PATH`. The runner token (`0400` of `64101`), `/tmp` with `/tmp/semaphore` and the lock directory, every other task directory and the environment, memory, descriptors and working directory of every process of another uid stay closed to it. At start the spawner walks the container, `/proc` and `/sys` left out, and drops world-write and the sticky bit from every directory any uid may write to, at least `SEMAPHORE_SANDBOX_SHARED` (`/var/tmp`, `/dev/shm`, `/dev/mqueue`); it refuses to start when one keeps world-write, or when every uid may pass a directory it cannot list, as a world-writable directory could hide below it, so a sandbox creates files only in its task and home directories. Before the run's first OpenTofu call, `provision.py` stages the root module, the provider lock file and the modules into the fresh task directory with `shutil.copytree` and `shutil.copy2`, while no process of the sandbox has run there; from the first call on, `64101` writes into it only through `sandbox.task_write`, by directory descriptors with `O_NOFOLLOW` and `O_CREAT|O_EXCL`, which refuses `..`, so a link the sandbox plants never redirects a write into another run. The task directory has no sticky bit, so `tofu init` may replace the staged `.terraform.lock.hcl`.
- **Lifetime.** When `opentofu.tofu` returns or raises, the spawner has killed every process of the sandbox's uid, one in a session or process group of its own included. A process that survives the kill fails the call, the spawner quarantines the uid at once, and the run gets no further call in it; the error reply ends `opentofu.tofu` at once, without the SIGINT grace, and a captured stdout is read no further, as the survivor may hold its pipe. A uid returns to use only when it owns no entry anywhere the spawner's walk of the container reaches and no System V IPC object. Once the run ends, the spawner removes the task and home directories by a descriptor walk that holds below `PATH_MAX` too and, as the sandbox uid, every System V IPC object of that uid from `/proc/sysvipc`, each step even when an earlier one failed, and only then frees the uid; a uid with anything left stays quarantined and stderr names it. Quarantined uids return only when the container restarts, so at most `SEMAPHORE_SANDBOX_UID_COUNT` (256) failed cleanups exhaust the range, after which every open is refused with `every sandbox uid is taken`. Should `provision.py` die, its connection closes and the spawner does the same. `sandbox.opened` waits at most `sandbox.OPEN_SECONDS` (60) to connect and for `sandbox.QUEUED`, which the spawner sends once it read the open and before it waits for a free uid, else the run fails with its `failed:` line instead of waiting out the run budget; the wait for the uid after `sandbox.QUEUED` is bounded only by the run budget, so a burst of parallel runs queued behind the walk for leftovers never fails on it, and a serve thread that dies after `sandbox.QUEUED` closes the connection, which fails the open with `opened no sandbox`. A socket that is missing or refuses the connection, and a spawner that closes the connection with the open unread, fail the open the same way, as a `SandboxError` naming the error, so the run still ends with its `failed:` line. An `OSError` of the kill, the close or its answer at the end of `sandbox.opened`, a spawner that broke the connection off mid-run among them, fails the run the same way, and an error the run raised first stays the one it reports.
- **Container.** The provision runner sets `cap_drop: ALL`, adds only `SETUID`, `SETGID` and `CHOWN`, sets `no-new-privileges` and keeps Docker's default seccomp profile in compose and swarm mode. `docker stack deploy` drops `security_opt`, so the spawner sets `PR_SET_NO_NEW_PRIVS` on itself through `prctl` before it serves and refuses to start when that fails; `setpriv` still drops to the sandbox uid under it, as the flag bars only gains on `execve`; its `/tmp` is a `0700` tmpfs the spawner hands to `64101`, and `/run/provision` a `0711` tmpfs. The spawner reads its layout, the `SEMAPHORE_SANDBOX_*` names, from the runner's own env file [templates/env/provision-runner.j2](./templates/env/provision-runner.j2), which includes the env of the other runners, so the compose template declares no `environment:`. `sys-svc-compose` renders that file on every deploy, the provision runner off included; of the runner's settings it reads only `services.provision-runner.enabled`, which leaves `SEMAPHORE_SANDBOX_BAO_ADDR`, its one value that names OpenBao, empty while the runner is off, so the env of a deploy without the runner pins no OpenBao address, which no spawner would read; the `domain` lookup resolves `web-app-openbao` from the defaults of its role whether the inventory holds it or not, so the gate keeps the address out, not a failed lookup. Every other runner still starts as `64101`. The network is the runner's own.
- **Live probe.** Every deploy with the provision runner runs [sandbox/probe.py](./files/python/sandbox/probe.py) as `64101` in it, on the node `resolve_host_cid.yml` finds the runner on: two probes at once, each in a sandbox of its own, report every read above that succeeded, every directory outside their own they may write to, one they cannot list included, and whether a child of a new session or a System V IPC segment outlived the call, and two probes outside any sandbox must find the token, each other's marker, their living child, a byte of its `mem` at a mapped address and their own segment, else the check is blind. `🛡️ Assert the OpenTofu sandbox holds` fails the deploy on any finding of `semaphore_sandbox_findings`.
- **Tests.** The sandbox tests include `test_the_built_in_local_remote_is_refused` (control `test_negative_control_a_check_blind_to_the_local_remote_admits_it`), `test_the_spawner_reads_the_container_layout_from_the_role` (control `test_negative_control_a_layout_the_role_left_out_is_refused`) and `test_the_threaded_spawner_never_installs_or_awaits_a_signal`, which follows every class and function of the `provision` package a spawner thread names, transitively, and catches `signal` imported as a module or by name (controls `test_negative_control_a_handler_in_the_spawner_is_found`, `test_negative_control_a_handler_in_a_privileged_function_is_found`, `test_negative_control_a_handler_imported_by_name_is_found` and The spawner's unit tests run its own holder, kill, quarantine, file and IPC purge code against a fake `/proc`, a fake `kill` and a fake owner per planted inode, so a kill by process group, a purge that skips, follows a link, opens up a directory behind a link, removes another uid's file or stops at a tree beyond `PATH_MAX` fails them; the `tofu init` replace of the staged lock file runs on a real `2770` directory, but as one uid, so the group access of a distinct sandbox uid stays proven only by the mode model and the live run; the provision harness, without root, fakes the sandbox uid with the run's `HOME`, kills by process tree and purges as the test's uid without the IPC helper, and only the deploy's live probe proves the kill by uid.
