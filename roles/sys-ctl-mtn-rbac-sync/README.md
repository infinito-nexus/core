# RBAC Sync

## Description

Reconciles the role mapping of every application that cannot read its role groups at sign-in with the members those groups hold in the directory now, so a group change in Keycloak or LDAP reaches the application within one timer interval instead of at its next deploy.

## Overview

An application registers its reconcile as a hook through [tasks/utils/rbac/sync.yml](../../tasks/utils/rbac/sync.yml). The util writes `hooks/<application_id>/` under `DIR_RBAC_SYNC`, root-only, with `hook.json`, the hook's script and the modules a host hook imports, and runs the hook once with the members the deploy resolved. The timer runs [files/python/script.py](./files/python/script.py) on `SYS_SCHEDULE_MAINTANANCE_RBAC_SYNC`; it reads the members of each hook's role groups anonymously from the directory and runs every hook whose container runs on the node.

A `container` hook pipes its script into a command inside the application's container, for applications whose image ships a scripting runtime. A `host` hook runs its script with the node's Python beside its modules and reaches the container through `$RBAC_SYNC_CONTAINER_BIN exec ... $RBAC_SYNC_CID`, for applications that only expose a CLI or an HTTP API inside the container. It reads its members from the root-only file `$RBAC_SYNC_MEMBERS_FILE` names, which exists only while the hook runs and lives in the node's temporary directory, because every swarm node shares the hook directory. A hook runs on the node of the one container it names and reaches nothing else: in swarm no `ports.local` port is published, so an application whose hook acts on its database cannot also call its own HTTP API from there. Such work runs at deploy time inside the application's network namespace, as [web-app-peertube](../web-app-peertube/README.md) creates its accounts, and the hook keeps the SQL.

## Features

- **One execution path:** the deploy and the timer run the same hook through the same script; only the source of the members differs.
- **Directory lookup without packages:** members come from the `ldap_client` module of `svc-db-openldap`, a standard-library LDAP client. It connects to the `ldapi` socket `svc-db-openldap` bind-mounts on its node (`LDAP.SERVER.SOCKET_URI`), the address the role's own provisioning uses in both modes; swarm publishes no `ports.local` port, so the loopback port reaches nothing there.
- **Mailbox seed:** under the `mailbox` email policy of `web-app-keycloak`, `svc-db-openldap` installs the timer. Only once the deploy has applied the mailbox layout, which in a deploy with Keycloak happens after Keycloak accepted the realm's policy, [tasks/mailbox.yml](./tasks/mailbox.yml) writes the root-only `mailbox.json` under `DIR_RBAC_SYNC`; under the `external` policy `svc-db-openldap` removes it. While it exists, each run without `--only` gives every account of the users OU that holds no `mail` the address `<uid>@<DOMAIN_PRIMARY>` and the class `infinitoMailboxUser` before the hooks read the members. An existing `mail` value is never changed. The address comes from the `ldap_mailbox` module the deploy's mailbox layout uses. The run binds as `LDAP.DN.ADMINISTRATOR.DATA`; its password lives in `mailbox.json`, never in argv, the log, `config.json`, or the members a hook receives. Every deploy that installs the timer rewrites an existing `mailbox.json` before it starts the run, so a password the deploy rotated reaches the seed before the first bind, long before Keycloak applies the layout again.
- **Node-local execution:** a hook runs only where its container runs; on any other node the script reports it as skipped. The script and its modules are installed on every swarm node, because the deploy-time run happens on the node of the hook's container.
- **Reads follow the socket:** the socket exists only on the node OpenLDAP runs on, and OpenLDAP can only start on a host of `svc-db-openldap`, the only hosts where that role creates the socket's bind-mount source. The timer runs on each of them. A missing socket is one `SKIPPED` line with no hook run only where slapd is not expected: on a node outside `svc-db-openldap`, whose own unit passes `--remote-directory`, or while the backup's maintenance signal (`FILE_MAINTENANCE_BACKUP`, read by the `maintenance` module of [svc-bkp-volume-2-local](../svc-bkp-volume-2-local/README.md)) lists `svc-db-openldap` as stopped. On any other host of `svc-db-openldap`, including one whose signal cannot be read, a missing socket or a socket that does not answer fails the run in one `FAILED` line. Where slapd belongs is a fact of the node, so it lives in the node's unit and never in `config.json`: swarm nodes share `DIR_RBAC_SYNC` over NFS, and a per-node value there holds whatever node wrote last. No hook dials the directory itself: a hook that needs more of an account than its login, mail, name and uuid declares those attributes, and both member sources read them, the deploy on the stack host and the timer through the socket, so the hook works on a node without the socket, where in swarm the deploy-time run is its only run.
- **Runs only on change:** a hook registered with `skip_unchanged` runs when its definition or the members it receives changed since its last successful run, and at least once per `RBAC_SYNC_REFRESH_SECONDS`. An application that grants roles at sign-in MUST register with `skip_unchanged: false`: a member who joins and leaves a group between two runs leaves the member digest as it was, so a skipped hook would keep the sign-in grant until the refresh.
- **Single run per cluster:** in swarm the timer only uses the container of task slot 1. A hook registered with `any_slot` runs through a running task of any slot on the node instead, so it also runs while task slot 1 lives on another node. The timer reaches hooks only on the node whose `ldapi` socket answers, so such a hook still runs once per cluster; it skips while no task of its service runs on that node. [web-app-nextcloud](../web-app-nextcloud/README.md) registers its LDAP profile refresh this way.
- **Secrets stay out of argv:** forwarded variables reach `container exec` by name, their values travel in the environment.
- **Attributes stay out of the log:** the deploy masks every search, fact and reconcile run that carries declared attribute values, such as addresses or photos, also where `MASK_CREDENTIALS_IN_LOGS` is off. Turning `MASK_CREDENTIALS_IN_LOGS` off therefore no longer shows those tasks. To debug one, run the runner by hand with `--directory <DIR_RBAC_SYNC> --only <application_id>`: it prints every line of the hook's output and, when the hook fails, its errors. Without `--members-file` this run reads the directory itself, so it only reaches the hook on a host of `svc-db-openldap` that also runs the application's container. A host of `svc-db-openldap` without that container prints one `SKIPPED` line; a node outside `svc-db-openldap` fails in one `FAILED` line, or prints one `SKIPPED` line with `--remote-directory`. It also skips a `skip_unchanged` hook whose inputs did not change; delete `hooks/<application_id>/last_run.json` under `DIR_RBAC_SYNC` to force the run. On any other node, pass `--members-file <file>` with the `{role: [members]}` JSON the hook expects. That run reads no directory and never skips for unchanged inputs, but fails when the node runs no container of the application. Such a file holds the very attributes the masking hides, so keep it root-only and delete it afterwards.
- **Hooks from the previous release keep running:** a `host` hook whose `hook.json` has no `attributes` key was registered before hooks received a members file. It still gets the directory settings in `$RBAC_SYNC_LDAP`, the same value as before, and no members file, until its application's next deploy registers it again. A hook without an `any_slot` key keeps the task of slot 1. A runner that another application's deploy installs therefore never breaks such a hook.
- **One hook per failure:** a hook whose members cannot be read fails alone in one `FAILED` line; the other hooks of the run still run.
- **Timer only with a directory:** without `svc-db-openldap` on `STACK_HOST`, and on every host outside `svc-db-openldap`, the service stays installed for the deploy-time run and the timer stays off.
- **Failure notification:** a failed hook fails the unit, which triggers `sys-ctl-alm-compose`.

## Hook file

| Key | Meaning |
| --- | --- |
| `application_id` | application whose role mapping the hook reconciles |
| `kind` | `container` or `host` |
| `roles` | role names whose members the hook receives; `@users` stands for every account of the users OU, for hooks that refresh profiles, and `@users:<attribute>` for every account of it that holds the attribute |
| `attributes` | further directory attributes every member carries under `attributes`, the octets of the first value base64-encoded so binary values such as `jpegPhoto` survive; empty for none; a `host` hook without this key reads `$RBAC_SYNC_LDAP` instead of `$RBAC_SYNC_MEMBERS_FILE` |
| `container` | `{"name": ...}` in compose, `{"swarm_service": ...}` in swarm |
| `user` | user a `container` hook's command runs as, empty for the image's user |
| `argv` | command a `container` hook runs inside the container, empty for a `host` hook |
| `script` | file in the hook directory: piped to a `container` hook's command, run by a `host` hook; empty for none |
| `env` | variables the hook receives |
| `members_env` | `{name, role, field}` entries; `role: "*"` passes `{role: members}`, an empty `field` passes whole members |
| `skip_unchanged` | whether the timer skips the hook while its inputs are unchanged and its last run is younger than `RBAC_SYNC_REFRESH_SECONDS` |
| `any_slot` | whether the timer runs a swarm hook through a running task of any slot on its node; false or absent runs it only on the node of task slot 1 |
