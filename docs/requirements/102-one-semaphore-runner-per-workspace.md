# 102 - One Semaphore Runner per Workspace

## User Story

As the operator of a platform whose store runs customer deploys through Semaphore, I want every workspace project to run on its own runner that core creates, and every platform project on a runner of its own, so that code in one workspace's inventory can read neither another workspace's runner token, task environment, secrets or state, nor anything of the platform's own deploy.

## Background

The store's requirement 062 (`infinito-nexus/gui: docs/requirements/062-slim-store-orders-provisioned-through-platform-roles.md`, decisions 1, 3 and 15, criteria 062:80 and 062:100-104) needs this core side. Its reason: on a shared runner, code in one workspace's inventory reads the runner token and with it the next job of every project, the platform's own deploy included.

### Today

- One runner row serves every project. The deploy realigns a row with `project_id` NULL, `max_parallel_tasks` 0 and `is_default` TRUE (`roles/web-app-semaphore/templates/sql/project/prepare.sql.j2`) or creates it (its `INSERT`, which the store cites with its values).
- The server hands every task to a runner through `SEMAPHORE_USE_REMOTE_RUNNER=true` (`roles/web-app-semaphore/templates/env.j2`).
- That runner is the service `task-runner` of the Semaphore compose project (`roles/web-app-semaphore/templates/compose.yml.j2`, `roles/web-app-semaphore/meta/services.yml`). It joins the networks of the server (`compose.yml.j2`, the server) and gets the host alias. It reads its token from a file (`roles/web-app-semaphore/vars/main.yml`), runs as the UID of that file (`vars/main.yml`) and keeps its task files under `/tmp/semaphore` (`vars/main.yml`) in a writable container layer.
- It builds on the Infinito.Nexus image of the deploy that last built it (`roles/web-app-semaphore/files/runner/Dockerfile:5`, `vars/main.yml`) and takes its scripts from that image's own core tree (`Dockerfile`).
- It serves both platform projects: app control (`SEMAPHORE_PROJECT_NAME`, `vars/main.yml`) and the foreign-server deploy (`SEMAPHORE_DEPLOY_PROJECT_NAME`, `vars/main.yml`), whose deploy key logs in as `root` (`vars/main.yml`).
- `ansible.cfg` keeps SSH masters alive for 120 s under `~/.ssh` and accepts unknown host keys (`StrictHostKeyChecking=accept-new`).
- The deploy reaches the Semaphore API with a 30-minute admin token it mints by SQL and revokes afterwards (`prepare.sql.j2`, `vars/main.yml`, `roles/web-app-semaphore/tasks/utils/project/converge.yml`). No admin token outlives a deploy.
- [test_runner_isolation.py](../../tests/unit/python/roles/web-app-semaphore/test_runner_isolation.py) already holds the runner to remote execution, a token-only mount, a non-root user and an env file without keys.

So OSS has no API that creates a runner for one project: the store's "API path" (store item 1) does not exist upstream. A runner row with a project is written only by SQL, as core already does. Its container is started only by something with root on the host. Store decision 1 keeps the Docker socket out of the store, so core has to do both.

## Decisions

1. **No global runner.** Every runner row carries a `project_id`. Dispatch falls back to global runners whenever a project's own runner is busy or restarting, so one global runner would catch workspace tasks. The server never runs a task itself: `IsUseRemoteRunner()` stays true. Every template core creates carries a `runner_tag`, which forces a remote job on its own. The replacement of the deprecated flag by `SEMAPHORE_DEFAULT_GLOBAL_RUNNERS_MODE=require` is taken only if the dispatch test below stays green under it, never `disable`. The server holds no `SEMAPHORE_RUNNER_REGISTRATION_TOKEN`.
2. **One runner per platform project.** `runner.project_id` is a single column, so one runner serves one project. Each platform project gets its own runner service in the Semaphore compose project, with its own token, tag and token file. These projects are app control, the foreign-server deploy, the workspace operation (decision 3), provisioning (104) and the export (113). No workspace project runs on any of them. The runner of the workspace operation takes two tasks at once (`max_parallel_tasks` 2), and that project sets no parallel limit, so a `members` task (decision 9) runs beside a `workspace` task.
3. **The workspace operation.** A platform project `<SOFTWARE_NAME> Workspaces` holds one locked template, `workspace`. Its survey variables, all with target `env` (103), are `WORKSPACE` (the workspace id, a lowercase UUID the store chooses, 107 decision 2), `WORKSPACE_ACTION` (`apply` or `destroy`), `WORKSPACE_CORE_VERSION`, `WORKSPACE_TARGETS` (host and port pairs, empty for a workspace without servers; Store ask 15a, operator pick, 2026-11-13 ~21:50) and `WORKSPACE_PLATFORM_TOKENS` (`true` or `false`, required on `apply`: the store's switch for the platform provider tokens, [133](133-provision-secrets-per-template.md)). The task runs core's `workspace.sh` from the runner image, beside `deploy.sh`. It validates every input and deploys the platform inventory limited to the roles that own a per-workspace resource; each such role runs its `tasks/workspace.yml`. Roles that own one: `web-app-semaphore` (this requirement), `web-app-keycloak` (107), `web-app-openbao` (105), `web-svc-seaweedfs` (108), `svc-virt-incus` (109), `web-app-proxmox` (110) and `svc-dns-knot` (104 decision 9). `apply` is idempotent and `destroy` removes what `apply` created, together with the workspace's secrets (105 decision 2), so `destroy` is the one erasure path of a workspace. `workspace.sh` refuses a `WORKSPACE` that is not a lowercase UUID. `apply` creates the Keycloak organization with the workspace marker or finds it by that marker, and fails when the alias `ws-<id>` belongs to an organization without it (107 decision 2); a `destroy` acts only on the organization that carries the marker and does not ask for one to exist. Every step of `destroy` counts a resource that is already gone as removed, and `destroy` deletes the Keycloak organization last (107 decision 10). So a `destroy` that stopped at any step, or whose result the store never received, finishes or succeeds when the store runs it again with the same id (operator pick, 2026-11-13 ~18:15). A task the store saw time out can still sit queued in a workspace project and would run after the erase, so before any role erases, `playbook-workspace.yml` runs the stop of `web-app-semaphore` (`tasks/workspace_stop.yml`) ahead of the role loop, on `destroy` only: it stops every task of the workspace's templates, those of `ws-<id>` and the `<template> ws-<id>` templates of the provision and export projects, whose status is not `success`, `error` or `stopped`, through the stop without `force` (Upstream), and waits until each reports one of those three; the Workspaces project, where the `destroy` itself runs, is never touched. The `destroy` of `web-app-semaphore` repeats the stop before its own first erase, for a task started in between. A task still unfinished 120 seconds after its stop fails `destroy` with a message naming its id, before any role erases, and the next `destroy` stops and counts it again. The workspace runner is removed after the projects, so a running task still reaches the runner that kills it (Store ask 41, parent pick, 2026-11-14). `destroy` prints, as its last output line, `{"destroyed": true, "stopped_tasks": <n>, "workspace": "<id>"}` with sorted keys, where `stopped_tasks` is the number of tasks both stops had to stop, 0 when none was unfinished. `apply` prints, as its last output line, one JSON object with `workspace`, the id, `alias`, `ws-<id>`, `read_key`, the public half of the repository read key ([111](111-gitea-repository-per-workspace.md) decision 4), `project_id`, the Semaphore id of the project `ws-<id>`, and `templates`: an object keyed by template name with one entry for every template the store starts for this workspace, in the Workspaces project (`workspace`, `members` and `user`), in `ws-<id>`, in the provision project (104 decision 10) and in the export project (113). Each entry holds exactly `project_id`, `template_id`, the `repository_id`, `inventory_id` (always set: every template core creates names its inventory, and `apply` fails on a template without one, Store ask 36, robot pick, 2026-11-14) and `environment_id` the template points at, the `git_url`, `git_branch` and `ssh_key_id` of the repository the template runs from, its `runner_tag`, and `environment_variables`, the sorted names of the plain variables and `env` secrets of its environment and never a value, as Semaphore holds them after `apply` (Store ask 21, operator pick, 2026-11-14; `runner_tag`, Store ask 23, and the object keyed by name, Store ask 24, parent picks, 2026-11-14; the three ids and `environment_variables`, Store ask 32, robot pick, 2026-11-14, so the store pins repository, inventory and environment by id and compares the name set instead of resolving them by name). Core keeps the names unique across these projects and fails `apply` on a name held twice. The store pins the project and every template by these ids, never by name, and before each start compares the repository and the runner tag Semaphore reports for the template with the identity `apply` printed, refusing to start on a difference. Core is the only source of that identity, so the store keeps no copy of core's repository settings. The store pins the Workspaces project itself from the OpenBao entry `platform/data/store/semaphore/workspaces`, `{"project_id": N, "templates": {"workspace": E, "members": E, "user": E}}`, each `E` with exactly the keys of an entry of `templates` and built by the same code; its config keeps no project name or runner tag. Core writes that entry on every deploy (`web-app-openbao` `07_workspaces`, after Semaphore, from the fact `semaphore_workspaces_identity` of `roles/web-app-semaphore/tasks/utils/workspaces/identity.yml`), and the store reads it under its read on `platform/data/store/*` and cannot write it (Store ask 26, robot pick, 2026-11-14). 4. **A workspace runner.** `apply` creates one compose project `semaphore-ws-<id>` per workspace:
   - The runner container builds on the Infinito.Nexus image of `WORKSPACE_CORE_VERSION` (`SOFTWARE_IMAGE` and its `v<version>` tag, `group_vars/all/00_general.yml`). It carries the `semaphore` binary of the pinned server (`Dockerfile`) and runs as a UID that no other container on the host uses, with its own passwd entry, because OpenSSH refuses a UID without one.
   - The container runs with a read-only root filesystem. HOME and `SEMAPHORE_TMP_PATH` are `tmpfs` mounts. `SEMAPHORE_RUNNER_ONE_OFF` is true, and the restart policy `unless-stopped` (`group_vars/all/00_general.yml`) starts it again with empty `tmpfs` after every task. It gets `SEMAPHORE_RUNNER_MAX_PARALLEL_TASKS=1` and `SEMAPHORE_RUNNER_TAGS=ws-<id>`. All capabilities are dropped, `no-new-privileges` is set, and it has no host alias and no Docker socket. Its only mount is its token file, `0400` and owned by its UID.
   - The runner row has the workspace project as `project_id`, the tag `ws-<id>`, `max_parallel_tasks` 1 and `is_default` FALSE. An untagged template therefore never runs anywhere.
   - The runner's only network is its own, created `internal`, so it has no route out. Its one other member is the workspace's egress proxy (decision 6).
5. **Nothing survives a task.** Inside a workspace runner the SSH `ControlPath` lies under the task directory that `deploy.sh` removes on exit. `ansible.cfg` pins `ControlPath=~/.ssh/...` and OpenSSH keeps the first value it reads, so `deploy.sh` replaces `ANSIBLE_SSH_ARGS` as a whole. With an empty HOME on every task, `accept-new` would trust every host key anew. A workspace runner therefore runs `StrictHostKeyChecking=yes` against the one host key the task brings, in place of today's `DEPLOY_KNOWN_HOSTS` (`roles/web-app-semaphore/files/shell/repository/deploy.sh`): `deploy`, `update`, `backup` and `restart` each take `HOST` and `HOST_KEY` and write `<HOST> <HOST_KEY>` as the only line of the task's known-hosts file ([103](103-semaphore-pin-task-jwt-and-locked-templates.md) decisions 7 and 8; operator pick, 2026-11-13 ~18:50). `HOST_KEY` has the same `<type> <base64>` form in all four, and the store starts none of them until `workspace apply` has realigned their surveys (103 decision 8).
6. **Egress through an allowlist proxy.** The egress proxy is the only member of the workspace network with a route out. It accepts `CONNECT` to exactly the host and port pairs of the workspace's list and refuses every other target with a log line that names it:
   - the Semaphore server, Gitea and OpenBao, by their canonical names on their front-proxy ports;
   - each pair of `WORKSPACE_TARGETS`. `apply` resolves a target name once and pins the address it got, so a customer's DNS cannot redirect a later connection. A target must be a public address, or lie in `services.semaphore.workspaces.private_targets`, which is empty by default; the dev stack lists its own subnet there for the e2e targets.

   `apply` accepts an empty `WORKSPACE_TARGETS` for a workspace without servers; its list then holds the platform services only, and `deploy`, `update`, `backup` and `restart` refuse every `HOST`, because none is in `WORKSPACE_TARGETS` (103 decisions 7 and 8). A task cannot change its own list. Provider APIs and the state bucket are not on it, because provisioning runs on the platform's provision runner (104). The proxy refuses loopback, link-local (`169.254.0.0/16`, `fe80::/10`) and the host's own addresses even when a listed name resolves to one. The product is the implementation's choice among maintained `CONNECT` proxies with a released, pinned image; Squid is the reference candidate. Rejected: an IP allowlist in nftables alone, because the internal services would then have to join every workspace network or be reached through the host gateway that has to stay closed.
7. **The runner image per core version.** A workspace runner uses the runner image of its `WORKSPACE_CORE_VERSION`, which `apply` builds when it is missing. The value is a version as `lookup('version')` prints it, without the leading `v` (for example `17.0.0`), and core adds the `v` of the image tag itself, as `SOFTWARE_IMAGE_TAG` does (Store ask 16, 2026-11-13). `latest` resolves to the newest released version at `apply` time and is recorded as that version. Any other value that is not a released version, including one with a leading `v`, is refused. The prune of the platform runner (`vars/main.yml`) keeps every image a workspace runner uses. This keeps the store's per-workspace version choice working (store `apps/api/services/runner/args.py:47-58`, default `latest`).
8. **Semaphore admin stays in core (operator pick B, 2026-11-13).** The store's criterion 062:121 gives the store a Semaphore admin token "used only to create projects and runners". Runner creation moves to core (decision 3), but the store would still need admin rights to create projects and the Semaphore users of its members (Background). An admin passes every permission check in every project, so a leaked admin token could edit a template of the deploy project and run it on the deploy runner, whose key logs in as `root` on every host of the platform's deploy inventory. So no long-lived Semaphore admin credential exists outside a single `workspace` or `members` task:
   - `workspace apply` and `members` (decision 9) each mint a short-lived admin token by SQL, as `prepare.sql.j2` does, and delete it before the task ends.
   - With it, `apply` creates the workspace project and makes the store's non-admin service account its `manager` (operator pick, 2026-11-13). The Semaphore users of the organization's members and their project roles come from `members` (decision 9).
   - As `manager`, the store changes the project's templates, keys, inventories, repositories and environments and runs its tasks through the API ([107](107-keycloak-organizations-workspace-roles-and-one-client-per-consumer.md) decision 8). It holds neither `CanManageProjectUsers` nor `CanUpdateProject`, because only `owner` holds those (Upstream). So a leaked store credential can neither give `owner` or `manager` to any Semaphore account nor add a user who is not a member of the organization; as `owner` it could do both, outside Keycloak and outside the role cap of 107 decision 8.

9. **Members follow the Keycloak organization (operator picks, 2026-11-13).** The organization's role groups (107 decision 3) are the only source of a member's Semaphore role, and core is the only writer of the organization (107 decision 7). Semaphore cannot read the groups at login, because claim mapping is a stub in the community edition (Upstream). So the Workspaces project holds a second locked template, `members`, beside `workspace`. Its survey variables, all with target `env` (103), are:
   - `WORKSPACE`, the workspace id of 107 decision 2;
   - `MEMBERS_ACTION`: `sync`, `list`, `add`, `invite`, `uninvite`, `role` or `remove`, whose Keycloak side 107 decision 9 fixes;
   - `WORKSPACE_MEMBER`, a Keycloak user id, for `add`, `role` and `remove` only;
   - `INVITE_KEY`, the lowercase UUID under which the store staged the invitation in OpenBao, for `invite` and `uninvite` only, so no address passes through a survey variable (107 decision 9, Store ask 19);
   - `WORKSPACE_ROLE`, one of `Owner`, `Admin`, `Operator`, `Billing` and `Viewer`, for `role` only; `invite` reads the role from the staged entry (107 decision 9);
   - `WORKSPACE_SUSPENDED`, `true` or `false`, for every action (decision 10).

   It runs core's `members.sh` from the runner image. The script refuses a variable its action does not take and a missing one it needs, calls Keycloak through core's client `workspace-members` (107 decision 7) and Semaphore with its own admin token (decision 8), and runs no playbook.
   - `sync` makes the workspace project's members equal to the organization's role groups, with the roles of 107 decision 8. A member who has no Semaphore user gets an external user without a password, with their Keycloak username and verified email. Semaphore links that user to the member's `sub` at their first OIDC login, because under the default `auto` matching it adopts an unlinked external user whose email equals the verified email of the login (Upstream). A member whose email is not verified gets their role at the first `sync` after their first login. Every action but `list` ends with the same `sync`.
   - `remove` ends one member's organization membership (107 decision 9) and removes their project role in the same task, so revoking a member takes one task.
   - The store starts `members` for every membership change it needs (107 decision 7), and `members sync` when an invitee returns to it after accepting. The store starts `members sync` after every successful `workspace apply`, with its own `WORKSPACE_SUSPENDED` (decision 10), so every write of the organization after its creation runs in a `members` task (107 decision 3). `workspace apply` starts no task itself, because only the store knows whether the workspace is suspended, and a sync with a value core guessed could lift a suspension (Store ask 27, robot pick, 2026-11-14).
   - `members` has parallel tasks off, like every core template (103 decision 3), so its tasks wait only for each other, never for a `workspace` task (Upstream; decision 2). A revocation therefore runs in seconds, while an `apply` of any workspace deploys for minutes.
   - Every action is safe to run again (operator pick, 2026-11-13 ~18:15). `sync` computes the difference between Keycloak and the project and applies only that, so a second `sync` with the same organization changes nothing and succeeds, and a `sync` that stopped midway is finished by the next one. The other actions change nothing when their result already holds, and `remove` of a user who is no longer a member succeeds (107 decision 9). The store waits for each task until its status is `success`, `error` or `stopped` (Upstream); only `success` counts, and it reads the result from the task's last output line (107 decision 9). It runs any action again after `error`, `stopped` or a timeout, except an `error` whose last line is a refusal, which is final (107 decision 9, Store ask 18), and its GDPR erasure resumes from its own journal, which repeats these tasks and `workspace destroy` as often as it needs (store side).

10. **No member task while the store suspends a workspace (Store ask 27, robot pick, 2026-11-14).** Owner, Admin and Operator hold `task_runner` in `ws-<id>` (107 decision 8, store 062 decision 19), so while the store suspends a workspace for non-payment they could start `deploy`, `update` or `restart` themselves and skip the store's dunning gate. So the survey of `members` (decision 9) gains `WORKSPACE_SUSPENDED`, `true` or `false`, with target `env` and required on every run, and the store sets it on every `members` task: `true` while it suspends the workspace, else `false`. While it is `true`, `sync` gives every member whose role groups map to a role of 107 decision 8 `guest`, which starts no task, and names `role=guest` in each change line; a member of no mapped group keeps no role, and the store's account and the Semaphore admins stay untouched, as before. With `false` the roles of 107 decision 8 return. `sync` still applies only the difference, so a second run with the same value changes nothing. `members.sh` refuses a missing value, or one other than `true` and `false`, naming the variable, before any Keycloak or Semaphore call; there is no default. The members sync stays the only writer of member roles in `ws-<id>`: the RBAC hook (`files/sql/rbac/reconcile.sql`) writes project roles only in `<SOFTWARE_NAME>` and `<SOFTWARE_NAME> Deploy`, and `workspace apply` sets only the store's `manager`. Rejected: core's `deploy`, `update` and `restart` refusing a host the store marked suspended, because that needs a marker the store writes and leaves every other template of `ws-<id>`, such as `backup` and `directory`, open.

Rejected:

- Semaphore's project runner API, a Pro stub.
- The store as `owner` of a workspace project, mapping members itself by a username lookup: no new privilege, but a leaked store credential could give any Semaphore account `owner` or `manager`, and Keycloak and Semaphore would drift apart whenever a sync of the store fails halfway. Taking the Keycloak `sub` as Semaphore username would also rename every Semaphore user, the admin login included (`roles/web-app-semaphore/vars/main.yml`).
- A core template per (email, role) pair the store sends: the store's pairs would stay the source of truth, with an admin token minted per pair.
- Member changes as `workspace` actions: a revocation would wait behind every queued `apply` of every workspace, because `workspace` has parallel tasks off (Upstream).
- The global registration token in the store: it registers runners for any project.
- A shared runner with schema-checked inventory: store decision 3.
- A runner manager with the Docker socket in the store: store decision 1.
- A Semaphore admin token in the store (option A): a store compromise would be root on every host of the platform's deploy inventory.
- Semaphore users only from their first OIDC login (option C): a member who never signed in to Semaphore could not be added until they did.
