# 074 - Header-trust backends reachable only through openresty

## User Story

As an operator, I want every application that logs a user in from a proxy-set identity header to be reachable only through openresty, and openresty to clear or overwrite that header on every location, so that no client can impersonate a user, for example with `X-Forwarded-Preferred-Username: administrator`.

Implements [infinito-nexus/core#1089](https://github.com/infinito-nexus/core/issues/1089).

### Backend ports

- [ ] In swarm, no backend port of a header-trust role answers on any node address from outside the swarm. A probe from a host that is not a swarm node gets no TCP connect on `ports.local.<proto>` of each inventoried role.
- [x] In swarm, `container_ports` publishes no `ports.local` port carrying a host ip. The decision runs on the effective mode (`compose_mode_force` or `DEPLOYMENT_MODE`). Edge proxy, mail, TURN and SSH ports stay published. (`plugins/lookup/container_ports.py:252-261`; `tests/unit/python/plugins/lookup/test_container_ports.py:43-91`, where `test_swarm_keeps_public_term_with_ip` pins that a `ports.public` term keeps its ip and fails when the drop ignores `ports.local`.)
- [ ] Host-side provisioning that today reaches an app through its routing-mesh port in swarm (central Postgres and MariaDB init, OpenLDAP, Fider, the Nextcloud integration addons and the other roles listed in #1089) reaches it through container exec or the overlay instead, so the previous criterion holds without a failing deploy.
- [ ] `web-app-litellm` and `web-app-discourse` reach their backends without a published loopback port in swarm.
- [x] A lint fails when a `container_ports` term that passes `DOCKER_BIND_HOST` resolves its published port from `ports.public`. The swarm ingress guard in `roles/svc-swarm-node/templates/nftables.conf.j2` exempts public ports, so such a term would stay open. (`tests/lint/ansible/jinja/test_container_ports_bind_host_uses_local_port.py:55`, green, with its negative control at `:74`.)
- [ ] Once `container_ports` publishes no loopback port in swarm, a lint fails for every swarm-rendered `container_ports` term that carries `DOCKER_BIND_HOST` and no exemption.
- [ ] Production compose (no `DOCKER_IN_CONTAINER`) binds every header-trust backend to `127.0.0.1`. A unit test renders each inventoried role's `compose.yml.j2` with `DOCKER_BIND_HOST=127.0.0.1` and asserts no `0.0.0.0` or bare-port binding.
- [x] The DiD/dev case is decided and documented in [sandbox.md](../contributing/tools/agents/claude/sandbox.md) or the deploy docs. `DOCKER_BIND_HOST` is `0.0.0.0` under `DOCKER_IN_CONTAINER` (`group_vars/all/00_general.yml`) because host-side provisioning reaches apps through `DOCKER_REACH_HOST`, the docker bridge gateway (`roles/sys-svc-container/tasks/00_core.yml`). The outer `compose.yml` publishes no backend port, so the exposure stays inside the outer bridge network. Either a test asserts that `compose.yml` publishes no `ports.local` port, or `DOCKER_BIND_HOST` moves to the bridge gateway. (Decided for the first option and documented in `docs/contributing/actions/deploy.md:85-89`; `tests/lint/ansible/roles/test_header_trust_backends_bind_loopback.py:105,112` pins `127.0.0.1` outside the dev stack and fails when `compose.yml` publishes a `ports.local` port of a header-trust role.)
