# 113 - Workspace Secret Export as a KeePassXC Database

## User Story

As the Owner of a workspace, I want to download my workspace's secrets as a KeePassXC database that only I can open, so that I keep an offline copy of my credentials while neither the store, Semaphore, the platform's backups nor a leaked download link ever holds what opens it.

## Background

The store session proposed this on 2026-11-13 as item 10 of its gap list for the store's requirement 062 (`infinito-nexus/gui: docs/requirements/062-slim-store-orders-provisioned-through-platform-roles.md`). The operator picked the variant with a passphrase sealed to the Owner's public key the same day; decision 3 binds that key to the Owner.

### Today

- A workspace's secrets live under `tenant/data/ws-<id>/` and `tenant/data/ws-<id>-provision/` ([105](105-openbao-task-jwt-auth-transit-tenant-kv-and-store-approle.md) decision 4). The store writes them and cannot read them back (105 decision 6, store criterion 062:120). A task reads them with its own task token (105 decisions 2 and 3).
- The environment and the survey of a workspace template carry no secret value ([103](103-semaphore-pin-task-jwt-and-locked-templates.md) decision 5, line 37).
- A workspace runner holds no provider token, no DNS credential and no S3 identity ([104](104-runner-image-opentofu-and-root-modules.md), isolation criterion, line 127), and it runs code a workspace member can change (104 decision 1).
- Every platform project runs on a runner of its own ([102](102-one-semaphore-runner-per-workspace.md) decision 2). The store starts per-workspace platform templates through the built-in role `guest` and one run grant per template (104 decision 10).
- One backup generation holds Semaphore's database dump, and the inventory holds the key that decrypts the access keys in it ([112](112-backup-set-and-maintenance-signal.md) decision 1).
- The store holds no Keycloak admin role ([107](107-keycloak-organizations-workspace-roles-and-one-client-per-consumer.md) decision 7). It changes the organization's membership only through core's `members` template, whose actions it chooses (107 decision 9, 102 decision 9).
- The platform realm keeps admin events: `adminEventsEnabled` is true and `adminEventsDetailsEnabled` false (`roles/web-app-keycloak/templates/import/realm.json.j2`). They expire after `services.keycloak.events.admin.expiration_days`, 365 by default (`roles/web-app-keycloak/meta/services.yml`, `roles/web-app-keycloak/vars/main.yml`, `realm.json.j2`). Every deploy writes both settings again (`vars/main.yml`).
- No core file creates a KeePassXC database.

## Decisions

1. **A platform project for exports.** `<SOFTWARE_NAME> Export` is a platform project with a runner of its own (102 decision 2). `workspace apply` creates in it one locked template `export ws-<id>` per workspace (103 decision 3), and `destroy` removes it. The export runner has the shape of a workspace runner (102 decisions 4 and 5): read-only root filesystem, `tmpfs` HOME and task directory, one task at a time. Its egress list (102 decision 6) names OpenBao, Keycloak, the S3 endpoint and the platform's mail relay, and nothing else; the runner also reaches the Semaphore server it polls, through the same proxy, as workspace runners do (robot pick, 2026-11-14). The export runs neither on a workspace runner, which holds no S3 identity (104, line 127) and runs code a member can change, nor on the provision runner, which holds unscoped provider tokens the export does not need (104 decision 1).
2. **The store starts it for one Owner.** The survey of `export ws-<id>` holds exactly `WORKSPACE` and `EXPORT_FOR`, the Keycloak user id of the Owner the export is for, both with target `env` (103 decision 4). Neither is a secret, so 103 decision 5 holds. The store's account holds `guest` in the export project and one run grant on each `export ws-<id>`, as 104 decision 10 describes for the provision project.
3. **The recipient comes from the Owner, never from the store (operator pick, 2026-11-13).** An Owner MUST register one age recipient (`age1...`, Upstream) in the attribute `export_recipient` of their own Keycloak profile. The realm's user profile declares it with `edit` for the user only and `view` for admins. The store cannot change it, because it holds no Keycloak admin role (107 decision 7), and no core template writes it. The export task reads `EXPORT_FOR`'s recipient and group membership itself, through a confidential client `export` whose service account holds realm-management `view-users`, `view-organizations` and `view-events` only. It MUST exit non-zero before it reads a secret when `EXPORT_FOR` is not a direct member of the organization's pinned `Owner` group (107 decision 3, decision 8), holds no recipient, or joined that group too recently (decision 8). It takes no recipient from any survey or environment value.
4. **Reading the secrets.** `web-app-openbao` enables a second `jwt` mount, `auth/jwt-export`, on Semaphore's key set with the settings of 105 decision 1. `workspace apply` writes in it the role `ws-<id>`, which binds `project_id` to the export project and `template_id` to `export ws-<id>`, both as JSON numbers, with `bound_audiences` `openbao`, `user_claim` `sub` and `token_policies` `tenant-export` and `export-shared`; `destroy` deletes it. `export-shared` reads `platform/data/export/*`, the export's own platform credentials and the pinned `Owner` groups (decision 8), nothing of `platform/data/provision/*`, which only the per-workspace provision policies of [133](133-provision-secrets-per-template.md) read. The policy `tenant-export` grants `read` on `tenant/data/<role>/*` and `list` on `tenant/metadata/<role>/*`, where `<role>` is the `role` metadata of the `auth/jwt-export` accessor, as 105 decision 3 templates `tenant`. So an export reads exactly `tenant/data/ws-<id>/`: never `ws-<id>-provision/`, which holds platform-managed credentials, never `platform/` and never another workspace. One templated policy serves every workspace, as 105 decides for `tenant`.
5. **The file.** The task writes the secrets as a KeePass XML export into its task directory with mode `0600`. It generates a random passphrase of 32 bytes and runs `keepassxc-cli import --set-password <xml> secrets.kdbx`, with the passphrase twice on standard input (Upstream). It deletes the XML, encrypts the passphrase with `age -r <recipient>` into `passphrase.age`, packs `secrets.kdbx` and `passphrase.age` into one tar, and drops the passphrase. The passphrase and every secret value MUST NOT reach an argument, the environment, a log, the task output or Semaphore's database. The runner image pins one KeePassXC release and one age release and checks their SHA-256 sums, as 104 decision 2 does for OpenTofu.
6. **Delivery.** The deploy creates the platform bucket `exports` in `web-svc-seaweedfs` and the identity `export` with `Read`, `Write` and `List` on it only, without the `WriteAcp` and `Tagging` that consumer identities get (Upstream). Its keys live in `platform/data/export/s3` and the secret of the Keycloak client `export` (decision 3) in `platform/data/export/keycloak`; only `export-shared` reads them (decision 4). The task uploads the tar as `ws-<id>/<task id>.tar`, presigns a `GET` with `X-Amz-Expires` 900, and prints that URL as the last line of its output. The store reads it through `guest` and hands it to the Owner. The scheduled platform template `prune exports` deletes every object older than one hour.
7. **Every export is announced.** Before it uploads, and also when it refuses, the task mails every direct member of the pinned `Owner` group (decision 8) through the platform's mail relay, naming the workspace, the Owner the export is for, the time and, for a refusal, its reason. The store does not send this mail and cannot suppress it.
8. **A minimum Owner age (operator pick, 2026-11-13).** The store chooses the actions of `members`, so a leaked store credential could invite an account of its own, give it `Owner` through `members role` and export to that account's recipient. Three core controls bound this:
   - **The Owner group is pinned.** Any holder of `manage` on the organization renames, deletes and nests its groups (`deleteGroup` and `updateGroup` in [OrganizationGroupResource.java:126-168](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/organization/admin/resource/OrganizationGroupResource.java#L126-L168), `addSubGroup` at [:230-249](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/organization/admin/resource/OrganizationGroupResource.java#L230-L249)). The store holds no such right since 107 decision 7, but a Keycloak admin does, so the name `Owner` proves nothing. `workspace apply` writes the id of the `Owner` group it created (107 decision 3) to `platform/data/export/owners/ws-<id>` as `group`, and `destroy` deletes it. The store cannot write there (105 decision 6). Decisions 3, 7 and 8 count only direct members of that group id, never a group found by name and never a subgroup member.
   - **The age gate.** `services.semaphore.workspaces.export.owner_min_age_days` in `roles/web-app-semaphore/meta/services.yml` defaults to `7`. The task reads the newest admin event of type `ORGANIZATION_GROUP_MEMBERSHIP` whose resource path is `organizations/<org>/groups/<pinned group>/members/<EXPORT_FOR>`, with `<org>` the Keycloak id of the organization that carries the marker of workspace `<id>` (107 decision 2, Upstream), and refuses when that event is a `CREATE` younger than the parameter. With no such event in the kept window, the membership is older than the window. That holds because the realm keeps admin events on every deploy (Today), and the store can neither delete them nor turn them off: both need `manage-events` (Upstream, `updateRealmEventsConfig` in [RealmAdminResource.java:871-875](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/services/resources/admin/RealmAdminResource.java#L871-L875)), and the store holds no Keycloak admin role, while the client `workspace-members` that its `members` tasks use holds no `manage-events` (107 decision 7). The deploy MUST fail when the parameter is below 2 or not below `services.keycloak.events.admin.expiration_days`, because a missing event then no longer proves the age.
   - **The announcement of new Owners.** The scheduled platform template `announce owners` in the export project runs once a day. Its tasks log in through `auth/jwt-export` with the role `announce-owners`, which the deploy binds to the export project and that template, with the policy `export-shared` only; `export-shared` also lists `platform/metadata/export/owners/`. For each pinned group, it mails every direct member about every Owner whose newest membership event on that group is a `CREATE` younger than the parameter, naming the new Owner, the join time and the first day an export for them is possible. It keeps no state, so a missed run is caught by the next one, and the store cannot suppress it.

   The default of 7 days spans a weekend and a short absence: the first daily announcement reaches the other Owners within a day of the join, and they have the remaining days to remove the account before an export for it is possible. The minimum of 2 keeps at least one announcement ahead of the first possible export. A legitimate new Owner waits a week for their first export, and an operator who wants a longer window raises the parameter up to the event retention.

What a leaked store credential reaches here: it can start an export for any Owner of any workspace, and the file opens only with that Owner's age identity. An account it makes Owner can export only after the age window, and every Owner is mailed daily about that account until the window ends.

Rejected:

- The store forwarding the Owner's public key as a survey value: a leaked store credential could export any workspace to a key of its own and read every tenant secret, which 105 decision 6 and store criterion 062:120 exclude.
- The Owner typing a passphrase as a secret survey value: it would need an exception to 103 decision 5, and Semaphore keeps the value in its database until the task ends (Upstream), so every dump taken meanwhile holds it (112 decision 1).
- The export on a workspace runner or on the provision runner: decision 1.
- `tenant/data/ws-<id>-provision/` in the export: it holds the platform-managed DNS and S3 credentials of the workspace, not the customer's own secrets.
- A presigned link valid for days: SigV4 allows up to seven (Upstream), and a leaked link would stay usable that long.
- The export announcement alone, without the age gate: it reports an export by an account the store made Owner only after the secrets are gone.
- The `Owner` group found by its name, or with its subgroups: a Keycloak admin renames groups and adds subgroups (decision 8).
- An announcement that remembers what it already sent: a lost or missed run would drop a join for good, while a stateless daily run repeats it.
- The Owner starting the export in Semaphore and the task checking the token's `user_id`: the store still decides who is an Owner, so this adds no control over a leaked store credential.
