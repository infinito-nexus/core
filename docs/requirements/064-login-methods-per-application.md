# 064 - Login Methods per Application

## User Story

As a platform operator, I want the sign-in page of every application to offer only the login methods its deployment mode allows, each switchable on its own in `meta/services.yml`, so that users see one way to sign in (the SSO button whenever Keycloak runs) and no side door bypasses the central identity.

## Decisions (operator-confirmed 2026-10-30; do not re-litigate)

1. **Schema.** Every role whose sign-in offers more than one method in any mode declares `services.<entity>.login.method.<method>.enabled` under its own entity in `meta/services.yml`. The methods are `sso`, `ldap`, `native` and `2fa`, plus the extras an app actually has: `passkey`, `openid2` (Gitea), `odoo_com` (Odoo), `email` (Fider magic link) and `registration` (local self-registration).
2. **Defaults by mode.** `sso` means `web-app-keycloak` in `group_names`, `ldap` means `svc-db-openldap` in `group_names`.

   | Mode | sso | ldap | native | 2fa | extras and registration |
   |---|---|---|---|---|---|
   | SSO on | true | false | false | false (Keycloak is the only second factor and enforces it) | false |
   | SSO off, LDAP on | false | true | false | true (enforced where the app can) | false |
   | SSO off, LDAP off (native) | false | false | true | true (enforced where the app can) | false |

   The inventory may override any flag.
3. **2FA is enforced unless switched off (operator decision 2026-11-06; supersedes the 2026-10-30 offer-only rule).** An account without a second factor enrolls one at its next sign-in before it gets in.
   - With Keycloak enabled as a service of the app (`services.sso.enabled`), Keycloak is by default the only second factor: the realm enforces TOTP enrollment through `services.keycloak.realm.totp_enforced` of `web-app-keycloak` (default `true`), and the app's own `2fa` is off.
   - Without Keycloak, the app's own second factor is on and enforced through `services.<entity>.login.method.2fa.enforced` (default `true`) wherever the app can enforce it; the research table below lists which apps can.
   - The app's `meta/services.yml`, like the inventory, may override either default: `login.method.2fa.enabled: true` runs the app's own second factor beside Keycloak, and `login.method.2fa.enforced: false` only offers it. Keycloak's enforcement is realm-wide, so `totp_enforced: false` switches it off for every app of the realm at once, as every Keycloak variant and the development inventory do for automated logins.
4. **Shared form.** Where one form serves local and LDAP accounts (Gitea, Open WebUI, Matrix, MinIO, Semaphore, Zammad, Odoo), the LDAP mode keeps the form for LDAP, and `native: false` means no local account signs in except the break-glass admin wherever the app can tell the two apart; where it cannot, the role README states that the form is shared.
5. **Hiding.** A disabled method is switched off through the app's own setting where one exists, otherwise hidden by role-injected CSS or JavaScript through the role's `javascript` service. Every app keeps a documented break-glass path for its local admin (URL parameter, recovery account, CLI or token).
6. **Gitea OpenID 2.0.** `[openid] ENABLE_OPENID_SIGNIN` and `ENABLE_OPENID_SIGNUP` enable OpenID 2.0, not the OIDC source, and follow `login.method.openid2.enabled`.

## Rollout notice (2026-11-07)

App-native enforcement applies only where the app's own `2fa` is on, which means production inventories in the LDAP or native mode; every SSO deployment, CI and the development inventory are unaffected. In those inventories the first deploy after this change has these effects:

- Discourse, GitLab, Joomla, Matomo, Nextcloud, pgAdmin, pretix and Zammad send every human account without a second factor to enrollment at its next sign-in, the platform administrator included. EspoCRM does so for regular users only: `auth2FAForced` spares administrators and portal users. Weblate sends nobody to enrollment: it shows its enrollment banner to every account without a second factor in a flagged team and withholds that team's permissions and every permission on a flagged project, edits included for a superuser.
- ERPNext does the same only while `web-app-email` is deployed, because Frappe mails the first OTP setup link. Without mail the deploy holds the enforcement and prints why. Break-glass for a locked-out Administrator: `bench --site <site> execute frappe.db.set_value --args "['Role', 'All', 'two_factor_auth', 0]"`.
- Odoo enforces only while `web-app-email` is deployed and `ir.mail_server` opens an SMTP session at the deploy: `auth_totp_mail` mails a sign-in code to every account without an authenticator app, and password XML-RPC needs an API key from then on. Break-glass: `odoo shell -d <database>`, then `env['ir.config_parameter'].set_param('auth_totp.policy', False); env.cr.commit()`.
- Turning an app's own `2fa` off, or `enforced: false`, after the deploy enforced it clears that enforcement by one of two rules. Where the app's second factor stays usable, the deploy clears only what an ownership marker says it switched on itself: Matomo on `enforced: false` (option `InfinitoTwoFactorAuthRequiredByDeploy`, set only when the deploy switches `twoFactorAuthRequired` on), Moodle on `enforced: false` (`local_mfaenforce/grace_by_deploy`, set only when the deploy switches `factor_grace` on), Nextcloud (`occ config:app:get infinito twofactor_enforced_by_deploy`, and only while `occ` reports exactly "enforced for all users"), Odoo (`ir.config_parameter` `infinito.auth_totp_policy_by_deploy`, which also keeps the policy the deploy replaced and restores it) and Weblate on `enforced: false` and on `2fa` off (`/app/data/infinito/enforced_2fa.json` lists the teams and projects the deploy flagged; an enrolled second factor stays usable while `2fa` is off, which only hides the enrollment entries); an enforcement an admin set stays. Where turning `2fa` off leaves no usable second factor, the deploy clears any enforcement, also one an admin set: Discourse (no local logins, so second-factor setup answers NotFound), EspoCRM, ERPNext, Gitea (with `passkey` also off), Joomla once no `multifactorauth` plugin is enabled any more, Matomo (`2fa` off deactivates TwoFactorAuth), Moodle (`2fa` off turns `tool_mfa` off, and the deploy switches `factor_grace` off), Nextcloud while no provider app is enabled, and Zammad, where the enforcement would be dormant until a method comes back. Joomla break-glass for a forced list without an enabled method: the SQL in its README on `<prefix>extensions.params`.
- An Odoo SMTP probe that fails at a later deploy, by any error or without a session, keeps a policy the deploy already owns and only refuses to switch a new one on; the deploy names the failure in a notice. ERPNext's hold checks only that `web-app-email` is deployed, not that its outgoing Email Account delivers, and Frappe v16 exempts no account: keep its break-glass above at hand.
- Nextcloud refuses the login password on WebDAV, CalDAV, CardDAV and OCS once enforcement is on. Desktop, mobile and calendar clients need an app password.
- GitLab refuses the account password for Git over HTTPS and the container registry once enforcement is on. Clients need a personal access token.
- Moodle sends every account without a factor to setup at its first sign-in, the platform administrator included (operator decisions 2026-11-07 and 2026-11-12). The role's `local_mfaenforce` plugin, built into the image, starts the `factor_grace` period of every sign-in as already expired, and `forcesetup` turns the expired period into the setup page. `enforced: false` switches the plugin off, so later sign-ins keep their period again, and switches `factor_grace` off only where the deploy switched it on; its web-service tokens, the MCP token included, are not affected.
- Gitea keeps `enforced: false` by default, because enforcement would cut off the MCP account the deploy provisions.
- Weblate converges its flags at every deploy and every hour from a Celery beat task, so a project or team created between deploys is flagged within the hour. Teams a project defines stay unflagged: a flagged team drops its permissions for every member without a second factor, bots included (upstream weblate 2026.9 `weblate/auth/models.py`, `User._permissions`), so it would cut the project's API tokens, while the project's own `enforced_2fa` covers its human members and spares bots (`weblate/auth/permissions.py:239-241`, `check_enforced_2fa`). The deploy's own calls keep working: the management shell bypasses permissions, and the gateway's token belongs to a superuser and only reads (`check_permission` returns early for a superuser, `weblate/auth/permissions.py:300`).
- Matomo keeps the deploy's `token_auth` calls under enforcement, because TwoFactorAuth exempts a request authenticated by a token alone. `UsersManager.createAppSpecificTokenAuth` refuses an account without a second factor, so the deploy mints the token of an existing install without a stored one inside the container (`roles/web-app-matomo/files/php/mint_token_auth.php`).
- `login.method.2fa.enforced: false` in the inventory restores the offer-only behaviour per app.
- The first production deploy with the enforced default runs only after the IAM live run has proven the enrollment criterion below (a local account without a second factor is sent to enrollment before it gets in, per role in its native variant).

## Acceptance Criteria

### Schema and lint

- [ ] Every role whose sign-in page offers more than one method in any mode declares `login.method.<method>.enabled` under its entity for every method the app offers, and declares no method the app lacks.
- [x] A lint fails when a role's default for any declared method deviates from the mode table, and it fails on a negative control.
- [x] A lint fails when a role in scope lacks the `login.method` block, and it fails on a negative control.
- [x] An inventory override of a single method flag reaches the rendered app configuration, proven by a unit test per switch kind (environment, config file, database setting, injected CSS or JavaScript).
- [x] The existing role-local switches (`discourse.local_login_enabled`, `nextcloud.legacy_login_mask`, `PENPOT_NATIVE_LOGIN_ENABLED`, `MEDIAWIKI_LOCAL_PASSWORD_LOGIN`, `OPENBAO_USERPASS_ENABLED`, `MOBILIZON_INSTANCE_DISABLE_DATABASE_LOGIN`, Taiga's `defaultLoginEnabled`, the Listmonk login script) derive from `login.method.*` and keep no second source.

### SSO mode

- [ ] With SSO on, the sign-in page of every role in scope shows only the SSO entry: no password form, passkey, OpenID 2.0, third-party, magic-link or registration entry, proven by a Playwright assertion in each role's spec.
- [ ] With SSO on, an LDAP account signs in through Keycloak's LDAP federation in every role whose LDAP spec ran with SSO on before (Penpot, Open WebUI, Semaphore, MinIO, Gitea, Discourse), and those native LDAP specs are gated to SSO off.
- [ ] Gitea shows no "Sign in with OpenID" entry in any mode, and Odoo shows no "Sign in with Odoo.com" entry and no passkey entry in any mode.

### LDAP and native modes

- [ ] With SSO off and LDAP on, every role with a native LDAP path signs an LDAP account in through its form, and shows no registration, passkey or third-party entry.
- [ ] With SSO off and LDAP on, a local account other than the break-glass admin cannot sign in wherever the app separates local from LDAP accounts, and the README of every other shared-form role says so.
- [ ] With SSO and LDAP off, every role signs a local account in through its form, and its own second factor is on wherever the app has one.
