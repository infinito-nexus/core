# 135 - OpenTofu Sandbox per Run

## User Story

As the operator of the Infinito.Nexus platform, I want every OpenTofu run on the provision runner to run in a sandbox of its own, so that code execution in OpenTofu or a provider plugin of one run reaches neither the runner token nor the credentials, files or processes of any other run, whichever workspace that run serves.

## Context (2026-11-20)

- The templates `provision-<provider> ws-<id>`, `destroy-<provider> ws-<id>`, `unlock ws-<id>`, `dns ws-<id>` and `zone ws-<id>` of every workspace run on the one platform provision runner ([104](104-runner-image-opentofu-and-root-modules.md) decision 1, [133](133-provision-secrets-per-template.md)), never on a workspace runner. Its runner row has `max_parallel_tasks` 0 (`SEMAPHORE_PLATFORM_RUNNERS` in `roles/web-app-semaphore/vars/main.yml`), and its env (`roles/web-app-semaphore/templates/env/task-runner.j2`) sets neither `SEMAPHORE_RUNNER_MAX_PARALLEL_TASKS` nor `SEMAPHORE_RUNNER_ONE_OFF`, so it runs the tasks of many workspaces at once and outlives each of them.
- Every process of that container runs as uid 64101, the `USER` of `roles/web-app-semaphore/files/runner/Dockerfile`. Its token `semaphore_provision_runner_token` (`roles/web-app-semaphore/meta/volumes.yml`) is mounted `0400` for that uid at `/run/secrets/semaphore-runner-token`, and `/tmp` and `/tmp/semaphore` are `tmpfs` of mode `1777` that every task shares. Unlike the export runner, it drops no capability and sets neither `read_only` nor `no-new-privileges` (`roles/web-app-semaphore/templates/compose.yml.j2`).
- `Session.run` (`roles/web-app-semaphore/files/python/provision/session.py`) is the only caller of `tofu` in `roles/web-app-semaphore/files/python/provision/opentofu.py`, which starts `roles/web-app-semaphore/files/python/tofu_supervisor.py` and through it `tofu` in a new process group. That environment holds the provider credential of the line, a platform account token among them, the zone's DNS credential, `BAO_TOKEN` (the `ws-<id>-transit` child of 133) and `TF_ENCRYPTION`. The run's task directory comes from `tempfile.mkdtemp` under `/tmp` and holds the backend file with the keys of the workspace's state bucket and the credential files of `provider_env.private_file`; `task_lock` keeps the locks between runs in `/tmp/provision-locks` (`roles/web-app-semaphore/files/python/provision.py`).
- So code that runs in OpenTofu or a provider plugin, through a compromised provider release or a provider bug that an API answer triggers, reads as uid 64101: `/proc/<pid>/environ` of `tofu` and the plugins of every concurrent run, with another workspace's provider token, DNS credential and transit child; their task directories with the state bucket keys; Semaphore's task directories under `/tmp/semaphore`; and the runner token, with which it acts as the runner toward the server and receives the jobs of later provision tasks, task tokens included.
- A process that starts its own session leaves the process group that `_killed` in `opentofu.py` kills, so a plugin can outlive its run on the long-lived runner and read the runs after it too.
- `prctl(PR_SET_DUMPABLE, 0)` of 133 closes `provision.py` alone; 133 lists this gap under Known Gaps.

## Decisions

1. **Own requirement after 133. Decided** by the operator (hub card `fc7a589c6a0c32a7`, 2026-11-20). 133 lands first and stays as it is: the per-template roles, the transit child, the descriptor hand-over and the undumpable `provision.py`. This requirement adds the sandbox around OpenTofu and changes none of them.
2. **One sandbox per run around the OpenTofu process tree. Decided** with decision 1, because `opentofu.tofu` is the one spawn point. Every OpenTofu call of a run MUST start inside that run's sandbox; `provision.py`, the wrappers and the Semaphore runner stay outside it as uid 64101. The sandbox MUST make reachable only the run's task directory (read-write), the image's `tofu`, provider mirror and CLI configuration, the system libraries and CA store (read-only), and a temporary directory and `HOME` of its own; its environment is exactly `Session.environment`. It MUST hide the runner token, `/tmp/semaphore`, the lock directory, every other task directory, and the environment, memory, descriptors and working directory of every process outside it, and it can create nothing outside its task and temporary directory. When `opentofu.tofu` returns or raises, no process of the sandbox lives, one that left the process group included, and once the run ends its task directory is gone.
3. **Mechanism. Decided: B** by the operator (hub card `52dc334746c10720`, 2026-11-20). The options were:
   - A. `bwrap` in an unprivileged user namespace: own PID, mount and IPC namespaces, a private `/proc` and `/tmp`, only the paths of decision 2 bound in, `--die-with-parent`. It hides even the process list. It needs a seccomp profile on the provision runner that allows `unshare` and the namespace flags of `clone`, which Docker's default profile refuses without `CAP_SYS_ADMIN`, an AppArmor profile that allows its mounts, a host kernel that allows unprivileged user namespaces, and all of that in swarm mode too, which the provision runner enables (`roles/web-app-semaphore/meta/services.yml`). The image gains `bwrap` (104).
   - B. A uid of its own per run: the provision runner alone starts as root; a spawner drops the Semaphore runner to 64101, keeps at most `CAP_SETUID`, `CAP_SETGID` and `CAP_CHOWN`, and on request of `opentofu.tofu`, over a socket only uid 64101 reaches, starts the run's OpenTofu with `setpriv` under a uid from a range disjoint from 64101 and from the workspace runner UIDs, which count up from `SEMAPHORE_WORKSPACE_UID_BASE`. The kernel then refuses another uid's `environ`, `mem` and `fd`, mode `0400` keeps the token closed, and `/tmp` becomes a `0700` `tmpfs` of 64101 as on the workspace runners (`roles/web-app-semaphore/templates/workspace/compose.yml.j2`). `/proc` still lists every process with its command line, which carries no credential (104 decision 11). It keeps Docker's default seccomp profile and lets the container add `cap_drop: ALL` and `no-new-privileges`.
   - C. Both: B's uid inside A's namespaces, at the cost of both.

   Why B: it closes every read of the Context on the default seccomp profile, works alike in compose and swarm mode, and hardens the container beyond its present settings; A loosens the kernel surface of every process in the container to hide a process list that holds no credential.
4. **Concurrency on the provision runner. Decided: A** by the operator (hub card `e0d4eb3d201c2054`, 2026-11-20). The options were:
   - A. Runs stay parallel (`max_parallel_tasks` 0), one sandbox each.
   - B. One task at a time on top of the sandbox: row and env at 1 with `SEMAPHORE_RUNNER_ONE_OFF`, as the workspace runners ([102](102-one-semaphore-runner-per-workspace.md) decision 4).
   - C. A provision runner per workspace, tagged `provision-ws-<id>`.

   Why A: a run may take up to `RUN_BUDGET`, 2 h (`roles/web-app-semaphore/files/python/provision/provider_env.py`), so B holds every workspace's provision, destroy, unlock, dns and zone tasks behind one run for that long, and a one-off runner still leaves its token to a plugin without the sandbox. C needs the sandbox as well, adds one idle container per workspace and changes 104 decision 1 and 102 decision 2.
5. **Network unchanged. Decided** by the scope of the card. The sandbox keeps the runner's network, because OpenTofu needs the provider APIs, OpenBao and the state endpoint. The egress list that 104 decision 1 gives the provision runner is not in place (`compose.yml.j2` puts it on the role's default networks with the host alias); that gap stays with 104.

## Acceptance Criteria

- [ ] Every OpenTofu call starts inside the run's sandbox, and no module under `roles/web-app-semaphore/files/python` starts `tofu` another way (`test_every_tofu_call_runs_in_the_run_sandbox` in `tests/unit/python/roles/web-app-semaphore/files/provision/test_opentofu.py`; control `test_negative_control_a_direct_tofu_spawn_is_caught` plants a bare `subprocess.Popen(["tofu", ...])` in `session.py`).
- [ ] The sandbox a run gets makes reachable exactly the paths of decision 2 and passes `Session.environment` unchanged; one negative control each makes `/run/secrets`, `/tmp/semaphore`, the lock directory or a second task directory reachable, or adds a variable, and must fail (`test_the_sandbox_shows_a_run_its_own_files_only` and its `test_negative_control_*` in `tests/unit/python/roles/web-app-semaphore/files/provision/test_sandbox.py`).
- [ ] Two runs that overlap in time never share a sandbox, and a uid returns to its range only once no process holds it and no file of its run is left (`test_overlapping_runs_never_share_a_sandbox`, control `test_negative_control_a_uid_released_while_held_is_reused`, in `test_sandbox.py`).
- [ ] A child that a fake `tofu` starts in a new session is gone when `opentofu.tofu` returns, raises or the run budget ends, and the run's task directory is gone after the run; the control with the process-group kill alone finds the child alive (`test_no_process_of_a_sandbox_outlives_its_call`, `test_the_task_directory_is_gone_after_the_run` and control `test_negative_control_a_new_session_escapes_the_group_kill` in `test_sandbox.py`).
- [ ] Live, after the provision runner starts, the deploy runs two sandboxes in it at once, each with the probe `sandbox_probe.py` in place of `tofu` and a random marker in its environment, and fails when a probe opens the runner token, reads `environ`, `mem`, `fd` or `cwd` of any process outside its own sandbox, finds the other probe's marker or task directory, reads `/tmp/semaphore` or the lock directory, creates a file outside its task and temporary directory, or leaves a child of a new session alive. The same probe run once outside any sandbox must report the token, the other marker and the surviving child, else the check fails as blind (`🛡️ Assert the OpenTofu sandbox holds` in `roles/web-app-semaphore/tasks/utils/provision/sandbox.yml`; verdict logic `test_the_sandbox_check_fails_on_every_read_a_probe_reports`, control `test_negative_control_a_blind_probe_fails_the_check`, in `tests/unit/python/roles/web-app-semaphore/test_provision_sandbox_check.py`; live: a green IAM roundtrip deploy in compose and in swarm mode).
- [ ] Live, two `provision` tasks of two workspaces started together each create their server and end with the outputs line, and their `destroy` tasks leave neither server nor record (`provision: two workspaces provision at once, each in its own sandbox` in `roles/web-app-semaphore/files/playwright/test-provision.js`, against the Incus e2e target of [109](109-incus-api-listener-and-project-per-workspace.md)).
- [ ] The provision runner's service carries what decision 3 B needs and nothing more, in compose and swarm mode: `cap_drop: ALL`, `cap_add` within `CAP_SETUID`, `CAP_SETGID` and `CAP_CHOWN`, `no-new-privileges` and a `0700` `/tmp` of uid 64101, with Docker's default seccomp profile, while every other runner still starts as uid 64101. One negative control per property (`test_the_provision_runner_grants_the_sandbox_only_what_it_needs` and its controls in `tests/unit/python/roles/web-app-semaphore/test_runner_isolation.py`).
- [ ] The runner image carries the sandbox entry point of decision 3 B, the spawner and `setpriv`, and a build without it fails (`test_the_runner_image_carries_the_sandbox_entry_point` in `tests/unit/python/roles/web-app-semaphore/test_runner_build.py`, with a planted Dockerfile without it as control).
- [ ] `roles/web-app-semaphore/README.md` describes the sandbox of a run: what it reaches and hides, its identity per run, the container settings and the residuals of a uid per run, such as the visible process list; the Known Gaps entry of 133 gives way to a link to this requirement.

## Test Plan

- Unit, without privileges: criteria 1 to 4, 7 and 8 test the plan the code builds, the one spawn point and the service and image settings, and each negative control plants the regression it names and must fail.
- Deploy self-check: criterion 5 runs on every deploy of the provision runner, so the IAM roundtrip proves the isolation itself in compose and swarm mode.
- End to end: criterion 6 in `test-provision.js` proves that OpenTofu still provisions and destroys inside the sandbox.
