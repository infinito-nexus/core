# 135 - OpenTofu Sandbox per Run

## User Story

As the operator of the Infinito.Nexus platform, I want every OpenTofu run on the provision runner to run in a sandbox of its own, so that code execution in OpenTofu or a provider plugin of one run reaches neither the runner token nor the credentials, files or processes of any other run, whichever workspace that run serves.

## Context (2026-11-20)

- The templates `provision-<provider> ws-<id>`, `destroy-<provider> ws-<id>`, `unlock ws-<id>`, `dns ws-<id>` and `zone ws-<id>` of every workspace run on the one platform provision runner ([104](104-runner-image-opentofu-and-root-modules.md) decision 1, [133](133-provision-secrets-per-template.md)), never on a workspace runner. Its runner row has `max_parallel_tasks` 0 (`SEMAPHORE_PLATFORM_RUNNERS` in `roles/web-app-semaphore/vars/main.yml`), and its env (`roles/web-app-semaphore/templates/env/task-runner.j2`) sets neither `SEMAPHORE_RUNNER_MAX_PARALLEL_TASKS` nor `SEMAPHORE_RUNNER_ONE_OFF`, so it runs the tasks of many workspaces at once and outlives each of them.
- Every process of that container runs as uid 64101, the `USER` of `roles/web-app-semaphore/files/runner/Dockerfile`. Its token `semaphore_provision_runner_token` (`roles/web-app-semaphore/meta/volumes.yml`) is mounted `0400` for that uid at `/run/secrets/semaphore-runner-token`, and `/tmp` and `/tmp/semaphore` are `tmpfs` of mode `1777` that every task shares. Unlike the export runner, it drops no capability and sets neither `read_only` nor `no-new-privileges` (`roles/web-app-semaphore/templates/compose.yml.j2`).
- `Session.run` (`roles/web-app-semaphore/files/python/provision/session.py`) is the only caller of `tofu` in `roles/web-app-semaphore/files/python/provision/opentofu.py`, which starts `tofu` in a new process group. That environment holds the provider credential of the line, a platform account token among them, the zone's DNS credential, `BAO_TOKEN` (the `ws-<id>-transit` child of 133) and `TF_ENCRYPTION`. Each run keeps its task directory under the shared `/tmp`, holding the backend file with the keys of the workspace's state bucket and the provider's credential files; `task_lock` keeps the locks between runs in `/tmp/provision-locks` (`roles/web-app-semaphore/files/python/provision.py`).
- So code that runs in OpenTofu or a provider plugin, through a compromised provider release or a provider bug that an API answer triggers, reads as uid 64101: `/proc/<pid>/environ` of `tofu` and the plugins of every concurrent run, with another workspace's provider token, DNS credential and transit child; their task directories with the state bucket keys; Semaphore's task directories under `/tmp/semaphore`; and the runner token, with which it acts as the runner toward the server and receives the jobs of later provision tasks, task tokens included.
- A process that starts its own session leaves the process group that `_killed` in `opentofu.py` kills, so a plugin can outlive its run on the long-lived runner and read the runs after it too.
- `prctl(PR_SET_DUMPABLE, 0)` of 133 closes `provision.py` alone; 133 lists this gap under Known Gaps.

## Decisions

1. **Own requirement after 133. Decided** by the operator (hub card `fc7a589c6a0c32a7`, 2026-11-20). 133 lands first and stays as it is: the per-template roles, the transit child, the descriptor hand-over and the undumpable `provision.py`. This requirement adds the sandbox around OpenTofu and changes none of them.
2. **One sandbox per run around the OpenTofu process tree. Decided** with decision 1, because `opentofu.tofu` is the one spawn point. Every OpenTofu call of a run MUST start inside that run's sandbox; `provision.py`, the wrappers and the Semaphore runner stay outside it as uid 64101. The sandbox MUST make reachable only the run's task directory (read-write), the image's `tofu`, provider mirror and CLI configuration, the system libraries and CA store (read-only), and a temporary directory and `HOME` of its own; its environment is `Session.environment` with the spawner's own `PATH`. It MUST hide the runner token, `/tmp/semaphore`, the lock directory, every other task directory, and the environment, memory, descriptors and working directory of every process outside it, and it can create nothing outside its task and temporary directory. When `opentofu.tofu` returns or raises, no process of the sandbox lives, one that left the process group included, and once the run ends its task directory is gone. Task directories leave `/tmp`, which becomes a `0700` directory of 64101: each run gets `/run/provision/<uid>/task` (owner 64101, group `<uid>`, mode `2770`, without the sticky bit, so `tofu init` may replace the `.terraform.lock.hcl` 64101 staged) and `/run/provision/<uid>/home` (`<uid>`, `0700`) on a `0711` tmpfs of root at `/run/provision`, a mount that grants nothing. Before the run's first OpenTofu call `provision.py` stages its files into the fresh task directory with `shutil.copytree` and `shutil.copy2`, while no process of the sandbox has run there; from that call on, 64101 writes into a task directory only through `sandbox.task_write`, which refuses `..`, walks it by directory descriptors with `O_NOFOLLOW` and creates each file with `O_CREAT|O_EXCL`, so a link the sandbox plants never redirects a write. The spawner starts nothing but the image's `tofu` (or the probe of criterion 5) with only the commands and flags of `opentofu.COMMANDS`, `-backend-config=` and `-var-file=` in their file form only, naming a file below the task directory without `..` that the exec helper, as the sandbox uid, finds behind no link (root may not search the `2770` directory), and only the variable names `provision` passes, none with a line break or NUL: `PATH` its own, `TF_CLI_CONFIG_FILE`, `BAO_ADDR`, the proxy, locale and `SSL_*` names pinned to the layout, `BAO_CACERT` pinned to `SEMAPHORE_SANDBOX_CA` and refused while that is empty, as it is unless `TLS_MODE` is `self_signed`, `TF_ENCRYPTION` only as `session.encryption` writes it, `HOME` and `TMPDIR` only the run's home, credential file names only below the task directory, endpoints no local path; any other value, a secret included, passes as it is. That allowlist protects the spawner, other runs and the host, not a run against its own root module: `64101` stages the module and its `local-exec` runs inside the sandbox by design. A sandbox's System V IPC objects end with its uid as its files do, and a uid returns to use only when it owns no entry the spawner's walk reaches; the spawner refuses to start while every uid may pass a directory it cannot list.
3. **Mechanism. Decided: B** by the operator (hub card `52dc334746c10720`, 2026-11-20). The options were:
   - A. `bwrap` in an unprivileged user namespace: own PID, mount and IPC namespaces, a private `/proc` and `/tmp`, only the paths of decision 2 bound in, `--die-with-parent`. It hides even the process list. It needs a seccomp profile on the provision runner that allows `unshare` and the namespace flags of `clone`, which Docker's default profile refuses without `CAP_SYS_ADMIN`, an AppArmor profile that allows its mounts, a host kernel that allows unprivileged user namespaces, and all of that in swarm mode too, which the provision runner enables (`roles/web-app-semaphore/meta/services.yml`). The image gains `bwrap` (104).
   - B. A uid of its own per run: the provision runner alone starts as root; a spawner drops the Semaphore runner to 64101, keeps at most `CAP_SETUID`, `CAP_SETGID` and `CAP_CHOWN`, and on request of `opentofu.tofu`, over a socket only uid 64101 reaches, starts the run's OpenTofu with `setpriv` under a uid from a range disjoint from 64101 and from the workspace runner UIDs, which count up from `SEMAPHORE_WORKSPACE_UID_BASE`. The kernel then refuses another uid's `environ`, `mem` and `fd`, mode `0400` keeps the token closed, and `/tmp` becomes a `0700` `tmpfs` of 64101 as on the workspace runners (`roles/web-app-semaphore/templates/workspace/compose.yml.j2`). `/proc` still lists every process with its command line, which carries no credential (104 decision 11). It keeps Docker's default seccomp profile and lets the container add `cap_drop: ALL` and `no-new-privileges`. `docker stack deploy` drops `security_opt`, so in swarm mode the service sets no `no-new-privileges`; the spawner therefore sets `PR_SET_NO_NEW_PRIVS` on itself with `prctl` before it serves, in both modes, and refuses to start when the call fails. `setpriv` still drops to the sandbox uid under it, because the flag bars only gains on `execve`, and the spawner's `SETUID` and `SETGID` survive the `execve` of `setpriv`.
   - C. Both: B's uid inside A's namespaces, at the cost of both.

   Why B: it closes every read of the Context on the default seccomp profile, works alike in compose and swarm mode, and hardens the container beyond its present settings; A loosens the kernel surface of every process in the container to hide a process list that holds no credential.
4. **Concurrency on the provision runner. Decided: A** by the operator (hub card `e0d4eb3d201c2054`, 2026-11-20). The options were:
   - A. Runs stay parallel (`max_parallel_tasks` 0), one sandbox each.
   - B. One task at a time on top of the sandbox: row and env at 1 with `SEMAPHORE_RUNNER_ONE_OFF`, as the workspace runners ([102](102-one-semaphore-runner-per-workspace.md) decision 4).
   - C. A provision runner per workspace, tagged `provision-ws-<id>`.

   Why A: a run may take up to `RUN_BUDGET`, 2 h (`roles/web-app-semaphore/files/python/provision/provider_env.py`), so B holds every workspace's provision, destroy, unlock, dns and zone tasks behind one run for that long, and a one-off runner still leaves its token to a plugin without the sandbox. C needs the sandbox as well, adds one idle container per workspace and changes 104 decision 1 and 102 decision 2.
5. **Network unchanged. Decided** by the scope of the card. The sandbox keeps the runner's network, because OpenTofu needs the provider APIs, OpenBao and the state endpoint. The egress list that 104 decision 1 gives the provision runner is not in place (`compose.yml.j2` puts it on the role's default networks with the host alias); that gap stays with 104.
