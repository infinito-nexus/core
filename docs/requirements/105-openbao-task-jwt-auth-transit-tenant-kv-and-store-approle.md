# 105 - OpenBao: Task JWT Auth, Transit, Tenant KV and Store AppRole

## User Story

As the operator of a platform that keeps every workspace secret in OpenBao, I want a Semaphore task to log in with its own task token and read only its workspace's secrets, a transit key per workspace for its OpenTofu state, and a store credential that can write a workspace secret but never read one back, so that no store, member or task of another workspace ever holds a secret it does not need.

## Background

The store's requirement 062 (`infinito-nexus/gui: docs/requirements/062-slim-store-orders-provisioned-through-platform-roles.md`, decision 9, criteria 062:81, 062:120-121 and 062:135) needs this core side. [053 - web-app-openbao](053-web-app-openbao.md) decided the static seal, AppRole for Ansible, raft storage and the PKI flag; [047 - OpenBao Audit Device](047-openbao-audit-device.md) the audit device. This requirement adds to them.

### Today

- OpenBao `2.7.2` runs as a single raft node (`roles/web-app-openbao/meta/services.yml`) and stops for its backup (`services.yml`).
- One KV v2 mount, `infinito` (`roles/web-app-openbao/tasks/03_policies.yml`, `OPENBAO_KV_MOUNT` at `roles/web-app-openbao/vars/main.yml`). The store cites `tasks/04_auth_methods.yml` for it; those lines build the fact of the auth mount table and start the identity group upsert, not the KV mount.
- Auth methods:
  - OIDC for interactive logins, enabled at `roles/web-app-openbao/tasks/utils/oidc.yml`, with `role_type=oidc`, on the shared client (`vars/main.yml`);
  - AppRole for the deploy (`roles/web-app-openbao/tasks/02_auth.yml`, its role);
  - LDAP as an addon (`roles/web-app-openbao/tasks/addons/auth-ldap.yml`);
  - userpass (`roles/web-app-openbao/tasks/utils/userpass.yml`).

  There is no `jwt` mount and no transit engine.
- `reader` and `operator` read the whole `infinito` mount (`roles/web-app-openbao/templates/policies/reader.hcl.j2`, `operator.hcl.j2`). A secret placed there is readable by every platform reader.
- The deploy's AppRole policy `ansible-admin` manages policies, auth methods, mounts, identity, the KV mount and PKI (`roles/web-app-openbao/templates/policies/ansible-admin.hcl.j2`).
- The audit device is checked on every deploy, together with a probe read that must be logged and must not appear in plaintext (`03_policies.yml`).

## Decisions

1. **The `jwt` mount.** `web-app-openbao` enables `auth/jwt` when `web-app-semaphore` is in the deployment. It configures `jwks_url` as Semaphore's key set on its canonical origin (103), `bound_issuer` as `SEMAPHORE_JWT_ISSUER` and, under `TLS_MODE` `self_signed`, `jwks_ca_pem` as the deployment CA. `web-app-openbao` runs after `web-app-semaphore`, so the key set answers when the mount is written.
2. **Roles per workspace.** `workspace apply` (102) writes the roles of a workspace from one JSON body:
   - `ws-<id>` binds `project_id` to the workspace project, as a JSON number, and carries `tenant`. Its tasks deploy, back up, restart and update.
   - `ws-<id>-provision` binds `project_id` to the provision project and `template_id` to that workspace's `unlock` and `dns` templates (104), and carries its own policy `ws-<id>-provision` alone, which reads no provider secret.
   - The per-provider roles `ws-<id>-provision-<provider>`, each bound to its own `provision-<provider>` and `destroy-<provider>` templates, come from [133](133-provision-secrets-per-template.md), the zone role `ws-<id>-zone` from [124](124-cloudflare-zone-lifecycle-per-line.md); each carries its own policy alone.

   All set `bound_audiences` to `openbao`, `user_claim` to `sub`, and a `token_ttl` that covers the longest run of their templates. No provision role carries the transit policy `ws-<id>-transit`: a provision, zone, unlock or dns run mints one non-renewable child that carries it, through the token role `ws-<id>-transit-child`, and hands only that child to OpenTofu (133). A deploy reads at its start (106); a provision writes state until its end. `destroy` deletes every role of the workspace, the token role `ws-<id>-transit-child` and every secret under `tenant/data/ws-<id>/` and `tenant/data/ws-<id>-provision/` with all its versions: it lists `tenant/metadata/` below both prefixes and deletes the metadata of each key. So `workspace destroy` is the one erasure path of a workspace (operator pick, 2026-11-13), and the store holds no delete on roles or keys.
3. **One templated policy for the deploy role.** The policy `tenant` grants `read` on `tenant/data/<role>/*`, and `update` on `transit/datakey/plaintext/<role>` and `transit/decrypt/<role>`. `<role>` is `identity.entity.aliases.<jwt accessor>.metadata.role`, which OpenBao sets from the role name and no claim can set. So `ws-<id>` reads `tenant/data/ws-<id>/`. The provision roles do not carry `tenant`: their per-workspace policies name the paths under `tenant/data/ws-<id>-provision/` they read, and they reach the transit key `ws-<id>-provision` only through the child token above (133). A shared alias would let one workspace's login rewrite another's metadata; `sub` gives every task its own alias, so each token's metadata stays its own. A scheduled platform template deletes the `jwt` entities older than the longest `token_max_ttl`.
4. **Two new KV v2 mounts.** `tenant` holds workspace secrets. `platform` holds the store's service credentials and the provision secrets every workspace shares: the platform-account tokens of Hetzner Cloud and IONOS, and the zone tokens of 104's `cloudflare` DNS flavor. The per-workspace DNS credential of the `knot` and `route53` flavors goes to `tenant/data/ws-<id>-provision/dns`, and the Route 53 credential that creates IAM users to `platform/data/workspaces/route53`, outside `platform/data/provision/*`. No shared policy reads `platform/data/provision/*`: each provision role carries a per-workspace policy of its own name that reads only its workspace's paths and, for `ws-<id>-provision-<provider>`, its own provider's ([133](133-provision-secrets-per-template.md)); the deploy deletes the earlier shared policy `provision-shared`. Neither mount is under `infinito`, which every platform `reader` reads.
5. **Transit.** `web-app-openbao` enables `transit`. `workspace apply` creates the key `ws-<id>-provision` as `aes256-gcm96`, with `exportable` and `allow_plaintext_backup` false and `deletion_allowed` false. Only `destroy` turns `deletion_allowed` on and deletes the key, after the workspace's servers and states are gone (104). Right after creating a key, `apply` writes a raft snapshot (`sys/storage/raft/snapshot`) into the backup directory of `svc-bkp-volume-2-local` and fails when that write fails. The store starts no provision before `apply` succeeded, so the key is in a backup before the first state write. The provision script also refuses a key younger than the newest snapshot.
6. **The store AppRole.** The role `store` gets the policy `store` and nothing else:
   - `create` and `update` on `tenant/data/ws-*`, without `read`: the store writes a workspace secret and cannot read it back (store criterion 062:120);
   - `read` and `delete` on `tenant/metadata/ws-*`, so a replaced or destroyed secret can go, and so the store reads the version history of the workspace key `tenant/data/ws-<id>/ssh`, never its value (Store ask 5, 2026-11-14). OpenBao applies the one most specific pattern of all policies a token carries, and a `+` stands only for a whole segment, so a narrower `read` on `tenant/metadata/+/ssh` would always lose to `tenant/metadata/ws-*` and never apply;
   - `create`, `read` and `update` on `platform/data/store/workspace-keys/*` and `delete` on `platform/metadata/store/workspace-keys/*`, for the public-half record of each workspace key (Store ask 5, 2026-11-14). The store writes `tenant/data/ws-<id>/ssh` with check-and-set, then `platform/data/store/workspace-keys/ws-<id>` with the public half and the version that write returned, then its own record. After a crash between them, the key is the store's own only when the record's public half equals the store's intent and its version equals `current_version` of `tenant/metadata/ws-<id>/ssh`; anything else stays a refusal. The record holds nothing secret, and the store deletes it with the workspace, as it does its host keys;
   - `read` on `platform/data/store/*`, its own service credentials and the identity of the Workspaces project at `platform/data/store/semaphore/workspaces`, which the deploy (`tasks/07_workspaces.yml`, under the Ansible AppRole) writes from Semaphore's fact `semaphore_workspaces_identity` whenever it differs from the stored entry ([102](102-one-semaphore-runner-per-workspace.md) decision 3, Store ask 26, robot pick, 2026-11-14);
   - `create`, `read`, `update` and `delete` on `platform/data/store/hostkeys/*` and on `platform/metadata/store/hostkeys/*`, for the host keys the store pins (operator picks, 2026-11-13 ~18:30 and ~18:50). An entry `platform/data/store/hostkeys/ws-<id>/<host>/<port>` holds exactly one field, `line`, the server's public host-key line (`<type> <base64>`), and nothing secret. The store reads it to fill the `HOST_KEY` input of `deploy`, `update`, `backup`, `restart`, `suspend` and `resume` ([103](103-semaphore-pin-task-jwt-and-locked-templates.md) decisions 7 and 8), the only templates that take one, and deletes a workspace's entries after `workspace destroy` of that workspace. `list` only on `platform/metadata/store/hostkeys/+/` and `platform/metadata/store/hostkeys/+/+/`, so the erasure walks the hosts and ports of one workspace whose id it knows, and a list of `platform/metadata/store/hostkeys/` itself, which would enumerate the workspaces, stays refused (Store ask 39, 2026-11-14). No task token reads this path, because `tenant` grants nothing under `platform`;
   - `create` and `update` on `platform/data/store/invites/*`, without `read` and `delete`, and `delete` on `platform/metadata/store/invites/*` and on no other metadata path besides the host keys and the workspace-key records (Store ask 25, GDPR; parent pick, 2026-11-14 ~02:15). The store stages `{email, role}` of an invite at `platform/data/store/invites/<ws>/<key>` ([107](107-keycloak-organizations-workspace-roles-and-one-client-per-consumer.md) decision 9) and erases that entry with every version by a `DELETE` of its metadata after a successful invite and on uninvite, so the address is gone, not only soft-deleted. The more specific path wins over `read` on `platform/data/store/*`, so the store cannot read a staged invite back;
   - `update` on `auth/approle/role/store/secret-id` and `auth/approle/role/store/secret-id-accessor/destroy`, to rotate its own secret id;
   - `update` on `auth/approle/role/store/secret-id/lookup`, to read the `expiration_time` of its own secret id (Upstream; operator pick, 2026-11-13). The lookup needs the secret id itself and answers only metadata of the role `store`, so it reaches nothing that minting a new secret id does not already reach.

   No `auth/jwt` path, no `sys` path, no transit path, no `list` on `tenant`, and no `custom-secret-id`, which would let the caller choose its own secret: under 102 the roles and keys are written by `workspace apply` and erased by `workspace destroy`, not the store. Store item 4 asked for `auth/jwt/role/ws-*`; this is its stricter replacement. The secret id has `secret_id_ttl` 720 h. The store's tokens live 1 h, at most 4 h.

   In OpenBao, a leaked store credential reaches: writing and deleting any workspace secret without reading it, reading the store's own Semaphore and Gitea tokens, and staging and erasing an invite without reading a staged one. It reads no Keycloak credential: the store holds no Keycloak admin role ([107](107-keycloak-organizations-workspace-roles-and-one-client-per-consumer.md) decision 7), and the secret of a deployed Keycloak's read-only usage client stays under `tenant/data/ws-<id>/`, which only the workspace's own task token reads ([130](130-workspace-usage-metering.md)). It can also replace a pinned host key, so a host template would trust a server that pretends to be the host; it reaches no more than the `HOST_KEY` it already passes to the four host templates (103 decision 8). The README MUST state this reach.
7. **The store's other credentials (operator pick, 2026-11-13).** The scheduled platform template `rotate store credentials`, in the Workspaces project, runs every 7 days. It mints the store's Semaphore token and the store's Gitea token (111) and writes each to its own path, `platform/data/store/semaphore` and `platform/data/store/gitea`. Each entry MUST hold exactly two fields:
   - `token`: the token;
   - `expires_at`: the moment the rotation revokes that token, as RFC 3339 with a numeric offset in UTC (`2026-11-27T09:00:00+00:00`). It is the mint time plus two rotation periods, 14 days.

   Each token's name carries its `expires_at`, and each run revokes every store token whose `expires_at` has passed, and no other. So a token works at least until its `expires_at`, also after a manual run, and the store MUST switch to the newer entry before then. The Semaphore token additionally gets Semaphore's own `expires_at` of 30 days (Upstream), so a stalled rotation still ends it. Gitea's CLI sets no expiry (Upstream), so a Gitea token ends only by the rotation's revocation.
8. **No member logs in to OpenBao.** A workspace member reaches a secret only through the store, which writes for an Owner or Admin (store criterion 062:120), and through a task token of the workspace's templates. So no workspace OIDC role exists. Each organization role maps to what the store may write on its behalf, not to an OpenBao login.
9. **Audit.** Every store write is in the audit log under the store role's display name with HMAC'd values. The audit check of `03_policies.yml` holds for the new mounts too.

Rejected:

- A string `project_id` in `bound_claims`: it never matches the numeric claim.
- `aud` or `iss` as `user_claim`: they are shared, so the alias and its metadata would be shared.
- One policy per workspace: one templated policy serves every workspace without a policy write per `apply`.
- Exportable keys with plaintext backups: they let a key leave OpenBao.
- `delete` on `transit/keys/ws-*` and `auth/jwt/role/ws-*` for the store's erasure: a key deletes only after its `deletion_allowed` is set (Upstream), so the store would also need `update` on each key's config, and a leaked store credential could then make every workspace's state unreadable; a role delete stops every task login of its workspace.
- `list` on `tenant/metadata/ws-*` for the store: the store wrote every name it would list, and a list shows the secret names of every workspace.
- A separate erasure AppRole for the store: a second store credential with the same reach.
- The secrets of the deployed Keycloaks' directory clients under `platform/data/store/directory/` for the store (operator pick of 2026-11-13, replaced at ~18:50): a leaked store credential would hold `manage-users` in every workspace's deployed Keycloak. The store manages no user of a deployed instance; core's `usage` template only counts them ([130](130-workspace-usage-metering.md)).
- An `expires_at` in the KV entry's `custom_metadata`: the store would need `read` on `platform/metadata/store/*` too.
- Revoking by run count ("the run before the previous one"): a manual run would revoke a token before the time the store relies on.
