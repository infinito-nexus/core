# 107 - Keycloak Organizations, Workspace Roles and One Client per Consumer

## User Story

As the operator of a platform whose customers work in workspaces, I want each workspace to be a Keycloak organization with five fixed roles that tokens carry as a flat claim, core to be the only writer of those organizations, and the store, Semaphore, OpenBao and Gitea each to sign in through a confidential client of their own, so that invitations, members and roles live in one place, a leaked store credential changes nothing in Keycloak, and no consumer accepts a token minted for another.

## Background

The store's requirement 062 (`infinito-nexus/gui: docs/requirements/062-slim-store-orders-provisioned-through-platform-roles.md`, decisions 6 and 7, criteria 062:83 and 062:111-114) needs this core side.

### Today

- The platform realm has organizations off (`roles/web-app-keycloak/templates/import/realm.json.j2`) and fine-grained admin permissions on (`realm.json.j2`).
- The client scope `organization` with the stock `oidc-organization-membership-mapper` (claim `organization`, multivalued) is in the import (`realm.json.j2`) and among the default optional scopes (`realm.json.j2`).
- The browser flow carries the stock sub-flow `Browser - Conditional Organization` with the `organization` authenticator (`realm.json.j2`).
- Every consumer signs in through one shared client: its id is the software domain (`group_vars/all/11_oidc.yml`), and it is public (`roles/web-app-keycloak/templates/import/clients/default.json.j2`). Semaphore (`roles/web-app-semaphore/vars/main.yml`), OpenBao (`roles/web-app-openbao/vars/main.yml`) and Gitea (`roles/web-app-gitea/vars/main.yml`, `roles/web-app-gitea/tasks/setup/oidc.yml`) use it.
- A role can already bring a client of its own through `services.sso.oidc.clients` and `templates/keycloak/clients.json.j2`, which `roles/web-app-keycloak/filter_plugins/oidc_clients.py` includes, as `web-app-stalwart` does ([066](066-server-side-logout-everywhere.md)).
- The platform RBAC roles are application roles such as `operator` of `web-app-semaphore`, which pauses and resumes the platform's applications (`roles/web-app-semaphore/meta/rbac.yml`), and `administrator`, `operator` and `reader` of `web-app-openbao` (`roles/web-app-openbao/meta/rbac.yml`).

### The target Keycloak's users

Store item 6 also asks for user management of a deployed Keycloak. The operator dropped it on 2026-11-14: the customer manages the instance's users in its own Keycloak, and core only counts them through a read-only client for billing ([130](130-workspace-usage-metering.md)). The store asked whether `GET /admin/realms/<r>/roles/<name>` needs `view-realm` on Keycloak 26.8. It does, with and without fine-grained admin permissions v2:

- [RoleContainerResource.getRole](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/services/resources/admin/RoleContainerResource.java) calls `auth.roles().requireView(roleContainer)`.
- For a realm, [RolePermissions.canView](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/services/resources/admin/fgap/RolePermissions.java) asks `canViewRealm`, and [RealmPermissions](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/services/resources/admin/fgap/RealmPermissions.java) answers it with `canViewRealmDefault`, which is `hasOneAdminRole(MANAGE_REALM, VIEW_REALM)`.
- [RolePermissionsV2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/services/resources/admin/fgap/RolePermissionsV2.java) overrides only `canMapRole`, and [RealmPermissionsV2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/services/resources/admin/fgap/RealmPermissionsV2.java) does not override `canViewRealm`.

The core realm runs with v2 on (`realm.json.j2`), and that does not change the answer. The usage client of 130 holds only `view-users`, so it reads no role configuration.

## Decisions

1. **Organizations on the platform realm.** `services.keycloak.organizations.enabled` in `roles/web-app-keycloak/meta/services.yml` defaults to `false`. Variant 0 and every inventory that runs the store turn it on. With it on, the realm import sets `organizationsEnabled` true. The `organization` execution of `Browser - Conditional Organization` is set to `DISABLED`, because workspaces broker no identity provider per organization, so the login page stays one step.
2. **A workspace is one organization, and core creates it (operator pick, 2026-11-13 ~18:50).** The store chooses the workspace id `<id>`, a lowercase UUID matching `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`, and starts `workspace apply` with it ([102](102-one-semaphore-runner-per-workspace.md) decision 3). `apply` creates the organization with the name and alias `ws-<id>` and the attribute `workspace.id` set to `<id>` in the create request, which Keycloak stores with the organization (Upstream). That attribute is the workspace marker:
   - Every core template that acts on a workspace's organization finds it only by the marker, through the attribute search of the organization list (Upstream). It refuses, and changes nothing, when it finds more than one, or when it finds none; only `apply` then creates the organization, only `destroy` then counts it as deleted, and only `members list` then succeeds with `{"workspace":"<id>","absent":true}` (decision 9).
   - An `apply` whose alias `ws-<id>` belongs to an organization without the marker gets 409 from Keycloak (Upstream) and fails. So no template acts on an organization that a Keycloak admin created by hand.
   - Keycloak chooses an organization's own id (Upstream), so the workspace id is the store's and the organization id stays inside core. A retried `apply` finds the organization it created by the marker and creates no second one.
3. **Five fixed roles as organization groups.** `workspace apply` (102) creates the groups `Owner`, `Admin`, `Operator`, `Billing` and `Viewer` in the organization. A member's role is their membership in one of these groups, and `members role` (decision 9) keeps it to exactly one. A custom role lives in the store, which has `members role` place its members into the group of its widest built-in right (store criterion 062:113). Keycloak holds no custom role. `PUT` writes the organization from the request body (Upstream), so `apply` writes the organization only in its create request, and `members` writes it only as a read-modify-write of the representation it read in the same task; `members` tasks never run side by side (102 decision 9). So the marker and the pending invitations of decision 9 survive every write.
4. **The flat claim.** The stock mappers cannot write `<id>:<role>` entries. So the realm holds a client `workspaces`, with no flow enabled, whose client roles are named `<id>:<role>`, with `<id>` the workspace id of decision 2. `workspace apply` creates the five roles of an organization and maps each onto its group. The client scope `workspace_roles` holds one stock "User Client Role" mapper for client `workspaces`, with claim `workspace_roles`, multivalued and without a prefix. It is a default scope of the store's client only, and the mapper writes the claim into the access token, the ID token and userinfo. The nested `organization` claim stays available to any consumer that asks for the `organization` scope. So the store computes a user's rights with no admin read: from `workspace_roles` of the user's own access token, whose `aud` holds the store's client id (decision 6), and from `organization`, which lists the alias `ws-<id>` of every membership, also of an accepted invitee whom no `members` task has placed yet (decision 9). A change of a member's group reaches the store with that member's next token.
5. **No mapping into platform RBAC.** A workspace role never grants a platform RBAC role. Mapping a workspace `Operator` onto `web-app-semaphore`'s `operator` would let a customer pause the platform's applications. The store's rule "map onto `iam-profile-rbac` where a role of the same name exists" applies only inside the workspace's own deployed instance. There the customer applies it in the instance's own Keycloak ([130](130-workspace-usage-metering.md) decision 1).
6. **One confidential client per consumer.** The store, Semaphore, OpenBao and Gitea each declare their own client under `services.sso.oidc.clients`. Each client is confidential, with its secret from its role's credentials, the standard flow only, and redirect URIs and web origins of its own application only. Each consumer accepts only tokens whose `aud` holds its own client id: Semaphore and Gitea check the ID token's audience, and the OpenBao OIDC role sets `bound_audiences`. The shared public client stays for every other application. The store's client is a login client only:
   - It has no service account (`serviceAccountsEnabled` false), no realm-management role and no fine-grained permission (decision 7).
   - It sets `rootUrl` and `baseUrl` to the store's own origin, and `members invite` sends its client id with every invitation, so an invitee returns to the store after acceptance instead of a 400 (Upstream; operator pick, 2026-11-13).
   - It carries one `oidc-audience-mapper` with `included.client.audience` set to its own client id and the access token claim on, so its access tokens name it in `aud` (Upstream), and the store refuses every token whose `aud` does not hold its client id (operator pick, 2026-11-13 ~18:15).
   - Its secret reaches Keycloak only through the realm import or a `kcadm` stdin payload, as for every confidential client of core. The store's role mounts the secret as a file with mode `0600`, owned by the store's UID, and passes only its path as `KEYCLOAK_CLIENT_SECRET_FILE`; the secret never enters the store's environment or an argument.
7. **Core is the only writer (operator pick, 2026-11-13 ~18:50).** The store holds no Keycloak admin role at all: no `manage-organizations`, no `manage-users`, no `view-users`, no `query-users` or other `query-*` role, no other role of realm-management, and no fine-grained permission. Every change to the platform realm that the store needs runs as a core template on a platform runner (102 decision 2), which the store starts and cannot change:
   - `workspace apply` and `workspace destroy` (102 decision 3) create and delete the organization, its groups and its `workspaces` client roles with the platform deploy's own Keycloak admin access, as every platform deploy does.
   - `members` (102 decision 9) changes invitations and memberships through core's confidential client `workspace-members`, which has no flow enabled and whose service account holds exactly `manage-organizations` and `manage-users` of realm-management (Upstream). Its secret is the credential `workspace_members_client_secret` of `web-app-keycloak`, rendered into the realm import by [workspace_members.json.j2](../../roles/web-app-keycloak/templates/import/clients/workspace_members.json.j2). Only templates that run the platform inventory read it (102 decision 3).

   Each template takes only a workspace id of the form of decision 2 and acts only on the organization that carries its marker. Each task prints every change it makes, naming the workspace, the action, the user id and the group, and never a secret, so the task log of the Workspaces project audits every membership change.    The store holds a right in no other project and on no other template of these projects. It waits for every task until Semaphore reports `success`, `error` or `stopped` (102 decision 9). Only `success` counts, and after `error` or `stopped` it starts the same input again (decision 9), except after an `error` whose last output line is a refusal (decision 9): a refusal is final, the store answers it with 409 and never starts the same input again (Store ask 18, operator pick, 2026-11-14). It reads each result from the task's last output line (decision 9, 102 decision 3, 130 decision 5). A workspace delete counts as done only when `workspace destroy` reached `success`, and a GDPR erasure only when every `workspace destroy` it needs and then `user erase` (decision 11) reached `success`.
8. **Workspace roles in Semaphore: run and view only (operator pick A, 2026-11-13; core applies them, operator pick, 2026-11-13).** In a workspace's Semaphore project (102), `members sync` ([102](102-one-semaphore-runner-per-workspace.md) decision 9) gives a member `task_runner`, `guest` or no role, never `owner` or `manager`, from the role groups of decision 3: Owner, Admin and Operator get `task_runner`, Viewer gets `guest`, and Billing gets no role, because billing runs nothing. A member of several groups gets the widest of these. Owner and Admin, which the store's plan maps onto `owner` and `manager`, get `task_runner`. The store sets no Semaphore role itself. Only an owner or a manager may edit templates, keys, inventories, repositories and environments; a task runner runs templates and reads the rest, and a guest only reads ([Semaphore project roles](https://semaphoreui.com/docs/user-guide/team)). An edited template would run a member's own code under the workspace's task identity, whose token reads the workspace's OpenBao paths (105), which store criterion 062:120 leaves to the store alone. The `template_id` binding of 105 does not stop that, because an edit keeps the id. So every change to a template, key, inventory, repository or environment of a workspace project goes through the store's account, its `manager` (102 decision 8).
9. **The `members` actions (operator picks, 2026-11-13).** Each action of `members` (102 decision 9) works through the client `workspace-members` (decision 7). Each checks the state before every change, so an action that failed at any step finishes when the store runs it again with the same input, and a further run changes nothing (operator pick, 2026-11-13 ~18:15):
   - `add` makes `WORKSPACE_MEMBER`, an existing user, the first member of the organization and puts them into `Owner`. It refuses when the organization holds another member or a pending invitation, so every later member joins by an invitation they accept. A user who already is the only member and in `Owner` is no change.
   - `invite` reads the staged invitation `{email, role}` at `platform/data/store/invites/<id>/<INVITE_KEY>` in OpenBao with the task's own login, so no address passes through a survey variable, the task input or the task log (Store ask 19, operator pick, 2026-11-14). `INVITE_KEY` is a lowercase UUID the store chooses; the store's OpenBao policy holds exactly `create` and `update` on `platform/data/store/invites/*`, so it neither reads nor deletes there, and exactly `delete` on `platform/metadata/store/invites/*` (105), and only the Workspaces project's task role reads it. `invite` sends a Keycloak invitation to the staged address with the store's client id (decision 6) and records the pending entry as the organization attributes `workspace.pending.<role>`, which lists the key, and `workspace.invite.<key>`, which holds the address. The same call serves a new and an existing user: Keycloak sends an existing user an invitation link and a new one a registration link (Upstream). A key that already has a pending invitation and entry gets no second mail. The address of a member is refused, because `role` changes members. The store erases the staged entry with all its versions by one `DELETE` to `/v1/platform/metadata/store/invites/<id>/<INVITE_KEY>`, in a `finally` block after `invite` and on `uninvite`, and sends no other delete there (Store ask 25, 2026-11-14); `invite` only reads the entry, and no core template writes or deletes it.
   - `uninvite` takes the address from `workspace.invite.<INVITE_KEY>`, deletes every pending invitation of that address (Upstream) and drops the key's two attributes. A key with no entry is no change.
   - `role` puts the member `WORKSPACE_MEMBER` into the group of `WORKSPACE_ROLE` and takes them out of every other role group. A user who is not a member is refused.
   - `role` and `remove` MUST refuse, change nothing and name the workspace when the change would leave the organization without an enabled member in `Owner` (Store ask 14, operator pick, 2026-11-13 ~21:50). Ownership moves by first giving a second member `Owner`. `workspace destroy` is not affected.
   - Every refusal of a `members` action ends the task with a non-zero exit, so Semaphore reports `error`, and its last output line is exactly `{"workspace":"<id>","refused":"<reason>"}`, with `<reason>` one of `last_owner` (the bullet above), `not_first` (`add`), `member_address` (`invite`), `not_member` (`role`), `managed` and `platform_role` (`remove`) and `absent` (a writing action on a workspace without an organization). Any other failure ends without such a line, so the store tells a final refusal from a failure it runs again (Store ask 18, operator pick, 2026-11-14).
   - `remove` first takes `WORKSPACE_MEMBER` out of every role group, so their next token carries no `workspace_roles` entry of the organization. It then removes their Semaphore role (102 decision 9) and ends the membership through `DELETE /admin/realms/<realm>/organizations/<org>/members/<user id>`. It MUST refuse, and change nothing:
     - a member whose membership is `MANAGED`, because Keycloak would delete the user with it (Upstream);
     - a user who holds a platform RBAC role, whose membership the operator manages.

     A user who is no longer a member is not refused: the task removes any Semaphore role they still hold and succeeds without a membership call.
   - `sync` puts each member who is in no role group and whose address is held by a pending entry into the group of that entry, and drops the entry. It drops every entry whose invitation Keycloak no longer holds (Upstream), and mirrors the role groups into the Semaphore project (decision 8). Every action but `list` ends with the same `sync`.
   - `list` makes no write call to Keycloak or Semaphore and only prints the last output line below, for the one organization that carries the marker of `WORKSPACE` (decision 2), so it is safe to run any number of times and its task log audits every read (operator pick, 2026-11-13 ~19:40). When no organization carries the marker, `list` succeeds and its last output line is exactly `{"workspace":"<id>","absent":true}`, while every writing action (`add`, `invite`, `uninvite`, `role`, `remove`, `sync`) still refuses and changes nothing (operator pick, 2026-11-13 ~21:50). The store builds its member view from `list` and from the same line of every other `members` task.

   Keycloak tells no one when an invitation is accepted, so core places an accepted invitee into the invited group at the next `members` task of their workspace. The store starts `members sync` when such a user returns to it, which it sees from their token: `organization` names `ws-<id>`, while `workspace_roles` holds no entry of `<id>` (decision 4). The store's own settle step, which placed an accepted invitee with its `manage-group-membership`, disappears.

   Each task that does not refuse prints, as its last output line, one JSON object: the organization's members, each with their Keycloak user id, role group and `enabled`, `true` or `false` as Keycloak holds the user (Store ask 17, operator pick, 2026-11-14), and its pending invitations, each with its key and role. It prints no name, no username and no address, neither of a member nor of an invitee (operator picks, 2026-11-13 ~21:50 and 2026-11-14). So the store's last-owner pre-check counts enabled `Owner` members exactly as `role` and `remove` do. The store takes its members and their roles from that line. It takes each member's email address and username from the OIDC claims of that member's own login to the store, where every accepted invitation returns them (decision 6), and refreshes them at the member's next login; the invoice recipients and the read-only Gitea team ([122](122-gitea-workspace-access-levels.md)) read from there. The store keeps the line it last received as its view of the workspace; Keycloak stays the only source.
10. **`workspace destroy` deletes the organization last.** After every other resource of the workspace is gone, `web-app-keycloak`'s `tasks/workspace.yml` deletes the five `workspaces` client roles of the organization and then the organization with its groups. It comes last, so the marker that makes the id a workspace outlives every other resource of it. A client role or an organization that is already gone counts as deleted, so a `destroy` that stopped after this step, or whose result the store never received, succeeds when the store runs it again (operator pick, 2026-11-13 ~18:15).
11. **`user erase` deletes the platform account (Store ask 20, operator pick, 2026-11-14).** The Workspaces project holds the locked template `user`, whose survey variables, with target `env` (103), are `USER_ACTION` (`erase`) and `USER_ID`, the Keycloak user id. It runs on a platform runner through the client `workspace-members` (decision 7), whose `manage-users` covers the call. `erase` refuses, with the refusal line of decision 9 keyed `"user"` and the reasons `member` and `platform_role`, a user who still is a member of any organization that carries a workspace marker, so the store's workspace steps come first, and a user who holds a platform RBAC role, whose account the operator manages. Otherwise it deletes the user in Keycloak and the user's entry in the platform's LDAP directory, so the next login with that address finds no account and the store records nothing. A user who is already gone in both counts as erased, so a rerun succeeds. The task prints the user id it erased and never an address, and its last output line is exactly `{"user":"<id>","erased":true}`. The store keeps an erasure pending until this task reached `success`.

Rejected:

- `manage-organizations` for the store, with `query-users` and a v2 `manage-group-membership` permission (the variant before 2026-11-13 ~18:50): creating an organization needs `manage` on all organizations ([OrganizationsResource.java:104-105](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/organization/admin/resource/OrganizationsResource.java#L104-L105)), so the store would reach every organization of the realm, could rename, delete and nest their groups, and could delete any organization, and Keycloak has no narrower permission that stops it (Upstream).
- A v2 `manage` permission per organization in place of `manage-organizations`: it cannot create an organization ([OrganizationsResource.java:104-105](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/organization/admin/resource/OrganizationsResource.java#L104-L105)). Once `apply` creates each organization, the store needs no Keycloak role at all.
- A v2 `manage` permission on members, or `manage-members` on their groups, for the store to add and remove members itself: `manage` on a user also changes its email, deletes it and removes its credentials, so a leaked store credential could take over every customer account (Upstream).
- `view-users` or `query-users` for the store, to read members or a user's organizations: a leaked store credential would read or search the profile of every user of the realm, staff included. The `members` output and the user's own token carry what the store needs.
- A service account on the store's client without any role: it mints tokens nothing needs, and one role added by hand would give them reach.
- The Keycloak organization id as the workspace id: Keycloak chooses it at creation (Upstream), so an `apply` retried after its result was lost would create a second organization.
- The deploy's master-realm administrator for `members`: it holds every right in every realm, while `members` needs two roles of one realm.
- An invitation of an existing user by id: it takes no client id, so the invitee lands in the account console instead of the store (Upstream). The invitation by address serves existing users too.
- The stock "Organization Group Membership" mapper for the store's rights: it nests the groups per alias and only next to the membership mapper (Upstream), while `workspace_roles` is one flat list.
- A claim that lists every member of a workspace, for the store's member list: no stock mapper writes one, it would grow every member's token with the team, and every member would read the ids of all others.
- A copy of the membership in OpenBao or in the workspace repository, for the store's member list: a second copy beside Keycloak that a change by hand leaves stale, and in the repository every member who reads it would read the list.
- A flat claim through a script mapper or a provider extension: core installs none (066).
- Members without a role who stay in the organization: former members would stay linked to the customer indefinitely, and the `organization` claim would keep naming the workspace.
- Realm groups per workspace: store decision 6.
- The invitee's address as a survey variable, masked with `no_log`: Semaphore stores every task's input, so the address would stay in its database and API beside the log (Store ask 19).
- An invitation held by Keycloak alone, started by the store: the store would need an admin role on the realm, against decision 7.
- Disabling the account in place of `user erase`: the account and its address stay, so a disabled account is no erasure (Store ask 20).
- An erasure by hand through the operator: slow, and nothing tells the store when it is done.
- Custom roles as Keycloak groups: the store keeps their per-script rights, and Keycloak would hold a second copy.
