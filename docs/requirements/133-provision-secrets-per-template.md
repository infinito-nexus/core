# 133 - Provision Secrets Per Template

## User Story

As the operator of the Infinito.Nexus platform, I want each provision template of a workspace to read only the platform provider secrets its own run needs, so that a leak or code execution in one workspace's run cannot hand over a platform account token that reaches every other customer's servers, records or zones.

## Context (2026-11-18, IAM store round)

- Every workspace has one task token role, `ws-<id>-provision`, for its `provision`, `destroy`, `unlock` and `dns` templates ([105](105-openbao-task-jwt-auth-transit-tenant-kv-and-store-approle.md)). Its policy `provision-shared` grants `read` on `platform/data/provision/*`.
- That subtree holds platform account tokens: `hetzner`, `ionos`, `scs`, `proxmox-<host>`, `incus-<host>`, and one Cloudflare token per pool zone at `cloudflare/<zone>`. Each reaches every workspace that the platform account serves.
- The provision script hands its OpenBao token to OpenTofu as `BAO_TOKEN`, so the provider plugins of a run hold a token that can read all of them, whichever provider the line uses.
- [124](124-cloudflare-zone-lifecycle-per-line.md) already moved the account-wide zone token out of that reach: `zone ws-<id>` logs in with its own role `ws-<id>-zone`, whose per-workspace policy reads that token and its own state, transit key and snapshot record only, and `provision-shared` denies the token.

## Decisions

Decided by the operator on 2026-11-20.

1. **Scope per run: one role per template and provider.** Task tokens carry no provider claim, so the template pins it: `workspace apply` creates `provision-<provider> ws-<id>` and `destroy-<provider> ws-<id>` for each provider of `OPENBAO_PROVISION_SECRETS`, each with the provider as its locked first argument, and removes every other template of the workspace once it stopped that template's unfinished tasks. `ws-<id>-provision-<provider>` binds those two template ids alone and carries the per-workspace policy of its name; `ws-<id>-provision` binds `unlock ws-<id>` and `dns ws-<id>` and reads no provider secret. So the `template_id` alone picks the policy, and a leaked task token opens that one provider's role of that one workspace. A run logs in once, with its template's role. `provision` refuses a line on another provider before the login; `destroy` must log in first, because the line's provider is in its state record, so it reads the state bucket keys and the record, refuses a mismatch, and only then reads the DNS credential and the provider secrets. OpenTofu and its provider plugins get a non-renewable child token that carries `ws-<id>-transit` alone, the workspace's transit datakey and decrypt, never the role token. The task roles hold their own policy alone; the child comes from the token role `ws-<id>-transit-child` (`allowed_policies` `ws-<id>-transit`, `disallowed_policies` `default`, not renewable, not orphan, explicit max TTL of the provision task token), and each role policy grants `update` on `auth/token/create/ws-<id>-transit-child` only, never on bare `auth/token/create`, so a leaked role token mints no child with another policy. `workspace apply` writes that token role beside the transit policy, `workspace destroy` deletes it. The wrappers hand the task token to `provision.py` on a file descriptor instead of its environment; `provision.py` sets `prctl(PR_SET_DUMPABLE, 0)` before it reads that descriptor, so another process of the runner's uid cannot read its `/proc/<pid>/environ` or memory while OpenTofu runs (the `execve` of OpenTofu resets the flag, and OpenTofu holds the child alone), and on every exit Python handles it revokes its role token with `revoke-self`, which revokes the child too. Any error of that revoke while a refusal or failure of the run is in flight, the run budget passing during it included, is only reported on stderr, and the run ends with its own exit code and message. The exceptions are a SIGTERM or SIGINT during the revoke, which ends the run with that signal instead, and a SIGKILL at any point: the role token then stays valid until its TTL of 4h and the child until its TTL of 2h. The provider list has one source, `providers` of `roles/web-app-semaphore/files/opentofu/credentials.json`, from which `provision.py` derives the pin at run time; `PROVISION_PROVIDERS` of `project.py` (run as `python3 -c`, without the file), `OPENBAO_PROVISION_SECRETS` and `ALL_PROVIDERS` of `test-provision.js` keep copies that `test_every_provider_list_names_the_providers_of_credentials_json` compares file by file. The store runs the template of the line's provider: for `provision` the provider whose catalog offers the line's flavor, size and region, for `destroy` the one the line was provisioned with. `apply` deletes the roles and policies of providers the table dropped; every deploy deletes the earlier policy `provision-shared`, each `ws-<id>-provision` role that holds another policy than its own or binds other than two templates (`unlock` and `dns`; a role from before 133 binds four), and each `ws-<id>-transit-child` token role that allows another policy than `ws-<id>-transit`, so a workspace's provision tasks fail closed until its next `workspace apply`.
2. **The DNS pool: own zone only.** The per-workspace policy reads only `platform/data/provision/cloudflare/<zone>` of the workspace's own zone, written at `workspace apply`; a zone change needs a re-apply. Known cross-workspace reach: a pool zone is shared, so `cloudflare/<zone>` is one DNS write token for every workspace placed in that zone, and a leaked task token of one of them can change the records of all others in the same pool zone. A per-workspace zone ([124](124-cloudflare-zone-lifecycle-per-line.md)) has no such neighbour.
3. **Platform tokens: denied by default.** `PROVIDER_TOKEN=platform` needs the per-workspace store switch `WORKSPACE_PLATFORM_TOKENS`, a required `workspace apply` input; without it only `PROVIDER_TOKEN=workspace` runs. No backward compatibility.
4. **Rollout: core and the store ship together.** The store starts `provision-<provider> ws-<id>` and `destroy-<provider> ws-<id>` and sends `WORKSPACE_PLATFORM_TOKENS` on every `workspace apply`; neither works against the other's old release, and nothing stays backward compatible. Core and the store deploy in one window, then `workspace apply` runs once per workspace. Between the core deploy and each re-apply it fails loud: an apply without the switch exits 2 (`WORKSPACE_PLATFORM_TOKENS None is neither true nor false`); a run of the old `provision ws-<id>` or `destroy ws-<id>` exits 2 (`pins no provider`) before any login; `unlock ws-<id>` and `dns ws-<id>` fail at the OpenBao login, because the deploy deleted the old `ws-<id>-provision`; `zone ws-<id>` fails when its old policy refuses `auth/token/create/ws-<id>-transit-child` (403); and a store that still names `provision ws-<id>` after the re-apply gets 404, because apply removed that template. Drain the provision project before the core deploy: no `provision`, `destroy`, `unlock`, `dns` or `zone` task of any workspace may run then, because the re-apply stops every unfinished task of a template it retires and a pre-133 run cut off mid-way may leave servers it created out of its state. The re-apply deletes the retired `provision ws-<id>` and `destroy ws-<id>` templates, and with them Semaphore loses their task history and logs. A restore of an OpenBao backup from before 133 brings the old `ws-<id>-provision` role and `provision-shared` back: after it, redeploy core, whose drop deletes them again, then run `workspace apply` once per workspace, as for the first rollout.

## Known Gaps

- **One uid for every task of a runner.** The provision runner runs parallel tasks as one uid (`64101`, `roles/web-app-semaphore/vars/main.yml`), so a provider plugin of one run reads `/proc/<pid>/environ` of the processes and the task directories of every concurrent run the runner holds, and the runner token under `/run/secrets` (`meta/volumes.yml`) belongs to that uid too, so a plugin can poll the JWTs of other jobs. `prctl(PR_SET_DUMPABLE, 0)` hides `provision.py`'s own environment and memory only. The concurrent runs belong to other workspaces, because this one platform runner takes the provision, destroy, unlock, dns and zone tasks of every workspace. The remedy, a sandbox per OpenTofu run, is [135](135-opentofu-sandbox-per-run.md). Pre-existing, not fixed by 133.

## Acceptance Criteria

- [ ] A `provision` or `destroy` run of a line on one provider gets 403 on the platform secret of every other provider and on the Cloudflare tokens of every zone but its workspace's own (`test_a_provision_run_reads_its_own_provider_only` in `tests/unit/python/roles/web-app-openbao/test_policies.py`, with a planted wildcard as its negative control).
- [ ] The OpenBao token OpenTofu receives reads no path outside the run's provider, state, transit key and snapshot record (`test_the_tofu_token_reaches_the_line_provider_only` in `tests/unit/python/roles/web-app-semaphore/files/test_provision_sh.py` bounds the run's role token; OpenTofu itself gets the `ws-<id>-transit` child token only, `test_tofu_holds_a_transit_child_token_never_the_role_token` there and `test_the_child_token_reaches_its_own_transit_key_only` in `test_policies.py`, each with a negative control).
- [ ] Live, a provision task token of one workspace gets 403 on `platform/data/provision/<other provider>` (`provision isolation: a provision task reads no foreign provider secret` in `roles/web-app-semaphore/files/playwright/test-provision.js`).
- [ ] No two OpenBao roles of a workspace bind one template id, and each provider role binds only its own `provision-<provider>` and `destroy-<provider>` (`test_the_template_id_alone_picks_the_role` in `tests/unit/python/roles/web-app-openbao/test_workspace_roles.py`, with two planted shared bindings as negative controls).
- [ ] Live, the task token of one provider's template gets 400 or 403 from every other provider's role, the neutral role and the zone role (`provision isolation: a provider template's task token logs in to its own provider role only` in `roles/web-app-semaphore/files/playwright/test-provision.js`).
- [ ] Every deploy deletes `provision-shared` and each `ws-<id>-provision` role naming it, and `workspace apply` deletes the roles and policies of dropped providers, both idempotently (`tests/unit/python/roles/web-app-openbao/test_provider_access.py`, with planted no-op deletes as negative controls).
- [ ] No other process of the runner's uid reads the role token or the task token of a run: the fake `tofu` reads `/proc/<pid>/environ` of `provision.py`, the parent of its supervisor, and as non-root finds it closed (`test_the_python_process_is_undumpable_before_the_login`, control `test_negative_control_a_dumpable_process_is_found`); the task token never reaches that environment (`test_the_task_token_never_reaches_the_python_environment`, controls `test_negative_control_a_token_kept_in_the_environment_is_seen` and `test_negative_control_a_wrapper_that_keeps_the_token_is_refused`); and the dumpable `tofu_supervisor.py` holds no variable its `tofu` lacks (`test_the_supervisor_holds_no_variable_tofu_lacks`, control `test_negative_control_a_supervisor_that_keeps_a_variable_from_tofu`), all in `tests/unit/python/roles/web-app-semaphore/files/test_provision_sh.py`.
- [ ] Every run revokes its role token, and with it the child, on every exit Python handles, with the run budget's alarm deferred, and a failed revoke beside a refusal keeps exit 2 and the refusal text (`test_the_run_revokes_its_role_token_and_with_it_the_child`, control `test_negative_control_a_session_without_the_revoke_leaves_the_token`, and `test_a_failed_revoke_keeps_the_refusal_of_the_run`, control `test_negative_control_an_unguarded_revoke_replaces_the_refusal`, in `test_provision_sh.py`; `test_the_revoke_takes_no_alarm_on_either_exit`, `test_a_failed_revoke_keeps_the_exception_of_the_block` and `test_a_failed_revoke_after_a_clean_block_fails_the_run`, control `test_negative_control_a_revoke_in_finally_replaces_the_refusal`, and `test_a_budget_passing_during_the_revoke_keeps_the_refusal`, control `test_negative_control_a_remote_error_only_catch_lets_the_budget_win`, in `tests/unit/python/roles/web-app-semaphore/files/provision/test_session.py`).
- [ ] The token role `ws-<id>-transit-child` mints only the non-renewable `ws-<id>-transit` child and lives exactly as long as its workspace: `workspace apply` writes it (`test_apply_writes_the_token_role_that_alone_mints_the_child`, control `test_control_a_renewable_token_role_is_found`) and `workspace destroy` deletes it with every role of the workspace (`test_destroy_deletes_every_role_of_the_workspace`), both in `tests/unit/python/roles/web-app-openbao/test_workspace_erasure.py`; every deploy drops one that allows another policy (`test_deploy_retires_the_shared_policy_and_each_role_naming_it`, control `test_negative_control_a_kept_token_role_still_allows_more`, in `test_provider_access.py`); and no role policy mints through bare `auth/token/create` (`test_a_provision_run_reads_its_own_provider_only`, control `test_control_a_bare_token_create_mints_any_child`, in `test_policies.py`).
