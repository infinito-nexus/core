# 110 - Proxmox Test Target and Pool Token per Workspace

## User Story

As the operator of a platform that provisions customer servers on Proxmox VE, I want `web-app-proxmox` to deploy a real Proxmox VE, by default as a virtual machine on any container host, echoserver and the CI runners included, and to give each workspace a resource pool with a privilege-separated token scoped to it, so that the store's Proxmox lane runs against the real API, CI tests the role on every change, and a workspace's credential can touch only the VMs of its own pool.

## Background

The store's requirement 062 (`infinito-nexus/gui: docs/requirements/062-slim-store-orders-provisioned-through-platform-roles.md`, decisions 14 and 18, criteria 062:136 and 062:192) needs this core side. [093 - Agents: VM Workspaces on Incus and Proxmox](093-agents-vm-workspaces.md) built the role for agent VMs; its host criteria for the broker's pool and token are still open.

### Today

- `web-app-proxmox` runs Proxmox VE as one Docker container built from the official repository (`roles/web-app-proxmox/README.md`): the Debian base plus the pinned packages of `roles/web-app-proxmox/meta/services.yml` (`roles/web-app-proxmox/files/Dockerfile:13-25`).
- The container gets `/dev/kvm`, `/dev/net/tun`, `/dev/vhost-net`, `/dev/fuse`, `NET_ADMIN`, `SYS_ADMIN` and `cgroup: private` (`roles/web-app-proxmox/templates/compose.yml.j2`). It has no user namespace of its own, so root in it is root on the host (`README.md`).
- The deploy refuses a host that also runs `web-app-keycloak`, `svc-ai-litellm` or `web-app-openbao` (`roles/web-app-proxmox/vars/main.yml`) unless `services.proxmox.shared_host` is true (`roles/web-app-proxmox/tasks/00_core.yml`, `vars/main.yml`). The default is false (`meta/services.yml`), as `README.md` documents.
- The deploy proves `/dev/kvm` (`00_core.yml`, `roles/svc-virt-kata/tasks/utils/assert/kvm.yml`) and sizes the container limits for the agent VMs (`00_core.yml`).
- The role is `pre-alpha` (`meta/services.yml`), and CI deploys no `pre-alpha` role (`meta/lifecycle.yml`); `alpha` is the first status CI deploys (`meta/lifecycle.yml`). It declares no `architectures`, while CI spreads its rows over amd64 and arm64 (`.github/workflows/call-test-deploy.yml`) on GitHub-hosted runners, into the dev stack's privileged `target` (`compose.yml`), across the distributions `arch debian ubuntu fedora centos` (`.github/workflows/call-validation.yml`).
- `svc-virt-incus` installs Incus on a Debian or Arch host only (`roles/svc-virt-incus/README.md`).
- The README documents one privilege-separated broker token per instance, bound to one pool (`README.md`). No task creates a pool or a token: the role's code holds no `pveum pool`, `pveum user token` or pool API call.
- Secrets reach the container on stdin and never on an argv (`README.md`), and break-glass access is `pveum` as root inside the container (`README.md`).

### Upstream

| Fact | Source |
| --- | --- |
| A privilege-separated API token has only the permissions granted to the token itself, never more than its user. | [Proxmox VE user management](https://pve.proxmox.com/wiki/User_Management) |
| A resource pool groups VMs and storage. A permission on `/pool/<id>` covers its members. | [Proxmox VE user management](https://pve.proxmox.com/wiki/User_Management) |
| Bridges and SDN zones are permission paths of their own (`/sdn/zones/<zone>/<vnet>`). A VM NIC needs `SDN.Use` there, and without `SDN.Audit` or `SDN.Use` the bridge is not visible to the token. | [Proxmox VE user management](https://pve.proxmox.com/wiki/User_Management) |
| The `bpg/proxmox` provider needs SSH to the node only for snippets (custom cloud-init files), `source_file` uploads and `idmap`. VM creation and change, `import_from` and `download_file` use the API alone. | [bpg/proxmox provider](https://search.opentofu.org/provider/bpg/proxmox/latest) |
| The installer runs unattended from an answer file since 8.2-1. `proxmox-auto-install-assistant prepare-iso <iso> --fetch-from iso --answer-file <file>` embeds it. `[global]` takes exactly one of `root-password` and `root-password-hashed`; `reboot-mode = "power-off"` exists since 8.4-1, and the `[first-boot]` hook (`source`, `ordering`) since 8.3-1. | [Proxmox VE automated installation](https://pve.proxmox.com/wiki/Automated_Installation) |
| The installer ISOs carry a checksum file each, for example `proxmox-ve_9.2-1.iso` and `proxmox-ve_9.2-1.iso.sha256`. | [Proxmox VE ISO downloads](https://enterprise.proxmox.com/iso/) |
| A Proxmox VE guest runs its own KVM guests when the host's `kvm_intel` or `kvm_amd` has `nested` on and the guest's CPU type is `host`. Without hardware assistance nested guests run 10 times slower or more, and a guest with nesting active cannot be live-migrated. | [Proxmox VE nested virtualization](https://pve.proxmox.com/wiki/Nested_Virtualization) |
| The VM option `kvm` (default 1) enables or disables KVM hardware virtualization. | [qm(1)](https://pve.proxmox.com/pve-docs/qm.1.html) |
| GitHub-hosted x64 Linux runners offer KVM since April 2024; the runner user needs access to `/dev/kvm`. The arm64 fleet has no KVM device, and nested virtualization is not officially supported on hosted runners. | [GitHub changelog 2024-04-02](https://github.blog/changelog/2024-04-02-github-actions-hardware-accelerated-android-virtualization-now-available/), [community discussion 160591](https://github.com/orgs/community/discussions/160591), [runner-images#14062](https://github.com/actions/runner-images/issues/14062) |
| QEMU passes a file to the guest with `-fw_cfg name=opt/<reverse domain>/<item>,file=<path>`; names under `opt/` belong to the user. | [QEMU fw_cfg](https://www.qemu.org/docs/master/specs/fw_cfg.html) |

## Decisions

1. **A pool and a token per workspace.** `workspace apply` (102) creates, through `pveum` inside the Proxmox VE that the flavor of decision 3 runs:
   - the pool `ws-<id>`;
   - the user `ws-<id>@pve` without a password;
   - a privilege-separated token `ws-<id>@pve!provision`;
   - its ACLs: the role `InfinitoWorkspace` on `/pool/ws-<id>`, `Datastore.AllocateSpace` and `Datastore.Audit` on the workspace's storage only, `SDN.Use` on the workspace's bridge only, and `VM.Clone` on the two VM templates of [116](116-proxmox-vms-from-kvm-and-emulated-templates.md) only.

   `InfinitoWorkspace` holds the VM privileges the `proxmox` root module of 104 needs to create, configure, start, stop and delete a VM: CPU, memory, disk, network, cloud-init and options, but no `Sys.*`, no `Permissions.*` and no privilege outside the pool; the clone right on the templates (116 decision 3) is the one ACL outside it. The README lists them, and a test pins the list. The token goes to `tenant/data/ws-<id>-provision/proxmox` (105) as the fields `token_id` (`ws-<id>@pve!provision`) and `secret`, and nowhere else; the provision runner joins them as `PROXMOX_VE_API_TOKEN` `<token_id>=<secret>`, the form `bpg/proxmox` takes (`roles/web-app-semaphore/files/opentofu/credentials.json`). `destroy` refuses while the pool holds a VM, and otherwise removes the token, the user and the pool.
2. **API only.** The workspace token gets no SSH access to the node, so the `proxmox` root module uses no snippet, no `source_file` and no `idmap`. Cloud-init stays with what the API sets: user, keys, network and DNS. So Proxmox returns no `host_key` in the provision output, and the first contact pins the host key (104 decision 4, store decision 17).
3. **Two runtime flavors, `vm` by default (operator direction and picks 2026-11-13: "echoserver runs Arch. Important: Proxmox is also tested in CI. Best platform-agnostic.").** `services.proxmox.flavor` in `meta/services.yml` defaults to `vm`, and `meta/variants.yml` holds one row per flavor, so CI deploys both, in the core pattern of `services.matrix.flavor` (`roles/web-app-matrix/meta/services.yml`, `roles/web-app-matrix/meta/variants.yml`). Each flavor's steps live in `tasks/flavors/vm.yml` and `tasks/flavors/container.yml`; the pool, token and RBAC steps are shared and run against whichever Proxmox VE the flavor started.
   - **`vm`, the default.** The role's container runs QEMU with KVM, which boots Proxmox VE as its guest. It needs a container engine and `/dev/kvm` only, so one role runs on echoserver's Arch, on every distribution of the CI axis and inside the dev stack's `target`, with no host package and no host daemon. The launcher image builds from the official Debian base with Debian's QEMU package at a pinned version, so the role still uses no third-party image. The container runs as a UID of its own with `/dev/kvm` as its only device, all capabilities dropped and `no-new-privileges`. QEMU's user-mode network forwards the guest's port 8006 to the container, so the front proxy and the agent broker keep reaching `proxmox:8006`. None of the grants of `compose.yml.j2` applies. Root in Proxmox VE is root in the guest only: a QEMU escape out of a VM inside Proxmox VE lands in the guest, and an escape out of the guest lands in an unprivileged container. So the co-hosting refusal does not run, and the role deploys beside Keycloak and OpenBao. The role runs its `pveum` and Perl steps (`files/perl/`, the RBAC sync) inside the guest over SSH from the launcher container, on a port the user-mode network forwards to the container's loopback only, and break-glass access takes the same path. The container's limits hold the guest's CPUs and memory plus QEMU's overhead, and the capacity check of `00_core.yml` measures the guest.
   - **`container`, opt-in for a dedicated host.** Today's container runs Proxmox VE itself, so agent VMs (093) run at full speed without nesting. Only this flavor renders the grants of `compose.yml.j2` and runs the co-hosting refusal of `00_core.yml`, because root in this container is root on the host. The refusal has no override (operator pick 2026-11-13): `services.proxmox.shared_host` (`meta/services.yml`, `vars/main.yml`) is removed, CI included, so this flavor never runs on a host with `web-app-keycloak`, `svc-ai-litellm` or `web-app-openbao`.
4. **The `vm` guest image comes from the official installer, unattended.** The two flavors carry one pin each: `services.proxmox.ve.iso` pins the `vm` ISO by file name and SHA-256, and the package pins of `meta/services.yml` stay for `container`. The version updater bumps both, and a test holds them on the same Proxmox VE release.
   - The image build verifies the ISO and embeds core's answer file with `prepare-iso --fetch-from iso`. The answer file sets `reboot-mode = "power-off"`, a `root-password-hashed` of a password the build discards, and a `[first-boot]` hook. The build boots the ISO under QEMU and KVM onto an empty disk and keeps the disk when the installer powers off.
   - The image holds no secret of any deployment. It is tagged by ISO and answer file digest, published by the image workflow like the CI images, and pulled like any image; a host that cannot pull it builds it.
   - Each deploy boots a copy-on-write overlay on the image. The deploy hands the guest its hostname, root password hash and the launcher's SSH public key as a QEMU `fw_cfg` item under `opt/` (Upstream). On first boot the hook applies them and regenerates the SSH host keys, the machine id and the node certificate, so no two deployments share a key.
5. **Nested KVM where the host has it (`vm`).** The launcher starts the guest with CPU type `host`. The deploy reads `nested` of the host's `kvm_intel` or `kvm_amd`, writes the result to the deploy log and to OpenBao at `platform/data/provision/proxmox-<host>` beside the endpoint. With nesting on, as on echoserver, VMs inside Proxmox VE run with KVM. Without it, as on GitHub-hosted runners, where nested virtualization is not supported, they run with `kvm: 0`: slower, same API. The `proxmox` root module of 104 takes `kvm` from the catalog region of the target and applies it by cloning the matching template of [116](116-proxmox-vms-from-kvm-and-emulated-templates.md).
6. **CI deploys both flavors.** `web-app-proxmox` moves to `alpha` once both variant rows are green on amd64, so CI deploys them on every branch run. It declares `architectures: [amd64]`, because the arm64 runners have no KVM and the pinned ISO is the amd64 one. On an amd64 runner without `/dev/kvm` the row fails and names the device; the role is never skipped silently. The `container` row runs on two hosts, so the refusal holds there too. It reuses the swarm harness's lab, whose privileged systemd hosts share one bridge, and adds a non-swarm host the way `backup-host` is added: a service behind its own profile (`compose/swarm/compose.yml`), brought up by `scripts/tests/deploy/swarm/routine/01_bootstrap.sh`, with host vars written by `routine/02_provision_inventory.sh`. The row deploys `web-app-proxmox` alone on that host, and Keycloak with the rest of the row on the other.
7. **The test target.** The store's Proxmox lane uses a real Proxmox VE that this role deploys, never a fake (store decision 18): the `vm` flavor on echoserver for the store's stacks, and both flavors in the dev stack's `target` for core's CI.
8. **An API listener behind the host firewall, like Incus (operator pick B, 2026-11-23).** The public domain refuses every request that carries an API token, so token clients reach `pveproxy` on a listener of their own, as [109](109-incus-api-listener-and-project-per-workspace.md) decision 1 does for Incus: `services.proxmox.api.enabled` (default `false`) publishes the container's port 8006 on port `services.proxmox.ports.public.api` of `services.proxmox.api.bind`, a port of the port registry, and the role's own nftables table admits that port only from `services.proxmox.api.allowed_sources`. `pveproxy` serves a deploy-generated certificate whose subjectAltName is the host name the consumers dial, because `bpg/proxmox` checks that name and the node certificate holds only the node, `localhost` and addresses. The deploy stores `endpoint`, `certificate` and `fingerprint` at `platform/data/provision/proxmox-<host>`. `bpg/proxmox` `v0.119.0` has no CA option, so the provision runner writes `certificate` to `servercerts/<host>.crt` of its task and points `SSL_CERT_DIR` there (`roles/web-app-semaphore/files/opentofu/credentials.json`). No client trusts the server blindly.

Rejected:

- A host of its own for Proxmox VE (option A): it costs a server, and CI would still not test the role.
- A virtual machine in `svc-virt-incus` (option B): Incus is a host package for Debian and Arch only (`roles/svc-virt-incus/README.md`), so the CI distributions lack it.
- `services.proxmox.shared_host: true` on echoserver (option C): root in the container would be root on echoserver.
- libvirt on the host: a distribution package and a root daemon on every host.
- Proxmox VE on a Debian cloud image: a second install path beside the official installer, assembled by core.
