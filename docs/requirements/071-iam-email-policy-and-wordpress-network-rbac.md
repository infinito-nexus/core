# 071 - IAM Email Policy and WordPress Network RBAC

## User Story

As a platform operator, I want every address an application trusts for login to be either owned by the platform or proven by its user, and WordPress Multisite to grant each user exactly the rights their groups name on every site of the network, so that no user can take over another account by changing their email and no administrator loses rights by signing in.

## Decisions (2026-11-01)

1. The email policy is a setting in `roles/web-app-keycloak/meta/services.yml`.
2. With the mail provider in the deployment, the primary address of every user is `<username>@<DOMAIN_PRIMARY>`, set automatically and not changeable by the user. Every user also holds a secondary address; registration requires it by default. Confirmations go to the secondary address, and changing it needs a confirmation link sent to the new address.
3. Without the mail provider, the user's external address is the primary address. A change takes effect only after a confirmation link sent to the new address through the configured SMTP relay; without any SMTP, only an administrator can change it.
4. The policy is recorded in the inventory and defaults to `external`, so an existing inventory keeps its external primary addresses, changeable only through a confirmation link. A new inventory that holds the mail provider, `svc-db-openldap` and `web-app-keycloak` is created with `policy: mailbox`. Switching an existing inventory to mailbox is the operator's setting; that switch makes each existing external address the user's secondary address.
5. WordPress Multisite keeps domain tenancy and the `network-administrator` role in its variant, because a single site has no tenant paths; a role granted without a tenant scope applies on every site of the network.
6. A new RBAC role `site-owner` gives its members their own site `<username>.user.blog.<DOMAIN_PRIMARY>`, created on their first SSO login. Without a wildcard certificate, the sites are created at deploy for the inventory users holding the role.
7. Leaving `site-owner` archives the user's site without deleting its content; rejoining restores it.
8. The Joomla plugin keeps overwriting the user's groups from Keycloak on every login; locking the profile fields belongs to requirement 072.
9. Keycloak's own `email` field holds the address Keycloak mails to: the secondary address with a mail provider, the primary address without one. The mailbox address is a separate read-only attribute stored in LDAP `mail`, and the `email` claim and SAML read it in mailbox mode.

Applications that cannot require email_verified:

- No lever in the app's configuration: web-app-listmonk, web-app-mobilizon, web-app-litellm, web-app-fider, web-app-taiga (only by patching the owned fork), web-app-decidim (only by a role-side patch).
- Built-in, not configurable: web-app-penpot. It checks `email_verified` only when linking to a password or LDAP profile.
- Cannot require it, so linking by email is switched off or patched out: web-app-zammad, web-app-gitlab, web-app-bigbluebutton, web-app-gitea, web-app-weblate.
- The app cannot, but the role's own glue does: web-app-shopware (role gate / JMESPath), web-app-semaphore (`email_claim` template), web-app-baserow, web-app-n8n, web-app-erpnext (`login.py`).

Applications that cannot link an SSO login by `sub` or `preferred_username` instead of by email:

- No lever in the app's configuration: web-app-listmonk, web-app-mobilizon, web-app-litellm, web-app-penpot, web-app-fider (it tries `sub` first, but nothing turns its email fallback off), web-app-taiga (only by patching the owned fork) and web-app-decidim (only by a role-side patch).
- The app matches by email only, so the role gates that match on a verified address: web-app-discourse (the OIDC authenticator cannot match by username), web-app-shopware (AdminOpenAuth resolves the email first; the role gate refuses without `email_verified`) and web-app-semaphore (`GetUserByLoginOrEmail` keys on the address the `email_claim` template emits only while `email_verified` is true).

Applications that link by `sub`/`preferred_username` but keep native accounts that SSO no longer reaches (a login that would claim one by email fails instead): web-app-zammad and web-app-mastodon outside the deploy-time binding, web-app-weblate and web-app-bigbluebutton for native-only accounts.

Known limitations (criterion 36):

- web-app-erpnext: an e-mail changed in Keycloak reaches the account at the next `sys-ctl-mtn-rbac-sync` run or deploy, which renames the account found by its `keycloak` or `directory` `User Social Login` row (roles/web-app-erpnext/files/python/apply/rbac_roles.py `former_account`); until then the sign-in is refused instead of creating a second account (roles/web-app-erpnext/files/python/infinito_rbac/infinito_rbac/login.py `refusal`). A member bound to two accounts, or whose former account another member now holds by address, gets neither renamed (roles/web-app-erpnext/TODO.md).
  - Fix option for the 15-minute window: rename in the sign-in under `frappe.set_user("Administrator")`, because `frappe.rename_doc` takes no `ignore_permissions` and `User.after_rename` renames `Notification Settings` with a permission check the Guest session fails.
- web-app-penpot: Penpot finds a profile only by e-mail, so a changed address registers a second profile (roles/web-app-penpot/TODO.md).
  - Fix option: roles/web-app-penpot/files/sql/rbac/reconcile.sql sets `profile.email` from the directory where the stored `:oidc/preferred-username` prop equals the member's username (prop encoding unverified); upstream keying of the profile by the OIDC subject is the clean fix.

Findings outside the table:
