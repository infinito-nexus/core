# 104 - Runner Image: OpenTofu and Root Modules

## User Story

As the operator of a platform that provisions customer servers at Hetzner, IONOS, SCS, Proxmox and Incus, I want one pinned OpenTofu with an offline provider mirror and one core root module per provider in the provision runner, fed only with schema-checked values, with its state locked and encrypted per workspace, so that every server is created and destroyed by reviewed platform code and no customer file or value runs as infrastructure code.

## Background

The store's requirement 062 (`infinito-nexus/gui: docs/requirements/062-slim-store-orders-provisioned-through-platform-roles.md`, decisions 8, 11 and 18, criteria 062:80, 062:105, 062:132-136) needs this core side. Decision 18 places the root modules in core, baked into the runner image and versioned with the core tag. The store line writes the modules in a core sidetree, with the IAM line's consent per bundle; this requirement is their contract.

### Today

- No core file installs or runs OpenTofu or Terraform: the root `Dockerfile`, `cli/`, `plugins/`, `utils/` and every role's tasks hold neither; the two hits under `roles/web-app-semaphore` are descriptions (`meta/main.yml`, `README.md`).
- The runner builds on the Infinito.Nexus image of the deploy (`roles/web-app-semaphore/files/runner/Dockerfile:5`) and links its scripts from that image's core tree (`Dockerfile`). A file under `roles/web-app-semaphore/files/` is therefore in the runner image of the same core tag.
- The only cloud API core drives is reverse DNS at Hetzner (`hetzner.hcloud` in `requirements/requirements.galaxy.yml`, used by `roles/sys-dns-hetzner-rdns/tasks/flavors/cloud.yml`).
- Core selects one of several implementations of a role by a flavor key: the default sits in `meta/services.yml` (`services.matrix.flavor` at `roles/web-app-matrix/meta/services.yml`), each other flavor is a row of `meta/variants.yml` that CI deploys (`roles/web-app-matrix/meta/variants.yml`), and each flavor's tasks live in `tasks/flavors/<flavor>.yml` (`roles/sys-dns-hetzner-rdns/tasks/flavors/`).
- Platform records in the Cloudflare zone are written by `sys-dns-cloudflare-records` (`roles/sys-dns-cloudflare-records/README.md`).

## Decisions

1. **Provisioning runs on the platform's provision runner.** The platform project `<SOFTWARE_NAME> Provision` (102 decision 2) holds, per workspace, the locked templates `provision ws-<id>`, `destroy ws-<id>` and `unlock ws-<id>`, and `dns ws-<id>` of [115](115-dns-record-for-bring-your-own-servers.md). `workspace apply` creates them. They run on the provision runner, never on a workspace runner. That runner holds tokens that cannot be scoped per workspace (Hetzner Cloud, IONOS) and the DNS credentials. A workspace runner runs code a workspace member can change, so it never holds them (store criterion 062:136). The per-workspace templates give each workspace its own `template_id`, which its OpenBao role binds (105). The store starts and reads them under decision 10. The provision runner gets the egress proxy of 102 decision 6, with the provider API hosts, the DNS endpoint of the deploy zone, OpenBao, the S3 endpoint, Gitea and the Semaphore server on its list.
2. **Pinned OpenTofu with an offline mirror.** The runner build installs one pinned OpenTofu release of at least 1.10.0 from its release archive and checks its SHA-256 sum, which core pins. For every root module the build mirrors the providers its `.terraform.lock.hcl` pins (`tofu providers mirror`). The image's CLI configuration names only that `filesystem_mirror`. A provider that is missing fails the build, never a task.
3. **Root modules in core.** `roles/web-app-semaphore/files/opentofu/roots/<provider>/` holds one root module each for `hetzner`, `ionos`, `scs`, `proxmox` and `incus`. Each pins its providers to exact versions and carries its lock file, which the updater of [121](121-opentofu-provider-pin-updater.md) keeps current. `roles/web-app-semaphore/files/opentofu/modules/dns-<flavor>/` holds the DNS child module of each flavor of decision 9, and the provision script copies the selected one into the task directory as `modules/dns`, so every root sources one path. The modules sit in the core tree of the image, so they follow the core tag.
4. **One interface.** `roles/web-app-semaphore/files/opentofu/interface.json` is a JSON Schema of the inputs plus the list of outputs. Every root takes exactly these inputs:
   - `name`: `<SALES_ORDER>-<LINE>` (decision 6), which names the server and so MUST be a hostname label: `^(?=[A-Za-z])[A-Za-z0-9-]{0,62}[A-Za-z0-9]$`, at most 63 characters, starting with a letter and ending with a letter or digit. Incus refuses an instance name that is longer, has a leading or trailing `-` or is a number (Upstream); the leading letter is the store's stricter rule;
   - `flavor`: `demo` or `cloud`;
   - `size`: a catalog size the module maps to a server type;
   - `region`;
   - `ssh_public_key`;
   - `dns_label`: a DNS label matching `^(?!-)[a-z0-9-]{1,63}(?<!-)$`, the same pattern the `deploy` survey holds ([103](103-semaphore-pin-task-jwt-and-locked-templates.md) decision 7).

   Every root returns exactly these outputs:
   - `host`: its public addresses;
   - `host_key`: the SSH host public key;
   - `server_id`;
   - `fqdn`.

   The store pins `host_key` (105 decision 6) and passes `host` and `host_key` to the workspace's `deploy`, `update`, `backup` and `restart` templates as `HOST` and `HOST_KEY` (103 decisions 7 and 8). `host_key` comes from a key the module generates and installs through the provider's cloud-init user data. A provider that cannot take user data over its API leaves it empty, and the first contact pins the key (110 for Proxmox).

   A root maps `region` to provider settings from the catalog, which each deployment sets ([118](118-provision-catalog-per-deployment.md)). For `proxmox` these are the node, the storage and `kvm`, which the catalog region sets to false for a target without nested KVM (110 decision 5), so a VM there starts emulated.
5. **DNS in the same state.** Each root creates the per-deploy record `<dns_label>.ws-<id>.<deploy zone>` with the `dns` module, so `tofu destroy` removes it with the server (store decision 18), and all names of a workspace share one suffix. Decision 9 sets the zone and the flavor, and `apply` passes the zone to the run ([117](117-workspace-values-of-a-provision-run.md)).
6. **Values only, from JSON.** `provision`, `destroy` and `unlock` take two survey variables with target `env` (103 decision 4): `SALES_ORDER`, which MUST match `^[A-Za-z][A-Za-z0-9-]{0,55}$`, and `LINE`, which MUST match `^[1-9][0-9]{0,5}$` (operator pick, 2026-11-13, the store's patterns; no leading zero since 2026-11-14, so `7` and `007` cannot name the same line twice). A `LINE` holds no `-`, so the last `-` of a name built from both separates them. The longest pair joins to 56 + 1 + 6 = 63 characters, starts with the letter of `SALES_ORDER` and ends with a digit of `LINE`, so every valid pair is a valid `name` (decision 4). The store rejects an order whose Sales Order does not match at intake, before any server exists, so a malformed name never reaches a provider. The provision script reads one `provision/<SALES_ORDER>-<LINE>.tfvars.json` from the workspace checkout and validates it against `interface.json`: no unknown key, typed values, a size and region from the catalog. It refuses the run when the checkout holds any `*.tf`, `*.tf.json`, `*.tofu`, `*.tofu.json`, `.terraformrc` or `.tofurc`. It copies the root module from the image into the task directory and runs OpenTofu there, never in the checkout. It clears every `TF_*` variable it did not set itself, so a template environment cannot pass `TF_CLI_ARGS`.
7. **State per Sales Order and line.** The S3 backend uses:
   - the workspace's bucket `ws-<id>-state` (108);
   - the key `<SALES_ORDER>/<LINE>.tfstate`, never the run, so a retry applies to the same server (store criterion 062:133);
   - `use_lockfile = true`;
   - the SeaweedFS endpoint with the S3-compatible settings above.

   The backend takes its keys from a private file of the task ([119](119-state-backend-keys-from-a-private-file.md)). The state is encrypted through `TF_ENCRYPTION`, with the key provider `openbao` on the workspace's transit key (105) and `enforced = true` for state and plan.
8. **Stale lock recovery.** `unlock ws-<id>` takes `SALES_ORDER` and `LINE` (decision 6). It refuses while a `provision` or `destroy` task of that workspace is running, and otherwise runs `tofu force-unlock -force` with the lock id read from the `.tflock` object.
9. **The deploy zone in three DNS flavors (operator picks, 2026-11-13).** Store decision 18 puts the per-deploy records in "a subzone of `infinito.nexus` on Cloudflare". The operator asked for a zone that scales and works without the Enterprise plan. A Cloudflare zone caps its records at 200 on Free and 3,500 on Pro or Business, and a Cloudflare token writes every record of its zone (Upstream). `services.semaphore.workspaces.dns.flavor` in `roles/web-app-semaphore/meta/services.yml` picks the flavor, in the core pattern of the Today section: `knot` is the default, and `meta/variants.yml` holds one row each for `route53` and `cloudflare`, so CI deploys all three. Each flavor's tasks live in `roles/web-app-semaphore/tasks/flavors/dns/<flavor>.yml`.
   - **`knot`, the default.** A new role `svc-dns-knot` runs Knot DNS as the authoritative server of the subzone `services.semaphore.workspaces.dns.zone`, signed with DNSSEC. The platform deploy writes the subzone's NS records, its nameservers' addresses and its DS record into the `infinito.nexus` zone through `sys-dns-cloudflare-records`; delegation works on every plan. Each further host of the role's group runs a secondary, fed by zone transfer with TSIG, so the names survive the loss of one host. `workspace apply` creates the TSIG key `ws-<id>.<subzone>`, writes it to `tenant/data/ws-<id>-provision/dns` (105) and adds it to one ACL with `action: update`, `update-owner: key`, `update-owner-match: sub-or-equal` and `update-type` A, AAAA, CNAME and TXT (CNAME for a BYO host name, [115](115-dns-record-for-bring-your-own-servers.md) decision 7). So a key changes only names at or below its own name. The module writes with the `hashicorp/dns` provider over RFC 2136. `workspace destroy` removes the key.
   - **`route53`.** The subzone is a Route 53 hosted zone in an AWS account that holds this zone only, delegated from `infinito.nexus` the same way. `workspace apply` creates one IAM user per workspace. Its policy allows `ChangeResourceRecordSets` on that hosted zone only when every name matches `*.ws-<id>.<subzone>` (`ForAllValues:StringLike` on `route53:ChangeResourceRecordSetsNormalizedRecordNames`) and every type is A, AAAA, CNAME or TXT (`route53:ChangeResourceRecordSetsRecordTypes`); the reads the provider needs beside it are in [120](120-route53-read-grants-for-the-record-lifecycle.md). Its access key goes to `tenant/data/ws-<id>-provision/dns`. The AWS credential that creates IAM users goes to `platform/data/workspaces/route53`, which the workspace operation reads and no provision task does.
   - **`cloudflare`.** A pool of registered domains, each a Cloudflare zone with a token scoped to it at `platform/data/provision/cloudflare/<zone>`. `workspace apply` places a new workspace in the first zone below its record limit and refuses when every zone is full. Its records are named `<dns_label>.ws-<id>.<zone>`. A zone token changes every record of its zone, so a leaked token reaches every workspace placed in that zone and nothing beyond it. The README states this reach, and no two zones share a token.

   A live write under `route53` or `cloudflare` needs that account's credentials in the inventory. A CI row without them deploys the flavor, runs its rendering tests and reports the live checks as not run, naming the missing credential.
10. **The store runs its workspace's provision templates and changes none (operator pick, 2026-11-13).** The store's Semaphore account holds the built-in role `guest` in the provision project; the deploy sets it. `workspace apply` adds one template grant for the role `guest` with `CanRunProjectTasks` and `CanReadProject` to each of `provision ws-<id>`, `destroy ws-<id>` and `unlock ws-<id>`, and `destroy` removes the grants with the templates. So the store:
    - starts, stops, confirms and rejects tasks of exactly the templates `apply` granted, and of no template added to the project later;
    - reads every template, task and task output of the project, which `guest` allows because Semaphore checks every read against `CanReadProject` (Upstream);
    - changes nothing, because every change asks for `CanManageProjectResources`, which neither `guest` nor a grant of `apply` holds.

    A grant applies to every holder of its role and the community edition has no custom role (Upstream). So the store's account MUST be the only member of the provision project that is not a Semaphore admin, and the deploy's post-converge query fails the deploy when another such member exists or a grant holds another bit. The provision task output therefore MUST NOT carry a secret: the store reads all of it.
11. **A customer's own provider token (Store ask 28, robot pick, 2026-11-14).** `provision` and `destroy` take a third survey variable with target `env`, `PROVIDER_TOKEN`, which MUST be `platform` or `workspace` (`$defs.provider_token` of `interface.json`). `platform` takes the platform's token of the provider, as before. `workspace` takes the customer's token from the KV key `tenant/data/ws-<id>-provision/providers/<provider>`, whose one field is `token`, for the token providers `hetzner` and `ionos` (`workspace_secrets` in `credentials.json`). Neither value falls back to the other: `workspace` refuses before OpenTofu runs when the key, its `token` field or its value is missing or empty, and on a provider without a customer token. Workspace mode serves hetzner and ionos; scs refuses it until a customer application-credential contract exists (Store ask 28, robot pick, 2026-11-14), because an OpenStack application credential is a credential id, a secret and an auth URL, not one token. The customer token reaches OpenTofu as the provider's environment variable, as the platform token does, never on an argument or in a log line. Only the `ws-<id>-provision` jwt role reads the key, under the tenant policy's read on `tenant/data/<role>/*`, so the `ws-<id>` workspace runner never sees it. The store writes the key through its create and update grant on `tenant/data/ws-*` and never reads it. No policy changes.
12. **The task output contract (Store R9 of GUI 062, question a and b, 2026-11-14).** The store reads two results from the task output, each the LAST stdout line of its task and one JSON object on one line:
    - a successful `provision` ends with `{"<output name>": <value>, ...}`, the outputs of decision 4 by name with their values, e.g. `{"host": ["192.0.2.10"], "host_key": "ssh-ed25519 ...", "server_id": "4711", "fqdn": "app.ws-<id>.<zone>"}`;
    - a successful `destroy` ends with `{"destroyed": [<resource address>, ...], "state": "deleted"}`. The list holds what `tofu state list` named before the destroy, empty for a line without a state. A line that holds neither a state nor its `.provision.json` record, such as one whose provision the live catalogs refused, has nothing to destroy: the destroy selects no provider, runs no OpenTofu, deletes a stale `.tflock` and ends with the empty list, so a cleanup or refund destroy cannot be refused by catalogs that have changed since. The script prints it only after `tofu state list` is empty again, the state, its `.tflock` and the record of decision 13 are deleted, and a `HEAD` of the state finds nothing. A destroy that leaves a resource in the state fails with exit code 1, deletes nothing and prints no such line.

    Exit code 0 means done, 1 failed and 2 refused; a failed or refused task prints neither line. A `dns` create and remove of [115](115-dns-record-for-bring-your-own-servers.md) end with the same two objects.
13. **A destroy takes its provider from the provision record, never from the live catalogs (Store R9 of GUI 062, 2026-11-14).** Right before `tofu apply`, `provision` writes `<SALES_ORDER>/<LINE>.provision.json` into the workspace bucket: `{"provider": "<provider>", "catalog": <the catalog of that provider it ran with>}`. So a partial apply leaves one too. The state is encrypted (decision 7), so the provider cannot be read from it. The object is plain JSON in the same bucket and holds catalog values only, no credential. `destroy` still checks the tfvars and their `name`, takes the provider and `catalog.json` from the record, checks the record's catalog against `$defs.catalog` and refuses a record whose catalog offers no region of the tfvars. So a region retired from the live catalogs, or a second provider whose catalog lists the same region, no longer blocks a destroy (`REFUND_DESTROY_FAILED`). A state from before this record has none: `destroy` then selects from the live catalogs as `provision` does and says so on stdout, `<SALES_ORDER>/<LINE>.provision.json is missing, so the destroy takes <provider> from the live catalogs`. A successful destroy deletes the record with the state and its `.tflock`. A `provision` whose live selection picks another provider than an existing record refuses with exit code 2 before OpenTofu runs or the record changes, naming the line and both providers, because applying another provider's root to the state would plan the destruction of the first server; a re-provision with the same provider rewrites the record with the current catalog (`test_a_provider_switch_is_refused_before_tofu`, `test_a_re_provision_with_the_same_provider_rewrites_the_record` and the negative control `test_negative_control_without_the_refusal_a_switch_reaches_apply` in `test_provision_sh.py`).

Rejected:

- Semaphore's native OpenTofu app: it runs the `.tf` files of the repository checkout (103).
- Provisioning on the workspace runner: the unscoped tokens and the DNS credentials would reach code a member can change.
- HCL `.tfvars`: JSON is checked by the same schema the store uses.
- The first round's deploy zones (an own Cloudflare zone, an Enterprise subdomain zone, the records in `infinito.nexus` itself): turned down by the operator on 2026-11-13; each is capped or needs Enterprise, and a zone token reaches every record of its zone.
- `task_runner` for the store in the provision project: it runs, stops and approves every template and workflow of the project, also one added later.
- A relay through the `workspace` task, which would start the provision task for the store: the admin token that task mints would live for the whole provision.
- Sales Order and line both in `[A-Za-z0-9-]`: `provision/A-1-2.tfvars.json` would name both `A-1` line `2` and `A` line `1-2`.
- A `SALES_ORDER` of up to 64 characters: the joined name would exceed the 63 characters of a hostname label, which Incus refuses as an instance name.

## Acceptance Criteria

### Image
